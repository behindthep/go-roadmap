### Типизация Go
Go статически и строго типизированный язык - максимальную скорость работы и безопасность.
#### Статическая vs Динамическая. Когда проверяются типы
##### Статическая (Go, Java, C++): на этапе компиляции (до запуска)
Тип данных связывается с переменной при объявлении, известен на этапе компиляции и не меняется.
Операторы и совместимость типов проверяются во время компиляции.
Ошибки типов видны до запуска, код не соберётся. Предсказуемость.
Исключение: Бестиповые константы - пока тип не зафиксирован, могут временно подстраиваться под тип переменной при присвоении.
##### Динамическая (Python, JavaScript, PHP):
Тип привязан не к переменной, а к значению в ней. Тип узнаётся в runtime, переменная хранящая строку, далее в коде может начать хранить число.
Ошибки типов обнаруживаются уже во время работы.

#### Строгая/Сильная vs Слабая. Насколько язык строг к неявным преобразованиям типов во время выполнения (runtime)
##### Строгая/Сильная (Go, Python):
Переменной закреплён тип данных и язык запрещает неявные (автоматические) приведения, которые могут привести к потере смысла (сложение строки и числа).
    - 5 != 5.0, int + float64 к ошибке компиляции (даже свой тип на основе сущ. - для Go разные сущности).
    - Необходимость явного преобразования для разных типов: float64(myInt) + myFloat.
##### Слабая (JavaScript, PHP, C):
Язык пытается неявно (автоматически) приводит когда считает уместным. В JS "5" + 2 ="52", "5" - 2 = 3. Может быть не очевидное поведение.

#### Утиная типизация (Duck Typing)
- Популярна в динамических языках. «Если это выглядит как утка, плавает как утка и крякает как утка, то это утка».
- Программе неважно, какого класса объект, главное — чтобы у него был вызванный метод.
В Go есть её строгий аналог — интерфейсы, которые проверяются еще при компиляции.

### Разница между var, := и const:
#### 1. Выделение памяти и адресация (RAM)
- var и := — физически выделяет память в RAM (на стеке или в куче). К ней можно применить оператор взятия адреса &myVar.
- const — не выделяет память в RAM и не имеет адреса. Сущ. только на этапе компиляции, компилятор подставляет значение в код (inline). &myConst к ошибке компиляции.
#### 2. Область видимости (Где можно объявить)
- var и const — Объявляется как внутри функций, так и глобально вне их на уровне пакета. Если имя с заглавной буквы, её можно экспортировать в другие пакеты.
- := — Доступна строго внутри функций. Идеальна для локальных счетчиков в циклах for или коротких проверок в if.
#### 3. Обязательность инициализации (Когда задавать значение)
- var — Если значение не указано, нужно обязательно написать тип. Переменная получит zero-value типа.
- := — Нельзя опустить значение или явно указать тип данных.
- const — Значение должно быть определено и известно еще на этапе компиляции. Тип можно указать явно, либо он автоматически будут выведен из значения.
#### 4. Допустимые типы данных
- var и := — поддерживает любые типы данных (базовые, слайсы, массивы, структуры, интерфейсы, функции...). := - просто сокращение для var.
- const — поддерживает только базовые типы. Создать константный слайс, массив или структуру в Go нельзя.
#### 5. Множественное объявление (В несколько переменных)
- var — поддерживает группировку в блоки var (...). В одну строку можно объявить несколько переменных (var a, b = 1, "ok";  name, age := "Alice", 30), но типы нужно опустить для автоматического вывода.
- := — не поддерживает группировку в ().
- const — поддерживает блоки const (...). Если внутри блока пропустить значение для следующей строки, Go автоматически скопирует выражение из предыдущей. Внутри автоинкремент iota.
#### 6. Специфика типизации (Вывод типов)
- var и := — если тип не указан явно, он фиксируется при первом присвоении (из списка дефолтных).
- const — могут быть «бестиповыми» (untyped) - уникальная фича констант: остаются «чистым значением» и автоматически подстраиваются под тип выражения (const Pi = 3.14 сработает и с float32, и с float64).

### Встроенные типы данных:
#### Целочисленные типы:
Два типа числовых данных, которые отличаются характером их размеров (статическим или динамическим).
Большинство системных архитектур сегодня 32 / 64 -битные.
- независимые от архитектуры типы (int32), размер данных в битах постоянный, независимо на какой машине выполняется / для какой архитектуры компилируете код.
- зависимым от архитектуры. int при компиляции для 32/64-битной архитектуры, размер 32/64 бита.

Диапазоны основаны на размере бита. Для двоичных данных 8 битов могут представлять 256 уникальных возможных значений.
Архитектурно-независимые целочисленные типы:
- int8:         от -128                       до 127                        занимает 1 байт  (8 бит).
- int16:        от -32768                     до 32767                      занимает 2 байта (16 бит)
- int32 / rune: от -2147483648                до 2147483647                 занимает 4 байта (32 бита)
- int64:        от –9 223 372 036 854 775 808 до 9 223 372 036 854 775 807  занимает 8 байт  (64 бита)
- uint8 / byte: от 0                          до 255                        занимает 1 байт
- uint16:       от 0                          до 65535                      занимает 2 байта
- uint32:       от 0                          до 4294967295                 занимает 4 байта
- uint64:       от 0                          до 18 446 744 073 709 551 615 занимает 8 байт

* rune может быть 1-4 байтами (диапазон определяемым int32). rune для представления символа Unicode, символы ASCII могут быть представлены только int32.
* byte и uint8 после компиляции программы идентичны, byte для представления символьных данных в числовой форме, uint8 в программе представлен числом. Прояснить, когда в элементах символьных строк программа использует байты в качестве общего вычислительного измерения (в отличие от маленьких целых чисел, не связанных с таким измерением данных).

Зависимые от архитектуры целочисленные типы:
- int:  целое число со знаком.   В зависимости о платформы занимает в памяти 4 байта (int32)  / 8 байт (int64).
- uint: целое число беззнаковое. В зависимости о платформы занимает в памяти 4 байта (uint32) / 8 байт (uint64).

uintptr — беззнаковый целочисленный тип, размер в байтах = размеру указателя на архитектуре процессора (32 бита/4 байта на 32-разрядных системах и 64 бита/8 байт на 64-разрядных системах). Не ссылка на объект в памяти. Число (адрес), может хранить битовое представление указателя.
На 64‑битной архитектуре uintptr хранит беззнаковое целое число размером ровно 64 бита (принимать значения от 0 до 2^64 − 1). На 32‑битной — соответственно 32 бита.
Его размер специально сделан таким, чтобы он в точности совпадал с размером машинного указателя на этой платформе — это нужно, чтобы без потерь упаковывать адреса памяти в число и потом восстанавливать из него указатель.

int и uint имеют наиболее эффективный размер для определенной платформы (32 или 64 бита). Это наиболее используемый тип для представления целых чисел в программе.
Различные компиляторы могут предоставлять различный размер для этих типов даже для одной и той же платформы.

Переменной не указан тип, но присвоено целочисленное значение, ее тип - int.

#### Числа с плавающей точкой (floating-point numbers):
- float32: от 1.4 *10^-45  (-3.4 *10^38)  до 3.4 *10^38  (для положительных). в памяти 4 байта IEEE-754 32-bit. Обеспечивает 6  десятичных цифр точности.
- float64: от 4.9 *10^-324 (-1.8 *10^308) до 1.8 *10^308 (для положительных). в памяти 8 байт  IEEE-754 64-bit. Обеспечивает 15 десятичных цифр точности.
IEEE-754 - технический стандарт для представления и обработки вещественных чисел (с плавающей точкой) в компьютерах.

Действительные числа (вещественные числа (R) — все числа, которые можно разместить на числовой прямой).
Числа с плавающей точкой для представления действительных чисел, которые не могут быть выражены как целые.
Множество действительных чисел состоит из объединения двух непересекающихся множеств:
рациональные (можно представить в виде дроби) и иррациональные (pi или sqrt(2) имеют бесконечную и непериодическую последовательность цифр после запятой) числа. Компьютерная память конечна, записать или сохранить иррациональное число в точности внутри типа float невозможно.

#### Комплексные числа:
1+2i
- complex64:  вещественная и мнимая части float32.
- complex128: вещественная и мнимая части float64.

#### Логический тип bool:
Значения true и false всегда будут объявляться строчными буквами t и f, это их предварительно объявленные идентификаторы в Go.

#### Строки string:
Строке соответствует строковый литерал - последовательность символов.
Структура данных байтовый срез, доступный только для чтения.
Байт в строке представляет часть символа в кодировке UTF-8, кодировкой переменной длины и может представлять любой символ Unicode.

Строки в Go неизменяемы, после создания строки ее содержимое нельзя изменить посимвольно.
Присваивая переменной str новую строку можно, переменная — это ссылка; ты просто перенаправляешь её на другой объект в памяти.

Строка содержать управляющие последовательности с обратного слеша \:
- \n: переход на новую строку
- \r: возврат каретки
- \t: табуляция
- \": двойная кавычка внутри строк
- \\: обратный слеш

- `` - необработанный строковый литерал. Символы внутри обратных кавычек отображаться как записаны, за исключением символа обратной кавычки.
a := `Say "hello"
to Go!\n`
Say "hello"
to Go!\n`

- "" - интерпретируемый строковый литерал. Внутри кавычек любой символ, кроме новой строки и незакрытых двойных кавычек. Двойные кавычки внутри - обратный слэш в качестве escape-символа.

#### Строки с символами UTF-8
UTF-8 – схема для кодирования символов переменной длины 1-4 байта. Для данных UTF-8 (спец символов 世) тип-псевдоним rune (int32), может состоять из 1-4 байтов.
Римские символы (A), могут быть представлены значением ASCII (65).

for и range для индексации строк, подсчета байтов в строке. range индексирует символы в строке, возвращая за раз один символ и индекс байта, в котором находится символ в строке.

```go
a := "Hello, 世界"
for i, c := range a {
    fmt.Printf("%d: %s\n", i, string(c))
}
fmt.Println("length of 'Hello, 世界': ", len(a))

// 0: H
// 1: e
// 2: l
// 3: l
// 4: o
// 5: ,
// 6:
// 7: 世  символу требуется 3 байта
// 10: 界
// length of 'Hello, 世界': 13  строка длиннее, чем количество символов
```

#### Неявная типизация
При определении переменной опускать тип, если инициализируем значением. Компилятор на основе значения неявно выводит тип переменной (int, float64)

Узнать тип переменной - спецификатор "%T" при выводе функцией:
```go

```

#### Выбор размера
Выбор правильного размера больше зависит от производительности целевой архитектуры, чем от самих данных.
Если не знаешь последствия для производительности программы:
Для целочисленных данных зависимые типы int или uint, вместо int64 или uint64. Увеличивает скорость обработки для целевой архитектуры.
- int64 и компилируете код в 32-битной архитектуре, для обработки значений минимум вдвое больше времени, для перемещения данных по архитектуре доп. циклы ЦП.
- int программа подстроится под архитектуру и быстрее обрабатываться.
Заранее знаете, не будете превышать определенный диапазон размеров, архитектурно-независимые типы – увеличить скорость и уменьшить использование памяти.
Знаете, данные не превысят значение 100 и только положительны, uint8 программу более эффективной, потребует меньше памяти.

#### Переполнение и сворачивание данных
Сохранить значение, превышает размер типа, Go переполнить и свернуть число.
Зависит, когда вычислено значение – во время компиляции или выполнения.

```go
var maxUint32 uint32 = 4294967295 // Max uint32 size
```

Прибавим во время выполнения 1 к переменной при ее назначении, до компиляции - свернется до 0:

```go
var maxUint32 uint32 = 4294967295 + 1
```

Если время компиляции компилятор определить, что значение велико для хранения в указанном типе, ошибку constant 4294967296 overflows uint32.


Zero value - значение по умолчанию, которое получает переменная, если её объявить без инициализации.
В Go не бывает неинициализированных переменных. У переменной будет предсказуемое, стартовое значение.
Во многих языках переменная без инициализации, потенциальная проблема: мусор из памяти, null, undefined, сюрприз в рантайме.

- Числа             - int / int64 / float64 - 0
- string                                    - ""
- bool                                      - false
- Указатели pointer - *User                 - nil
- slice                                     - nil
- map                                       - nil
- Каналы            - chan int              - nil
- func()                                    - nil
- interface         - error / io.Reader     - nil
- struct{}                                  - все поля получают свой zero values

### Nil slice vs nil map

* Nil slice - безопасен

```go
func main() {
	var s []int

	fmt.Println(len(s), cap(s)) // 0 0

	s = append(s, 1) // сработает
	fmt.Println(s) // [1]
}
```

- range по nil slice не упадёт (0 итераций)
- чтение/запись элементов - ок через append. append возвращает новый slice header, и Go сам может выделить память под элементы.

* Nil map - читать можно, писать нельзя

Код с nil map компилируется, ошибка вылезет уже в рантайме.

```go
func main() {
	var m map[string]int

    fmt.Println(len(m)) // 0

    fmt.Println(m["key"]) // 0
	// m := make(map[string]int)
    m["key"] = 1 // panic: assignment to entry in nil map
}
```

- чтение работает (верёнт zero value)
- range сработает (0 итераций)
- писать в в nil map нельзя, будет panic. Карта должна быть явно инициализирована. Запись требует внутренней структуры Хеш-таблицы, у nil map её просто нет.

#### Nil slice и empty slice - не всегда одно и то же

```go
var s1 []int  // nil slice превращается в null
s2 := []int{} // Пустой slice превращается в []

s1 == nil -> true
s2 == nil -> false
```

Если ты пишешь API, тесты - это может быть критично. Важно при JSON-маршалинге.

### Zero Values в Структурах

При создании структуры её поля получают zero values типов. Не заполнять вручную, если тебе подходит состояние по умолчанию.

```go
Type User struct {
    Name string
    Age int
    Active bool
}

func main() {
	var u User
	fmt.Printf("%+v\n", u) // {Name: Age:0 Active:false}
}
```

#### Не все поля безопасны.
Если в структуре есть map, slice, chan или что-то, где для работы нужна инициализация, даже если zero value может быть валидным, но неудобным или опасным.
Если внутри map и собираешься туда писать, нужен конструктор или явная инициализация.

```go
type Cache struct {
	items map[string]string
}

var c Cache
c.items["key"] = "value" // panic, map внутри структуры = nil.
```

### Необходимость конструктора (NewXxx)

##### Да NewXxx:
* zero value невалиден, опасен или требует обязательной инициализации внутренних полей
* внутри есть map, в которую нужно писать
* внутри есть chan, который должен работать сразу
* у типа есть обязательные зависимости

```go
type Item struct {
	Value string
}

type Cache struct {
    items map[string]Item // nil
}

func NewCache() *Cache {
    return &Cache{
        items: make(map[string]Item),
    }
}
```

NewCache() нужен, иначе поле items будет nil, и запись в карту вызовет panic.

##### Нет NewXxx:
* С zero value структуры можно работать сразу после объявления
* конструктор не даёт пользы

```go
type Counter struct {
    count int // 0
}
func (c *Counter) inc() {
    c.count++
}
```

### Паттерн: типы, у которых zero value рабочий и их можно использовать сразу после объявления.
Не тратить время на лишнюю инициализацию (make), вызывать конструктор, писать New.

Примеры из стандартной библиотеки:
- sync.Mutex{}
- bytes.Buffer{}
- strings.Builder{}
- sync.WaitGroup{}
- sync.Once{}

```go
import (
	"bytes"
	"fmt"
	"sync"
)

func main() {
	var mu sync.Mutex
	mu.Lock()
	mu.Unlock()

	var buf bytes.Buffer
	buf.WriteString("hello")

	fmt.Println(buf.String()) // hello
}
```

### Проектирование собственных типов, структур и пакетов
Если проектируешь свой тип, задавать себе вопрос:
Что будет, если кто-то создаст мой тип var x MyType и сразу начнёт им пользоваться?
Если всё работает нормальный - тип спроектирован удачно. Если ответ: "ну тут надо не забыть ещё вызвать инициализацию, иначе всё развалится", если код падает, требует обязательного Init() или скрытых условий, интерфейс у типа не дружелюбный.

Если можно сделать, чтобы zero value был полезен, делай так.

- Удобное проектирование API. Хороший Go-код часто можно использовать сразу, без лишних действий.
- Меньше шансов забыть инициализацию.
- Меньше бойлерплейта. Не надо везде городить конструкторы и ручную инициализацию.
- API выглядит чище и понятнее. Читаемость. Когда zero value рабочий, код становится проще для всех, кто будет его поддерживать.

### Nil channel блокирует выполнение
Такой канал нельзя использовать для отправки и получения. Операции с ним будут блокироваться.

```go
var ch chan int
ch <- 1   // блокировка
<-ch      // блокировка

ch = make(chan int)
ch <- 1
```

### Nil interface и typed nil - не одно и то же
Интерфейс = nil только когда у него нет ни типа, ни значения.

```go
var err error
fmt.Println(err == nil) // true

var p *MyError = nil
var err error = p
fmt.Println(err == nil) // false
```

Внутри интерфейса уже лежит тип *MyError, даже если само значение nil.
Эта часто кусает в обработке ошибок.


### iota инструмент для работы с константами
Применяется когда нужны:
- последовательные значения: статусы и режимы
- сделать enum-подобный тип
- битовые флаги и маски

iota — предопределённый идентификатор, создавать последовательные константы. Внутренний счётчик компилятора для констант внутри блока const, к которому можно добавить операции.

```go
const (
    Pending = 0
    Active = 1
    Closed = 2
)

// Копируется не результат, а исходная строка

const (
    A = iota // iota == 0
    B // iota == 1
    C // iota == 2
)
func main() {
    fmt.Println(A, B, C) // 0 1 2
}
```

iota — специальный идентификатор, имеет смысл только в объявлениях констант (работает даже для одиночной константы).
Компилятор в блоке const на каждой спецификации константы увеличивает iota.

Iota сбрасывается в каждом новом блоке const

```go
const (
    A = iota // счётчик 0
    B // = iota // 1
    C // = iota // 2
)

const (
    X = iota // 0
    Y // 1
)
```

### Повторение выражения и автонумерация
Внутри блока const Go повторяет предыдущее выражение (не готовое значение) автоматически, но iota в нём уже новое.

Задать правило один раз и дальше продолжать последовательность, улучшает читаемость, где констант много.

```go
// Читается хуже:
const (
    A, B = iota + 1, iota + 2
    C, D
    E, F
)

A = 1, B = 2
C = 2, D = 3
E = 3, F = 4
```

Правило:
Если статья, библиотека или код пишется для людей, использовать iota, чтобы смысл считывался почти сразу.

```go
const (
    A = iota + 1 // определяющее выражение. 1
    B // 2
    C // 3
)
```

### Пропуск значения

Во многих прикладных сценариях начинать с 1 читается естественнее:
- уровни
- порядковые номера
- приоритеты
- состояния, где 0 хочется оставить под «неизвестно»

```go
const (
    A = iota + 1
    _ // пустой идентификатор
    C
    D
)

A = 1
C = 3
D = 4
```

Компилятор всё равно вычисляет значение строки, но ты явно говоришь: это значение мне не нужно, не давай ему имя.

#### Когда пропуск полезен:
- зарезервировать значение
- начать enum не с 0
- оставить специальное место под неизвестный статус
- удобно собрать битовые флаги

Паттерн с пропуском нуля:
```go
const (
    _ = iota
    Read
    Write
    Execute
)
```

### Enum в Go через iota
В Go нет enum, как в некоторых других языках. type + const + iota позволяет имитировать близко и идиоматично.

внутри константного блока, если у константы нет своего выражения, компилятор копирует строку выражения из предыдущей константы — целиком, вместе с типом.

enum-подобный набор констант:

```go
type Status int

const ( // не просто числа, а значения типа Status
    Pending Status = iota
    Active
    Blocked
    Deleted
)

const (
    a = iota        // int
    b               // int — скопировано a
    c = 1 << iota   // int, значение 4
    d               // скопировано c → 8
    e = "hi"        // string
    f               // string, снова "hi" — iota тут уже не участвует.
)
```

Компилятор копирует всю строку выражения (включая тип) из предыдущей константы для следующих строк, где выражение не указано. Если посреди блока написать новое выражение с другим типом — дальше будет копироваться уже оно.

```go
type LogLevel string
	const (
		Debug LogLevel = "1"
		Info
		Warn
		Error
	)
	fmt.Println(Debug, Info, Warn, Error) // 1 1 1 1

// Чтобы enum красиво печатался
func (d Status) String() string { // (d Status) — приёмник (receiver): функция «принадлежит» типу Status, а d — имя переменной этого типа внутри метода. receiver - способ «привязать» функцию к типу, чтобы она стала его методом
    return [...]string{"Pending", "Active", "Blocked", "Deleted"}[d]
}
fmt.Println(Pending) // Pending
```

Создание массива строк [...]string{"Pending", "Active", "Blocked", "Deleted"} — объявление массива из 4 строк.
... в типе [...T]: «посчитай длину сам по количеству элементов в литерале». компилятор видит 4 элемента и делает тип [4]string.

[d] — это доступ к элементу массива по индексу d. d — это значение типа Status, а Status — это просто int (0, 1, 2, 3…), его можно использовать как индекс.

```
func handleStatus(s Stauts) {
    // работает со статусом
}
Pending -> handleStatus(Pending)
Active  -> handleStatus(Active)
Blocked -> handleStatus(Blocked)
Deleted -> handleStatus(Deleted)
```

Лучше, чем const без типа. Тип делает код безопаснее и выразительнее.

```go
func SetStatus(s Status) // видно, что речь про конкретный набор состояний. говорит больше, чем:
func SetStatus(s int) {} // случайно передать любое число
```

enum-подобные типы хорошо заходят в:
- статусы заказов
- роли пользователя
- уровни логирования
- направления
- режимы работы
- типы событий

#### Когда лучше быть осторожнее
Если значения должны быть стабильными на уровне внешнего API, базы или протокола, не всегда стоит полагаться на порядок строк.
Если потом кто-то вставит новую константу посередине, численные значения сдвинутся.

Как избежать тихой поломки? Если численные значения уже публичны или зафиксированы контрактом, лучше либо:
- не вставлять новые значения посередине
- либо задавать значения явно

### Битовые флаги, маски и 1 << iota
Иногда нужно хранить несколько булевых состояний в одном числе.
- можно читать;
- можно писать;
- можно удалять;
- можно экспортировать.

Вместо четырёх отдельных bool - разные биты одного значения.

```go
const (
    Read = 1 << iota // iota = 0, 1 << 0 = 1
    Write // iota = 1, 1 << 1 = 2
    Delete // iota = 2, 1 << 2 = 4
    Export
)

Read = 1   // 2^0 0001
Write = 2  // 2^1 0010
Delete = 4 // 2^2 0100
Export = 8 // 2^3 1000

const (
    Read = 1 << iota
    Write
    Delete
    Export
)

// маски
permissions := Read | Write // 0001 | 0010 -> 0011. | - объединение флагов.

if permissions&Write != 0 {
    fmt.Println("write allowed")
}
```

Где это встречается:
- права доступа
- конфигурационные флаги
- режимы работы
- low-level код
- системные библиотеки
- производительные внутренние структуры

#### Когда не надо использовать битовые флаги
Если задача простая и читабельность важнее компактности, отдельные булевы поля или enum честнее.

### Когда iota уместна, а когда лучше без неё:
iota хороша, когда:
- значения идут по естественной последовательности, порядок значений читается сразу

iota часто не нужна, лучше задать значения руками если:
- значения не образуют ясной последовательности.
- значения уже фиксированы внешним стандартом. Внешние протоколы, БД или API.
- числа общеизвестны и важны сами по себе. Для HTTP-статусов значения 200 и 404, не 0 и 1.
- формула получается слишком хитрой
- читатель кода без паузы не понимает, что происходит

Спроси себя:
Iota реально делает код короче и понятнее или просто делает его умнее на вид? Если второе, лучше не надо.

- Если значения внутренние и живут только внутри кода, iota подходит.
- Если enum на iota уже используется в БД, логах, API или внешнем контракте, вставка новой константы в середину может сдвинуть все численные значения. Кто-то добавил новый статус и не понял, что поменялся весь числовой смысл.
Если значения уже стали частью внешнего контракта, относись к ним как к публичному API и не двигай бездумно.

Упражнение: 1 << iota. Сделай флаги Read, Write, Delete, объедини Read | Write и проверь, что флаг Write включён.
