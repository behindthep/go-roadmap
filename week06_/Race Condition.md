Что такое shared memory в Go

### Shared Memory в Go
Несколько goroutine одновременно обращаются к одной области памяти

#### Схема доступа к общей памяти:
Несколько горутин одновременно читают и пишут в общую область памяти:
- Goroutine 1 (читает / пишет counter, map, cache) <-> Общая область памяти
- Goroutine 2 (читает / пишет counter, map, cache) <-> Общая область памяти
- Goroutine 3 (читает / пишет counter, map, cache) <-> Общая область памяти
- Goroutine 4 (читает / пишет counter, map, cache) <-> Общая область памяти
- Goroutine 5 (читает / пишет counter, map, cache) <-> Общая область памяти
- Goroutine N (читает / пишет counter, map, cache) <-> Общая область памяти

#### Содержимое общей области памяти:
- counter (int = 42): [ 0 | 0 | 0 | 4 | 2 ]

### Race condition в Go

### Race Condition
Две goroutine одновременно пишут в одну переменную. Из-за этого результат непредсказуем и ломается.

```go
counter := 0
go increment(&counter)
go increment(&counter)
time.Sleep(time.Second)
fmt.Println(counter) // ???
```

#### Схема гонки данных:
- ОБЩАЯ ПЕРЕМЕННАЯ counter: начальное значение 0
- Goroutine A (increment(&counter)):
  1. читает counter -> 0 (одновременно с Goroutine B)
  2. увеличивает на 1 -> 1
  3. записывает в counter -> 1
- Goroutine B (increment(&counter)):
  1. читает counter -> 0 (одновременно с Goroutine A)
  2. увеличивает на 1 -> 1
  3. записывает в counter -> 1 (последняя запись перезаписывает значение в counter)

#### ИТОГ
- Результат: 1
- Ожидалось: 2 (Одна из записей потерялась)
- Хронология: 0 (начало) -> 0 (A читает) -> 1 (A пишет 1) -> 1 (B пишет 1, перезаписал — потерялась эта запись)

#### Как сделать правильно
Использовать синхронизацию:
- sync.Mutex
- atomic
- каналы (channel)
- другие примитивы sync

Race condition — это когда результат зависит от порядка выполнения goroutine, а его предсказать нельзя.

Goroutine легко запускать, но из-за этого легко получить одну из самых неприятных ошибок в конкурентном коде — race condition.

Race condition (гонка данных) возникает, когда результат программы зависит от того, в каком порядке выполнились goroutine.

две goroutine одновременно трогают одни и те же данные

Если обе только читают — обычно проблемы нет.

Проблема, когда хотя бы одна goroutine пишет.

одна goroutine читает переменную, другая в этот момент её меняет

несколько goroutine пишут в одну map
несколько goroutine делают append в один slice
одна goroutine меняет структуру, а другая одновременно читает её поля
На первый взгляд код может выглядеть нормально. Он даже может тысячу раз отработать без ошибки. А потом внезапно начнёт давать странный результат.

ошибка зависит от порядка выполнения, а порядок выполнения goroutine не гарантирован.

Почему counter++ не безопасен

```go
package main
import (
"fmt"
"sync"
)
func main() {
var wg sync.WaitGroup
counter := 0
for i := 0; i < 1000; i++ {
wg.Add(1)
go func() {
defer wg.Done()
counter++
}()
}
wg.Wait()
fmt.Println(counter)
}
```

Кажется, что в конце должно быть 1000.

Но counter++ — не одна атомарная операция. Внутри там несколько шагов:

1. прочитать counter
2. увеличить значение на 1
3. записать новое значение обратно

представь две goroutine.

counter сейчас равен 0.

Первая goroutine читает 0.

Вторая goroutine тоже читает 0.

Первая увеличивает до 1 и записывает.

Вторая тоже увеличивает своё старое значение до 1 и записывает.

В итоге две goroutine выполнили работу, а в счётчике получилось 1, хотя ожидалось 2.

Схема:

counter = 0

Goroutine A читает 0
Goroutine B читает 0

Goroutine A пишет 1
Goroutine B пишет 1

ожидали 2
получили 1

Одна запись потерялась — это и есть race condition.

Почему race condition сложно заметить
Race condition часто не проявляется сразу. Сегодня программа выводит правильный результат. Завтра на другой машине — неправильный. Под нагрузкой — падает. В тестах — иногда зелёная, иногда красная.

Причина в том, что scheduler Go сам решает, когда какую goroutine выполнять.

Scheduler (планировщик) — это часть runtime Go, которая распределяет goroutine по потокам ОС.

Он постоянно решает:

какую goroutine сейчас запускать
какую остановить
какую разбудить после ожидания
какую перенести на другой поток

Из-за этого порядок выполнения goroutine заранее не гарантирован, ты не контролируешь точный порядок выполнения.

нельзя писать код в надежде, что эта goroutine точно успеет первой. В конкурентном коде такая логика ломается.

### Race condition с map
С map ситуация ещё опаснее. Обычная map в Go не безопасна для конкурентной записи.

```go
package main
func main() {
m := map[int]int{}
go func() {
m[1] = 1
}()
go func() {
m[2] = 2
}()
select {}
}
```

Такой код может упасть с ошибкой:
fatal error: concurrent map writes

если несколько goroutine работают с одной map, нужна синхронизация: sync.Mutex, sync.RWMutex, sync.Map или другая архитектура, где состоянием владеет одна goroutine.

sync.Map: когда используют concurrent map
Для некоторых сценариев в Go есть sync.Map.

```go
var cache sync.Map
cache.Store("user", 42)
value, ok := cache.Load("user")
```

sync.Map уже умеет безопасно работать конкурентно, но это не улучшенная map для всего подряд.

Обычно sync.Map используют:
для read-heavy нагрузки
кэшей
редко изменяемых структур
shared registry
long-lived concurrent state

Во многих случаях обычная map + mutex будет проще и быстрее.

sync.Map — инструмент под конкретные сценарии, а не универсальная замена map.

### sync.Map в действии
Несколько goroutine безопасно читают и пишут в concurrent map

#### Схема операций с sync.Map:
Содержимое sync.Map (Key -> Value):
- user:1 -> Alice
- user:2 -> Bob
- user:3 -> Charlie
- ... -> ...

Операции горутин:
- Goroutine 1: Load("user:1") -> read
- Goroutine 2: Store("user:4", "Diana") -> write
- Goroutine 3: Load("user:2") -> read
- Goroutine 4: Store("user:5", "Eve") -> write
- Goroutine 5: Load("user:3") -> read
- Goroutine N: Store("user:6", "Frank") -> write

Итог: Нет ошибок concurrent map writes (Потокобезопасно)
- read (Load, Range)
- write (Store, Delete, LoadOrStore)

#### Что даёт sync.Map
- Безопасно — нет паники concurrent map writes
- Высокая производительность — для часто читаемых данных
- Простота — не нужны mutex для базовых кейсов
- Проверено — используется в стандартной библиотеке Go

Для обычного запуска:

### Mutex: когда канал не нужен

### 7. Mutex: защита общей переменной
Mutex — это «замок». Только одна goroutine может войти внутрь критической секции и работать с общей переменной. Остальные ждут своей очереди.

```go
var mu sync.Mutex
var counter int

func increment() {
    mu.Lock()   // захват замка
    counter++   // критическая секция
    mu.Unlock() // освобождение замка
}
```

#### Схема работы MUTEX (mu):
- Goroutine 1: хочет войти в критическую секцию -> ждёт (получит доступ после освобождения)
- КРИТИЧЕСКАЯ СЕКЦИЯ (замок захвачен): Goroutine 2 выполняет работу с общей переменной -> ОБЩАЯ ПЕРЕМЕННАЯ (counter = 42) -> освобождает замок
- Goroutine 3: хочет войти в критическую секцию -> ждёт (получит доступ после освобождения)

Легенда схемы:
- выполняется (есть замок)
- ждёт (замок занят)
- получит доступ позже

Идея: Mutex гарантирует, что в критической секции работает только одна goroutine за раз, поэтому данные не ломаются.

#### ВАЖНО
Всегда вызывай Unlock() в defer, чтобы замок точно освободился, даже если произошла ошибка или panic.
```go
mu.Lock()
defer mu.Unlock() // так безопаснее
// ... критическая секция ...
```

Channels часто показывают как главный инструмент конкурентности в Go. Но это не значит, что ими нужно решать всё.

Если задача — защитить общую переменную, часто проще использовать sync.Mutex.

Пример исправления counter:

```go
package main
import (
"fmt"
"sync"
)
func main() {
var wg sync.WaitGroup
var mu sync.Mutex
counter := 0
for i := 0; i < 1000; i++ {
wg.Add(1)
go func() {
defer wg.Done()
mu.Lock()
counter++
mu.Unlock()
}()
}
wg.Wait()
fmt.Println(counter)
}
```

Mutex работает как замок.

Пока одна goroutine находится внутри критической секции, другая ждёт.

Правило: Нужно передать данные между goroutine — думай про channel. Нужно защитить общую память — думай про mutex.

Общая память + запись из нескольких goroutine = нужна синхронизация

Это не железный закон, но хорошая стартовая логика для новичка.

### Channels vs Mutex: что использовать

### Channels vs Mutex в Go
Два разных инструмента для конкурентности

#### CHANNELS
Передача данных между goroutine
Схема: Goroutine A (отправитель) -> channel -> Goroutine A (получатель)
*(Примечание: на схеме у получателя подписано Goroutine A, по смыслу это получатель)*

- Передаём данные из одной goroutine в другую
- Goroutine не делят память
- Безопасность встроена в сам канал

Когда использовать? Когда нужно передать данные или сигнал между goroutine

#### MUTEX
Защита общей памяти
Схема: Goroutine A (читает / пишет) и Goroutine B (читает / пишет) работают с Shared Memory (counter = 42) через Lock и Unlock

- Несколько goroutine работают с одной областью памяти
- Нужно явно защищать доступ к данным
- Гибкий контроль (можно читать и писать)

Когда использовать? Когда несколько goroutine должны читать или изменять одни и те же данные

Channels — это про передачу, Mutex — про защиту. Выбирай инструмент под задачу.

Новички пытаются решить вообще всё через channels. Но channels — не замена mutex.

Channels — для передачи данных.
Mutex — для защиты shared memory.

Если тебе нужно защитить: counter, map, slice, shared state — то mutex обычно проще.

Если нужно:
передать результат
построить pipeline
сделать worker pool
синхронизировать стадии обработки
То channels подходят лучше.

В production Go-коде почти всегда используются оба подхода.

sync.RWMutex

### 8. RWMutex: много читателей, один писатель
RWMutex — это «умный» замок.
- RLock() — можно читать одновременно из разных goroutine.
- Lock() — только один писатель, и он ждёт, пока все читатели закончат.

```go
var mu sync.RWMutex
var data map[string]int

// Чтение
mu.RLock() // можно нескольким goroutine
value := data["key"]
mu.RUnlock()

// Запись
mu.Lock() // только один писатель
data["key"] = 42
mu.Unlock()
```

#### Схема работы ЧТЕНИЕ (RLock):
несколько читателей одновременно читают ОБЩИЕ ДАННЫЕ (data map[string]int):
- Reader 1 (goroutine): mu.RLock() -> читает data map[string]int -> mu.RUnlock()
- Reader 2 (goroutine): mu.RLock() -> читает data map[string]int -> mu.RUnlock()
- Reader 3 (goroutine): mu.RLock() -> читает data map[string]int -> mu.RUnlock()
- ...
- Reader N (goroutine): mu.RLock() -> читает data map[string]int -> mu.RUnlock()
Все читатели могут читать одновременно

#### Схема работы ЗАПИСЬ (Lock):
писатель должен ждать, пока все читатели закончат:
1. Writer (goroutine): mu.Lock() -> ждёт... (читатели ещё активны)
2. RWMutex (mu): RLock счётчик = 4 (активные читатели), Writer ожидает = 1
3. после того как все читатели освободили RLock -> Writer (goroutine): mu.Lock() -> пишет в data map[string]int -> mu.Unlock()
Писатель получает исключительный доступ, когда читателей нет

Легенда схемы:
- читает (RLock)
- пишет (Lock)
- ждёт замок

Зачем нужен RWMutex? Когда чтений много, а записей мало — RWMutex даёт большую параллельность, чем обычный Mutex.

#### Важно!
- Нельзя вызывать Lock, пока есть активные RLock — писатель будет ждать.
- Новые читатели не смогут получить RLock, если уже есть ожидающий писатель.

Иногда данных много читают и редко изменяют:
кэш настроек
справочник
локальное состояние сервиса
таблица маршрутов
in-memory конфиг

Если использовать обычный Mutex, читатели будут блокировать друг друга, хотя они ничего не меняют.

Для таких случаев есть sync.RWMutex.

Он разделяет блокировки:
RLock() для чтения
Lock() для записи

```go
var mu sync.RWMutex
var cache = map[string]string{}
func get(key string) string {
mu.RLock()
defer mu.RUnlock()
return cache[key]
}
func set(key, value string) {
mu.Lock()
defer mu.Unlock()
cache[key] = value
}
```

Несколько goroutine могут читать одновременно, но когда приходит запись, она получает эксклюзивный доступ.

RWMutex полезен не всегда. Если записей много, он может не дать выигрыша и только усложнить код. Поэтому его используют там, где чтений действительно сильно больше, чем записей.

### Deadlock на mutex
Mutex тоже можно использовать неправильно.

```go
mu.Lock()
mu.Lock()
```

Вторая блокировка зависнет навсегда.

Также deadlock можно получить, если:

забыть Unlock()
взять mutex в разном порядке
получить циклическое ожидание
заблокировать mutex и уйти в долгую операцию
Поэтому конкурентный код — это ещё и про аккуратное управление shared state.

### Deadlock на mutex
Две goroutine держат разные mutex и ждут друг друга

#### Схема взаимной блокировки:
- Goroutine 1:
  1. Lock(mutexA) — успешно (держит/заблокировал mutexA)
  2. Lock(mutexB) — ждёт... (пытается заблокировать mutexB)
- Goroutine 2:
  1. Lock(mutexB) — успешно (держит/заблокировал mutexB)
  2. Lock(mutexA) — ждёт... (пытается заблокировать mutexA)
- Ресурсы в центре:
  - mutexA: Заблокирован goroutine 1
  - mutexB: Заблокирован goroutine 2
  - Между ними циклическая зависимость -> DEADLOCK

Легенда схемы:
- держит (заблокировал)
- ждёт (пытается заблокировать)
- циклическая зависимость

### Atomic operations

### Atomic counter — безопасный счётчик

#### Схема параллельного инкремента:
Несколько горутин одновременно вызывают атомарную операцию увеличения общего счётчика:
- Goroutine 1: atomic.AddInt64(&counter, 1) -> ATOMIC COUNTER
- Goroutine 2: atomic.AddInt64(&counter, 1) -> ATOMIC COUNTER
- Goroutine 3: atomic.AddInt64(&counter, 1) -> ATOMIC COUNTER
- ...
- Goroutine N: atomic.AddInt64(&counter, 1) -> ATOMIC COUNTER

#### Общий счётчик и результат:
- ATOMIC COUNTER (var counter int64): 0 -> 1 -> 2 -> 3 -> ... -> N
- Результат: counter = N

atomic.AddInt64 — атомарная операция. Race condition отсутствует.

Для простых счётчиков иногда используют пакет sync/atomic.

```go
var counter atomic.Int64
counter.Add(1)
fmt.Println(counter.Load())
```

Atomic операции полезны для:
счётчиков
флагов
метрик
простых числовых значений
Но ими не стоит заменять нормальную архитектуру.

Если состояние сложное, лучше использовать mutex, channel или отдельную goroutine-владельца состояния.

### RACE CONDITION В GO
mutex, atomic, shared memory и синхронизация goroutine
Race Condition — это когда несколько goroutine обращаются к общим данным одновременно, и хотя бы один из них пишет.

#### 1. ЧТО ТАКОЕ RACE CONDITION
Состояние гонки — непредсказуемый результат из-за конкурентного доступа к общим данным.

- Плохо (race condition):
```go
var counter int

func main() {
    for i := 0; i < 1000; i++ {
        go func() {
            counter++ // X гонка!
        }()
    }
}
```

- Хорошо (синхронизация):
```go
var (
    counter int
    mu sync.Mutex
)

func main() {
    for i := 0; i < 1000; i++ {
        go func() {
            mu.Lock()
            counter++
            mu.Unlock()
        }()
    }
}
```

#### 2. КАК НАЙТИ RACE CONDITION
Используй race detector (обязательно на собеседованиях):
```bash
go run -race main.go
```

Признаки:
- Плавающие и непредсказуемые результаты
- Падает только под нагрузкой
- Работает локально, но падает в проде

Пример вывода:
```bash
WARNING: DATA RACE
Read at 0x00c000014148 by goroutine 7:
  main.main.func1()
      /main.go:10 +0x6c

Previous write at 0x00c000014148 by goroutine 8:
  main.main.func1()
      /main.go:11 +0x8f
```

#### 3. КАК ЗАЩИТИТЬ SHARED MEMORY (Способ — Когда использовать — Плюсы — Минусы — Пример)

- Mutex (sync.Mutex)
  - Когда использовать: Сложные операции, несколько действий с данными
  - Плюсы: Просто, безопасно, подходит в 99% случаев
  - Минусы: Блокировки, возможен контеншн
  - Пример:
```go
mu.Lock()
// критическая секция
mu.Unlock()
```

- RWMutex (sync.RWMutex)
  - Когда использовать: Много чтений, редкие записи
  - Плюсы: Позволяет параллельные чтения
  - Минусы: Сложнее, можно сделать неправильно
  - Пример:
```go
mu.RLock()
// чтение
mu.RUnlock()
```

- Atomic (sync/atomic)
  - Когда использовать: Примитивные типы: int32/int64/uint32/uint64/uintptr/unsafe.Pointer
  - Плюсы: Высокая производительность, без блокировок
  - Минусы: Только простые операции (Load/Store/Add и т.д.)
  - Пример:
```go
atomic.AddInt64(&counter, 1)
val := atomic.LoadInt64(&counter)
```

- Channels
  - Когда использовать: Передача данных между goroutine
  - Плюсы: Безопасно, без shared memory
  - Минусы: Может быть сложнее по архитектуре
  - Пример:
```go
ch <- value
val := <-ch
```

- sync.Map
  - Когда использовать: Кэш, большое кол-во ключей, частые чтения, редкие записи
  - Плюсы: Оптимизирован для конкурентных нагрузок
  - Минусы: Специфичный API
  - Пример:
```go
m.Store(key, val)
val, ok := m.Load(key)
```

#### 4. ATOMIC: ЧТО МОЖНО ДЕЛАТЬ
- Load / Store
- Add / Sub / And / Or / Swap
- CompareAndSwap (CAS)

```go
var counter int64

atomic.AddInt64(&counter, 1)
v := atomic.LoadInt64(&counter)

ok := atomic.CompareAndSwapInt64(&counter, 10, 20)
if ok {
    // успешно заменили 10 -> 20
}
```
ВАЖНО: Atomic гарантирует атомарность, но не решает сложные проблемы логики. Для нескольких действий используй mutex.

#### 5. ДРУГИЕ ПРИМИТИВЫ СИНХРОНИЗАЦИИ
- WaitGroup — Ждать завершения группы goroutine
- Once — Выполнить инициализацию только один раз
- Cond — Ожидание условия (редко используется)
- Semaphore (канал) — Ограничить количество goroutine

```go
var wg sync.WaitGroup
wg.Add(1)
go func() {
    defer wg.Done()
    // работа
}()
wg.Wait()

var once sync.Once
once.Do(func() {
    // инициализация
})

sem := make(chan struct{}, 5) // лимит 5
sem <- struct{}{}             // заняли слот
// ...
<-sem                         // освободили слот
```

#### 6. HAPPENS-BEFORE (КРАТКО)
Операция A happens-before операции B, если:
- есть синхронизация (mutex, channel send/receive и т.д.)
- тогда изменения в A видны в B

Без happens-before возможна гонка.
Схема: goroutine A (запись) -> synchronization (happens-before) -> goroutine B (чтение)

#### 7. ЛУЧШИЕ ПРАКТИКИ
- Минимизируй shared memory
- Читай данные локально, затем работай
- Держи критические секции короткими
- Используй -race на всех тестах
- Пиши юнит-тесты с параллельными сценариями
- Выбирай правильный примитив под задачу

#### 8. ШПАРГАЛКА
- Сложная логика -> mutex / RWMutex
- Простые счётчики -> atomic
- Передача данных -> channels
- Кэш с ключами -> sync.Map
- Ожидание завершения -> WaitGroup
- Однократная инициализация -> Once
