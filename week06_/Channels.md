### КАНАЛЫ В GO
ПОЛНОЕ РУКОВОДСТВО
Goroutine общаются. Данные в безопасности. Код работает.
ПРОСТО • ПОНЯТНО • НА ПРИМЕРАХ

#### Схема работы канала:
- Отправитель (SEND) -> CHANNEL [ данные в очереди FIFO (ПОРЯДОК СОХРАНЯЕТСЯ) ] -> Получатель (RECEIVE)
- Схема взаимодействия: отправитель -> [ буфер ... ] -> получатель — Общение без блокировок и разделяемой памяти

#### Пример кода:
```go
ch := make(chan int)

go func() {
    for i := 1; i <= 5; i++ {
        ch <- i // отправляем
    }
    close(ch)
}()

for v := range ch {
    fmt.Println(v) // получаем
}
```

Channels (каналы) — это способ обмениваться данными между горутинами. Если goroutine — конкурентные задачи, то channels — механизм связи между ними.

Горутины выполняют работу:

go worker()

А channels позволяют этим goroutine:
передавать данные
синхронизироваться
сообщать о завершении
строить worker pool
делать fan-in/fan-out
управлять конкурентной обработкой

### Как goroutine общаются через каналы
Горутины только запускают конкурентную работу, чтобы им обмениваться данными нужны каналы.

Channel — типизированный канал связи между горутинами.

```go
Создание канала:
ch := make(chan string)

Отправка значения:
ch <- "hello"

Получение значения:
msg := <-ch

Полный пример:
package main
import "fmt"
func main() {
ch := make(chan string)
go func() {
ch <- "hello from goroutine"
}()
msg := <-ch
fmt.Println(msg)
}
```

main goroutine ждёт чтение из канала. Другая goroutine отправляет сообщение. После получения программа продолжает выполнение.

### Goroutine + Channel в Go
Одна goroutine отправляет данные, другая получает

#### Схема передачи:
Goroutine 1 (отправитель) -> отправляет -> channel [ данные ... ] -> получает -> Goroutine 2 (получатель)
(поток данных идёт от отправителя к получателю через канал)

#### Как это работает?
1. Отправитель кладёт значения в channel
2. Получатель забирает значения из channel
3. Channel гарантирует безопасную передачу данных между goroutines

#### Код примера:
```go
func sender(ch chan<- string) {
    messages := []string{"Привет", "Как дела?", "Пока!"}
    for _, msg := range messages {
        ch <- msg // отправка в channel
        fmt.Println("Отправлено:", msg)
        time.Sleep(time.Second)
    }
    close(ch)
}

func receiver(ch <-chan string) {
    for msg := range ch {
        fmt.Println("Получено:", msg)
    }
    fmt.Println("Channel закрыт")
}

func main() {
    ch := make(chan string)
    go sender(ch)   // запускаем отправителя
    go receiver(ch) // запускаем получателя
}
```

### Почему канал блокирует выполнение

Небуферизированный канал синхронизирует отправителя и получателя. Если goroutine отправляет значение в канал, но никто не читает, отправитель блокируется. Если goroutine читает из канала, но никто не пишет, получатель блокируется.

Пример deadlock:

```go
package main
func main() {
ch := make(chan int)
ch <- 1
}
```

Здесь main пытается записать в канал, но другой goroutine для чтения нет. Поэтому программа зависает и падает с ошибкой:

fatal error: all goroutines are asleep - deadlock!

channel — это не просто контейнер с данными, это ещё и механизм синхронизации между goroutine.

### DEADLOCK в Go
Goroutine пытается отправить данные в канал, но receiver отсутствует. Всё заблокировано.

#### Схема блокировки:
- Goroutine (sender): Пытаюсь отправить данные... -> ch <- data (ЗАБЛОКИРОВАНО)
- channel (небуферизированный): Ждёт receiver, чтобы передать данные
- Goroutine (receiver): связь оборвана (X) -> receiver отсутствует

DEADLOCK! Все goroutine спят и ждут события, которое никогда не произойдёт.
```bash
fatal error: all goroutines are asleep - deadlock!
```

#### Пример кода с ошибкой:
```go
package main

func main() {
    ch := make(chan string) // небуферизированный канал
    fmt.Println("Пытаюсь отправить...")
    ch <- "Привет" // блокируется здесь
    fmt.Println("Это не выполнится")
}
```

#### Почему это deadlock?
1. Goroutine пытается отправить данные в канал
2. Канал небуферизированный (ёмкость = 0)
3. Нет goroutine, которая принимает данные
4. Отправитель ждёт навсегда -> программа не может продолжить работу

Как избежать?
Запусти receiver, используй буферизированный канал или select с timeout.

Когда начинаешь работать с каналами, сначала кажется, что всё просто: одна goroutine отправила значение, другая его получила. Но у channels есть важное свойство: они не только передают данные, но и блокируют выполнение, если второй стороны нет.

Это поведение полезно. Благодаря ему горутины могут синхронизироваться без дополнительных флагов и ручных проверок. Но если неправильно выстроить обмен данными, программа может остановиться намертво.

Так появляется deadlock.

Deadlock возникает, когда goroutine ждут друг друга или ждут событие, которое уже никогда не произойдёт. В этот момент ни одна goroutine не может продолжить выполнение, а runtime Golang понимает: программа застряла.

Поэтому появляется ошибка:

fatal error: all goroutines are asleep - deadlock!
Эту ошибку часто видят именно при работе с каналами, потому что отправка и чтение из канала могут блокировать goroutine.

```go
package main
func main() {
ch := make(chan string)
ch <- "hello"
}
```

канал небуферизированный. main пытается отправить значение в ch, но другой goroutine, которая читает из канала, нет.

main goroutine доходит до строки ch <- "hello".
Канал ждёт получателя.
Получателя нет.
main goroutine блокируется.
Других goroutine, которые могли бы что-то сделать, тоже нет.
Runtime Go видит, что все goroutine спят.
Программа падает с deadlock.

проблема не в самом канале. Проблема в том, что мы создали точку ожидания, но не создали того, кто это ожидание разблокирует.

ситуации, где появляется deadlock:

отправили значение в канал, но никто не читает
читаем из канала, но никто не пишет
читаем через range, но канал никогда не закрывают
буфер канала заполнен, а получателя нет
ждём WaitGroup, но забыли вызвать Done
запустили pipeline, но одна из стадий перестала читать данные

Deadlock — не ошибка компиляции и не случайный баг. Код может спокойно скомпилироваться, но зависнуть уже во время выполнения.

В этом и опасность. По синтаксису всё выглядит нормально:
ch <- value

Но для Go эта строка означает не просто «положи значение в канал». Она означает: «передай значение, когда появится получатель». Если получателя нет, goroutine будет ждать.

Чтобы избежать deadlock, всегда проверяй три вещи:
Кто отправляет данные в канал
Кто читает данные из канала
Кто и когда закрывает канал, если чтение идёт через range

Исправленный пример:

```go
package main
import "fmt"
func main() {
ch := make(chan string)
go func() {
ch <- "hello"
}()
msg := <-ch
fmt.Println(msg)
}
```

Теперь есть две стороны:
goroutine отправляет значение
main goroutine читает значение

Обмен состоялся, блокировка снялась, программа завершилась нормально.

Buffered channel и unbuffered channel
Каналы Golang бывают буферизированные и небуферизированные.

### Небуферизованный канал vs Буферизованный канал

#### НЕБУФЕРИЗОВАННЫЙ КАНАЛ (buffer = 0)
Отправитель и получатель синхронизируются напрямую
Схема: SENDER (отправитель) <-> channel <-> RECEIVER (получатель)

Этапы работы:
1. Sender хочет отправить значение в канал
2. Sender блокируется, пока Receiver не будет готов принять значение
3. Receiver получает значение, sender продолжает работу

Как это работает?
- Отправка блокируется, пока получатель не готов.
- Получение блокируется, пока в канале нет данных.
- Всегда происходит рукопожатие (synchronization).

```go
ch := make(chan string) // небуферизированный канал (buffer = 0)
go func() {
    ch <- "Привет" // блокируется здесь
    fmt.Println("Отправлено")
}()

msg := <-ch // разблокирует sender
fmt.Println("Получено: ", msg)
```

#### БУФЕРИЗОВАННЫЙ КАНАЛ (buffer = N)
Данные помещаются в очередь (буфер)
Схема: SENDER (отправитель) -> channel (буфер: 3) [ 1, 2, 3 ] -> RECEIVER (получатель)

Этапы работы:
1. Sender отправляет значение в канал
2. Значение кладётся в буфер. Sender не блокируется (если буфер не переполнен)
3. Receiver забирает значение из буфера
4. Освобождается место в буфере для новых значений

Как это работает?
- Sender блокируется только если буфер переполнен.
- Receiver блокируется только если буфер пуст.
- Позволяет "накопить" несколько значений в очереди.

```go
ch := make(chan string, 3) // буферизированный канал (buffer = 3)
ch <- "A" // не блокируется
ch <- "B" // не блокируется
ch <- "C" // не блокируется
ch <- "D" // блокируется, буфер переполнен

fmt.Println(<-ch) // "A" — место освободилось
ch <- "D" // теперь сработает
```

#### Когда что использовать?
- Небуферизированный канал: Синхронизация, строгая передача данных
- Буферизированный канал: Производительность, очереди, пайплайны

Небуферизированный канал
ch := make(chan int)
Отправитель блокируется, пока получатель не заберёт значение. Такой канал хорош, когда тебе нужна строгая синхронизация.

Буферизированный канал
ch := make(chan int, 3)
У канала есть буфер на 3 элемента.

ch <- 1
ch <- 2
ch <- 3

Эти записи не заблокируются, пока буфер не заполнится. А вот четвёртая запись без чтения уже заблокируется:

ch <- 4 // блокировка, если никто не читает

Когда использовать buffered channel
Буфер полезен, когда отправитель и получатель работают с разной скоростью.

очередь задач
логирование
worker pool
пакетная обработка
временное сглаживание нагрузки

Но буфер не должен быть способом спрятать проблему. Если канал постоянно забит, проблема в архитектуре или скорости обработки.

Закрытие канала в Golang

### ЗАКРЫТИЕ КАНАЛА (close channel)
Sender закрывает канал после отправки всех данных. Receiver дочитывает все значения через range и корректно завершает работу.

#### Схема закрытия канала:
SENDER (отправитель) -> отправляет данные -> CHANNEL (канал) [ данные в буфере ] -> канал закрыт (X) -> RECEIVER (получатель) дочитывает через range
После закрытия новые данные отправлять нельзя.
range продолжает получать значения из канала, пока он не будет закрыт и буфер не опустеет. Когда канал закрыт и данных больше нет — цикл завершается автоматически.

#### Код примера:
```go
// Sender: отправка данных и закрытие канала
func sender(ch chan<- int) {
    for i := 1; i <= 3; i++ {
        fmt.Println("Отправляю:", i)
        ch <- i // отправляем значение в канал
    }
    close(ch) // закрываем канал
    fmt.Println("Канал закрыт")
}

// Receiver: чтение данных через range
func receiver(ch <-chan int) {
    for v := range ch {
        fmt.Println("Получено:", v)
    }
    // цикл завершится после закрытия канала
    fmt.Println("Канал закрыт, чтение завершено")
}
```

#### Особенности close(ch) и range:
- close(ch):
  - Сообщает receiver, что данных больше не будет
  - После close нельзя отправлять данные в канал
- range ch автоматически завершается, когда:
  - канал закрыт
  - и все значения из буфера прочитаны

Итог: sender отправляет данные -> закрывает канал -> receiver читает через range -> завершение без ошибок.
Важно: отправка в закрытый канал вызовет panic: send on closed channel

Канал можно закрыть:
close(ch)

Закрытие означает: новых значений больше не будет.

```go
ch := make(chan int)
go func() {
for i := 0; i < 3; i++ {
ch <- i
}
close(ch)
}()
for v := range ch {
fmt.Println(v)
}
```

range читает из канала, пока канал не закрыт и пока в нём остаются значения.

Кто должен закрывать channel
Обычно канал закрывает отправитель. Потому что только отправитель точно знает, что новых данных больше не будет.

Если записать в закрытый канал, будет panic:

panic: send on closed channel
Если закрыть уже закрытый канал:

panic: close of closed channel
Это одна из самых частых ошибок у новичков.

Что будет при чтении из закрытого канала
Из закрытого канала можно читать. Если в буфере ещё есть значения, они будут прочитаны. Если значений больше нет, чтение вернёт zero value типа.

### ЧТО ПРОИСХОДИТ С ЗАКРЫТЫМ CHANNEL? (closed channel)
После закрытия channel новые значения отправлять нельзя. Receiver дочитывает все оставшиеся значения из буфера. Когда буфер пуст — получает zero value и ok = false.

#### Схема чтения из закрытого канала:
- SENDER (отправитель): Отправляет значения (1, 2, 3) -> ЗАКРЫВАЕТ CHANNEL (CLOSE(ch)) -> После close(ch) отправка невозможна (X)
- CHANNEL (буфер = 3): [ 1, 2, 3 ] [ ЗАКРЫТ ] -> Channel закрыт. Отправка блокирована навсегда.
- RECEIVER (получатель) дочитывает через <-ch:
  - 1 -> ok = true
  - 2 -> ok = true
  - 3 -> ok = true
  - zero value -> ok = false (Когда буфер пуст, receiver получает zero value и ok = false.)

#### ПРИМЕР: SENDER
```go
ch := make(chan int, 3)
ch <- 1
ch <- 2
ch <- 3

close(ch) // закрываем канал
// ch <- 4 // X panic: send on closed channel
```

#### ПРИМЕР: RECEIVER
```go
for {
    v, ok := <-ch // читаем из канала
    if !ok {
        fmt.Println("Канал закрыт, чтение завершено")
        break
    }
    fmt.Printf("Получено: %d (ok = %v)\n", v, ok)
}
```

#### ВЫВОД:
```bash
Получено: 1 (ok = true)
Получено: 2 (ok = true)
Получено: 3 (ok = true)
Канал закрыт, чтение завершено
```

#### КЛЮЧЕВЫЕ МОМЕНТЫ:
- После close(ch) отправлять новые значения нельзя.
- Receiver дочитывает все оставшиеся значения.
- Когда буфер пуст — получает zero value.
- ok = false означает, что channel закрыт.

```go
ch := make(chan int, 1)
ch <- 10
close(ch)
v1 := <-ch // 10
v2 := <-ch // 0
```

Чтобы отличить настоящее значение от zero value, используют второе значение:

```go
v, ok := <-ch
if !ok {
fmt.Println("channel closed")
}
```

ok == false означает, что канал закрыт и значений больше нет.

### Select в Golang

### SELECT: слушаем несколько channels одновременно
select ждёт, пока будет готова операция на любом из каналов, и выполняет соответствующий case.

#### Схема работы select:
Источники каналов:
- ch1: сообщения
- ch2: уведомления
- ch3: ошибки

Все три канала поступают в блок select:
```go
select {
case msg := <-ch1:
    // получили сообщение
case note := <-ch2:
    // получили уведомление
case err := <-ch3:
    // получили ошибку
case <-time.After(5 * time.Second):
    // таймаут
default:
    // ничего не готово
}
```

#### Ветвление реакции по сработавшему кейсу:
- Если в ch1 есть данные — выполнится этот case
- Если в ch2 есть уведомление — выполнится этот case
- Если в ch3 есть ошибка — выполнится этот case
- Если ничего не готово 5 секунд — сработает таймаут (time.After)
- Если ничего не готово и нет default — select будет ждать

#### КАК ЭТО РАБОТАЕТ:
1. select проверяет все каналы
2. Как только любой канал готов — выбирается он
3. Выполняется соответствующий case
4. После выполнения цикл продолжается снова

select слушает всех сразу и реагирует на первого!

#### Когда использовать?
- Много источников данных
- Таймауты и отмена
- Реакция на события из разных мест

#### ПРИМЕР
```go
for {
    select {
    case msg := <-ch1:
        fmt.Println("Сообщение:", msg)
    case note := <-ch2:
        fmt.Println("Уведомление:", note)
    case err := <-ch3:
        fmt.Println("Ошибка:", err)
    case <-time.After(5 * time.Second):
        fmt.Println("Таймаут: ничего не пришло за 5 секунд")
    default:
        fmt.Println("Пока ничего не готово")
    }
}
```

#### ОСОБЕННОСТИ
- select не блокируется, если есть готовый канал
- Если готовы несколько каналов — выбирается случайный (рандомно)
- Часто используется для таймаутов и отмены (context)
- Можно использовать default, чтобы не ждать

select позволяет ждать несколько операций с каналами одновременно.

```go
select {
case msg := <-ch1:
fmt.Println("from ch1:", msg)
case msg := <-ch2:
fmt.Println("from ch2:", msg)
}
```

Если готово несколько каналов, Go выберет один из готовых вариантов.

select часто используют для:

timeout
cancellation
чтения из нескольких каналов
fan-in
graceful shutdown
обработки сигналов
worker pool

Пример с timeout:

```go
select {
case result := <-resultCh:
fmt.Println(result)
case <-time.After(time.Second):
fmt.Println("timeout")
}
```

В production-коде вместо голого time.After часто используют context.Context.

### Pipeline в Go
Pipeline в Go — когда обработка данных разбивается на несколько последовательных этапов.

Представь конвейер на заводе — сначала одна часть системы создаёт данные, потом другая их обрабатывает, потом третья сохраняет результат или отправляет дальше.

В Go такие этапы часто соединяют через каналы.

input → process → output

первая goroutine генерирует данные
отправляет их в channel
следующая goroutine читает данные из канала
обрабатывает их
отправляет дальше в следующий channel
последняя стадия получает готовый результат

channel здесь работает как труба между разными этапами обработки.

идея Pipeline

Каждая goroutine делает только свою часть работы: одна отвечает за чтение, другая за обработку, третья за сохранение.

### Pipeline в Go
Пайплайн — это цепочка стадий, где каждая стадия обрабатывает данные и передаёт их дальше. Стадии работают параллельно и связаны каналами (channels).
Идея: разбиваем большую задачу на маленькие шаги и соединяем их каналами.

#### Схема конвейера стадий:
Источник данных (1, 2, 3, 4, 5 ...) ->
1. INPUT (Получаем данные): Читает данные из источника и отправляет в канал ->
ch1 (chan T): [ 1, 2, 3, 4, 5 ... ] (Канал передаёт данные между стадиями) ->
2. PROCESS (Обрабатываем данные): Берёт данные из ch1, обрабатывает их и отправляет дальше в канал ch2 ->
ch2 (chan U): [ 10, 20, 30, 40, 50 ... ] (Каждая стадия может менять данные или фильтровать их) ->
3. OUTPUT (Отдаём результат): Читает данные из ch2 и передаёт их потребителю (вывод, запись в БД и т.п.) ->
Потребитель данных (10, 20, 30, 40, 50 ...)

#### Пример кода (упрощённо)
```go
func generator(out chan<- int) { // стадия 1: input
    for i := 1; i <= 5; i++ {
        out <- i
    }
    close(out)
}

func square(in <-chan int, out chan<- int) { // стадия 2: process
    for n := range in {
        out <- n * n
    }
    close(out)
}

func printer(in <-chan int) { // стадия 3: output
    for n := range in {
        fmt.Println(n)
    }
}

func main() {
    ch1 := make(chan int)
    ch2 := make(chan int)
    go generator(ch1)
    go square(ch1, ch2)
    printer(ch2)
}
```

#### Что происходит:
1. generator генерирует числа и кладёт их в ch1
2. square читает из ch1, возводит в квадрат и кладёт результат в ch2
3. printer читает из ch2 и выводит результат

#### Зачем нужен пайплайн?
- Параллелизм — стадии работают одновременно, увеличивая пропускную способность.
- Разделение ответственности — каждая стадия делает только свою работу.
- Повторное использование — стадии легко комбинировать и переиспользовать.
- Потоковая обработка — данные обрабатываются по мере поступления, не нужно загружать всё в память.

#### Где используется?
- Чтение и обработка больших файлов (логов, CSV и т.п.).
- ETL-процессы (извлечение -> трансформация -> загрузка).
- Обработка запросов, задач, сообщений в системах.
- Веб-скрейперы, парсеры, анализ данных и многое другое.

Из-за этого код проще масштабировать и распараллеливать.

### Worker Pool в Go
Worker Pool — это паттерн, при котором фиксированное количество воркеров (goroutine) берут задачи из общей очереди (jobs), обрабатывают их и кладут результаты в другую очередь (results).
Идея: вместо запуска сотен goroutine мы переиспользуем ограниченное число воркеров. Это экономит память, снижает нагрузку на систему и делает обработку предсказуемой.

#### Схема работы Worker Pool:
Источники задач ->
ОЧЕРЕДЬ ЗАДАЧ (jobs) (Источники задач кладут их в канал): [ 1, 2, 3, 4, 5, 6 ... ] (Канал jobs — это очередь. Задачи ждут, пока их возьмёт свободный воркер.) -> берут задачи ->
ВОРКЕРЫ (worker goroutine) (Фиксированное количество рабочих):
- Worker 1 -> обрабатывает задачу
- Worker 2 -> обрабатывает задачу
- ...
- Worker N -> обрабатывает задачу
(Воркеры постоянно берут задачи из jobs, обрабатывают их и отправляют результат в results.) -> кладут результат ->
ОЧЕРЕДЬ РЕЗУЛЬТАТОВ (results) (Результаты обрабатываются дальше): [ 101, 102, 103, 104, 105, 106 ... ] (Канал results — это очередь готовых результатов для дальнейшей обработки.) ->
Потребители результатов

#### Зачем это нужно?
- Контроль конкуренции — ограничиваем число одновременно работающих goroutine.
- Экономия ресурсов — меньше памяти и переключений контекста.
- Стабильность — система не «падает» от наплыва задач.
- Повышение пропускной способности — воркеры заняты работой, а не ожиданием.

#### Где применяется:
- Обработка HTTP запросов
- Парсинг файлов и данных
- Отправка писем и уведомлений
- Обработка изображений
- Фоновая обработка

#### Пример кода (упрощённо)
```go
jobs := make(chan int, 100)    // очередь задач
results := make(chan int, 100) // очередь результатов

const workerCount = 5          // количество воркеров

// Запускаем воркеров
for i := 1; i <= workerCount; i++ {
    go func(id int) {
        for job := range jobs { // берём задачу из очереди
            result := job * 2   // обрабатываем
            results <- result   // кладём результат в очередь
            fmt.Printf("Worker %d обработал %d\n", id, job)
        }
    }(i)
}

// Отправляем задачи
for i := 1; i <= 10; i++ {
    jobs <- i
}
close(jobs) // больше задач нет

// Читаем результаты
for res := range results {
    fmt.Println("Результат:", res)
}
```

#### Как это работает:
1. Источники кладут задачи в канал jobs.
2. Воркеры берут задачи из jobs.
3. Обрабатывают их параллельно.
4. Кладут результаты в канал results.
5. Потребители читают результаты.

Важно: количество воркеров подбирается под нагрузку и возможности вашего сервера.

если задач станет 10 000, ты создашь 10 000 goroutine. Иногда это нормально. Но в реальных сервисах так можно:

забить CPU
съесть память
положить базу
упереться в лимиты API
перегрузить систему
Поэтому в Go часто используют worker pool, идея очень похожа на очередь работников:

есть очередь задач
есть фиксированное количество работников
каждый worker берёт следующую задачу
делает работу
идёт за следующей

задачи могут быть тысячами, но одновременно работают только, например, 5 или 10 goroutine.

есть channel с задачами (jobs)
есть несколько worker goroutine
workers читают задачи из канала
результаты складывают в другой channel

цель

Контролировать нагрузку и не создавать бесконечное количество goroutine

Fan-out и Fan-in

Fan-out — когда одна очередь задач распределяется на несколько goroutine. Fan-in — когда результаты из нескольких goroutine собираются обратно в один канал.

Это частый production-паттерн.

параллельно обработать список URL
сходить в несколько API
распарсить пачку файлов
собрать результаты обратно

### Fan-out / Fan-in в Go
Один поток задач делится на несколько параллельных обработчиков (fan-out), а затем результаты снова собираются в один поток (fan-in).
Идея: распараллеливаем работу для скорости, а затем объединяем результаты для дальнейшей обработки.

#### Схема Fan-out / Fan-in:
- ИСТОЧНИК ЗАДАЧ (порождает задачи: Чтение файлов, запросы к API, сообщения из очереди и т.д.) ->
- jobs channel: [ 1, 2, 3, 4, 5, 6, 7, 8 ... ] (Один канал с задачами. В него помещаются задания (jobs).) ->
- FAN-OUT (задачи обрабатываются несколькими goroutine):
  - Worker 1 -> обрабатывает задачу
  - Worker 2 -> обрабатывает задачу
  - Worker 3 -> обрабатывает задачу
  - ...
  - Worker N -> обрабатывает задачу
  (Несколько воркеров читают из jobs параллельно и кладут результаты в results.) ->
- FAN-IN (результаты собираются в один поток):
  - results channel: [ 101, 102, 103, 104, 105, 106, 107, 108 ... ] (Все результаты попадают в один канал. Порядок может отличаться от порядка входящих задач — это нормально.) ->
- ПОТРЕБИТЕЛЬ (получает результаты: Запись в БД, ответ клиенту, агрегация, логирование и т.д.)

#### Зачем это нужно?
- Параллелизм — несколько воркеров обрабатывают задачи одновременно.
- Масштабируемость — легко изменить количество воркеров.
- Эффективное использование ресурсов — нет простоя, пока один воркер занят.
- Универсальность — подходит для I/O-операций, CPU-задач и смешанных нагрузок.

#### Где применяется?
- Обработка HTTP-запросов
- Скачивание файлов
- Отправка email / уведомлений
- Парсинг данных
- Пакетная обработка и агрегация

#### Пример кода (упрощённо)
```go
jobs := make(chan int)
results := make(chan int)
workerCount := 4

// Воркеры
for i := 0; i < workerCount; i++ {
    go func(id int) {
        for job := range jobs { // читаем задачи
            // ...обработка задачи...
            result := job * 2 // допустим, результат
            results <- result // отправляем в results
            fmt.Printf("Worker %d обработал %d\n", id, job)
        }
    }(i)
}

// Генератор задач
go func() {
    for i := 1; i <= 8; i++ {
        jobs <- i
    }
    close(jobs) // сигнал: задач больше нет
}()

// Закрываем results, когда все воркеры закончат
go func() {
    // ждём завершения всех воркеров
    // (в реальном коде используем sync.WaitGroup)
    // ...
    close(results)
}()

// Читаем результаты
for res := range results {
    fmt.Println("Результат:", res)
}
```

#### Важно:
- Порядок результатов может отличаться от порядка задач.
- Для ожидания всех воркеров на практике используйте sync.WaitGroup.
- Количество воркеров подбирайте под тип нагрузки и возможности системы.

Context и отмена операций через channels

### Context и отмена goroutine в Go
Context (ctx) — это встроенный механизм для управления жизненным циклом операций. Когда мы вызываем cancel(), все goroutine, которые слушают ctx.Done(), получают сигнал об отмене и могут корректно завершить работу.
Идея: Один источник отмены (cancel) -> все зависимости получают сигнал -> освобождаем ресурсы и выходим без утечек.

#### Как это работает
Схема распространения отмены:
- Родительская goroutine:
```go
ctx, cancel := context.WithCancel(...)
...
cancel()
```
  -> вызываем cancel() (X) ->
- ctx.Done() (канал закрывается):
  - До отмены: открыт (чтение блокируется)
  - После cancel(): канал закрывается
  - Чтение из закрытого канала происходит сразу и возвращает zero-value
- Дочерние воркеры одновременно получают сигнал из ctx.Done():
  - Worker 1: select { case <-ctx.Done(): // завершаемся return ... } -> goroutine завершена
  - Worker 2: select { case <-ctx.Done(): // завершаемся return ... } -> goroutine завершена
  - ...
  - Worker N: select { case <-ctx.Done(): // завершаемся return ... } -> goroutine завершена

#### Пример: отменяем работу группы goroutine
```go
func main() {
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel()

    for i := 1; i <= 3; i++ {
        go worker(ctx, i)
    }

    time.Sleep(2 * time.Second) // имитируем работу
    cancel() // отправляем сигнал отмены
    time.Sleep(500 * time.Millisecond) // даём время завершиться
}

func worker(ctx context.Context, id int) {
    fmt.Printf("Worker %d: старт\n", id)
    ticker := time.NewTicker(500 * time.Millisecond)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            fmt.Printf("Worker %d: отмена, выхожу\n", id)
            return
        case t := <-ticker.C:
            fmt.Printf("Worker %d: тики %v\n", id, t)
        }
    }
}
```

#### Что важно помнить
- ctx.Done() используем в select как ещё один канал.
- Отмена должна быть явной: cancel() вызываем в нужный момент.
- Всегда делаем defer cancel(), чтобы не забыть освободить ресурсы.
- Если goroutine не слушает ctx.Done(), она не узнает об отмене.
- Context не отменяет работу автоматически, он лишь сообщает.

#### Зачем это нужно
- Предотвращает утечки goroutine
- Позволяет останавливать долгие операции
- Упрощает управление сложными цепочками зависимостей
- Освобождает ресурсы (соединения, файлы, таймеры и т.д.)

#### Частые случаи применения
- HTTP-запросы (r.Context())
- Работа с БД и внешними сервисами
- Пайплайны (pipeline) и воркер-пулы
- Таймауты (context.WithTimeout / WithDeadline)

Правильная отмена через context — один из главных навыков при работе с конкурентностью в Go.

timeout уже истёк

Если goroutine продолжат ждать данные из channel или пытаться туда писать, они могут зависнуть навсегда. Так появляются goroutine leak и зависшие worker.

Для решения этой проблемы в Go используют context.Context.

context сам ничего не останавливает. Он только отправляет сигнал отмены. А goroutine уже сама должна:

получить этот сигнал
прекратить работу
выйти из цикла
освободить ресурсы

context используется вместе с select, потому что ctx.Done() — это тоже channel. Когда context отменяется, канал Done() закрывается и select может это поймать.

```go
func worker(ctx context.Context, jobs <-chan int) {
for {
select {
case <-ctx.Done():
fmt.Println("worker stopped")
return
case job := <-jobs:
fmt.Println("process", job)
}
}
}
```

worker ждёт либо новую задачу
либо сигнал отмены
как только context отменяется — goroutine завершается

Создание context:
```go
ctx, cancel := context.WithCancel(context.Background())
defer cancel()
```

Также часто используют:
```go
context.WithTimeout()
context.WithDeadline()
```

### Goroutine leak: утечки из-за каналов
Утечка goroutine — это когда горутина продолжает ждать на операции с каналом, но она уже никогда не завершится. Такая горутина остаётся в памяти и со временем их становится всё больше -> растёт потребление памяти и нагрузка на планировщик.
Главная идея: каждая операция с каналом (отправка, получение, range) может заблокировать goroutine. Если нет того, кто выполнит парную операцию — goroutine «зависает» навсегда.

#### Частые сценарии утечек

- 1. Отправка без читателя
  Горутина пытается отправить данные в канал, но никто их не читает.
  Схема: Goroutine (отправитель: ch <- data) -> ch (unbuffered) -> Читателя нет -> Заблокирована навсегда
  Пример:
```go
ch := make(chan int)

go func() {
    ch <- 1 // заблокируется навсегда
}()

// main ничего из ch не читает
```

- 2. Получение без отправителя (и без закрытия)
  Горутина ждёт данные из канала, но их больше никто не отправит и канал не закроют.
  Схема: Отправителя больше нет -> ch (unbuffered) -> Goroutine (получатель: data := <-ch) -> Заблокирована навсегда
  Пример:
```go
ch := make(chan int)

go func() {
    v := <-ch // заблокируется навсегда
    fmt.Println(v)
}()

// никто не отправляет и канал не закрыт
```

- 3. Range по каналу, который не закрывают
  Range завершится только когда канал будет закрыт. Если забыть закрыть — горутина будет ждать.
  Схема: Продюсер завершил работу -> ch (unbuffered) -> Goroutine (range: for v := range ch { }) -> Заблокирована навсегда
  Пример:
```go
ch := make(chan int)

go func() {
```

- runtime.NumGoroutine(): отслеживаем рост числа горутин во время работы.
- Нагрузочные тесты: запускаем сценарии повторно и смотрим, не растёт ли память.

```bash

```

Если число goroutine растёт и не возвращается к исходному — у вас утечка.

- Всегда закрывайте канал, если он больше не нужен (со стороны отправителя).
- Используйте контекст (context.Context) для отмены долгих операций.
- Добавляйте select с ctx.Done() для всех блокирующих операций.
- Документируйте, кто закрывает канал и когда.
- Тестируйте: проверяйте, что число goroutine не увеличивается после сценариев.


#### Типичные ошибки
- X Забыли читать из канала — Отправитель блокируется на ch <- v.
- X Забыли отправлять в канал — Получатель блокируется на <-ch.
- X Забыли закрыть канал при range — Горутина остаётся в цикле forever.
- X Закрыли канал со стороны получателя — Приводит к panic: close of closed channel или race при нескольких отправителях.
- X Используют буфер как «лекарство от всего» — Буфер только отсрочит проблему, но не решит её.
- X Не учитывают отмену (context) — Горутина продолжает ждать даже когда запрос клиента уже отменён.

#### Почему это важно
- Рост памяти: каждая утечка — это память, которая никогда не освободится.
- Снижение производительности: планировщику сложнее управлять тысячами лишних goroutine.
- Деградация сервиса: в худшем случае — падение по OOM.
- Дорого в проде: утечки сложно найти и дорого чинить.

### Правила поведения channels в Go
Эти правила основаны на спецификации языка и помогают предсказать, что произойдёт в любой ситуации. Зная их, вы избегаете deadlock, panic и странных зависаний.
Зачем это знать? Поведение каналов на этих четырёх ситуациях — фундамент работы конкурентных программ. Большинство багов связано с их незнанием.

#### 1. nil channel — блокирует навсегда
Чтение и запись в nil-канал блокируются. Такая операция никогда не продолжится.
Схема:
- чтение <-ch -> X -> ch (nil)
- запись ch <- 1 -> X -> ch (nil)

```go
var ch chan int // ch == nil

func main() {
    ch := (chan int)(nil)

    <-ch      // блокируется навсегда
    ch <- 1   // тоже блокируется навсегда
}
```
Зачем это может быть полезно? Иногда nil используют, чтобы «выключить» канал в select.

#### 2. closed channel — можно читать, но нельзя писать
Чтение из закрытого канала не блокируется и всегда сразу возвращает значение (zero value) и ok = false. Запись в закрытый канал вызывает panic.
Схема:
- чтение <-ch -> без блокировки (v, ok) -> ch (closed)
- запись ch <- 1 -> X -> ch (closed) -> panic!

```go
ch := make(chan int, 2)
ch <- 1
ch <- 2
close(ch)

v, ok := <-ch   // v = 1, ok = true
v, ok = <-ch    // v = 2, ok = true
v, ok = <-ch    // v = 0, ok = false — канал пуст

ch <- 3         // panic: send on closed channel
```

#### 3. запись в закрытый канал — panic
Отправка данных в закрытый канал — это ошибка времени выполнения.
Схема: запись ch <- 42 -> X -> ch (closed) -> panic!

```go
ch := make(chan int)
close(ch)

ch <- 42 // panic: send on closed channel
```
Почему так? После close никто не может гарантировать, что есть читатели. Чтобы не потерять данные и не нарушить логику программы, Go предпочитает упасть явно.

#### 4. безопасное чтение после close
Чтение из закрытого канала всегда безопасно и не блокируется. Если данных нет — вернётся zero value и ok = false.
Схема: чтение <-ch -> ch (closed) -> всегда безопасно (v, ok)

```go
ch := make(chan string, 1)
ch <- "hello"
close(ch)

for {
    v, ok := <-ch
    if !ok {
        fmt.Println("канал закрыт и пуст")
        break
    }
    fmt.Println("получено:", v)
}
```
Это позволяет удобно завершать циклы и обрабатывать оставшиеся данные.

#### Быстрая шпаргалка
- Чтение из nil -> блокируется навсегда
- Запись в nil -> блокируется навсегда
- Чтение из закрытого -> не блокируется, (zero value, false)
- Запись в закрытый -> panic

#### Практический совет
- Закрывайте канал только в том месте, где вы — единственный отправитель.
- Читайте из канала до тех пор, пока ok == true.
- Используйте select с ctx.Done(), чтобы не зависать на каналах.
- Следите, чтобы у каждой отправки был читающий получатель (и наоборот).

#### Пример с select и close
```go
for {
    select {
    case v, ok := <-ch:
        if !ok {
            fmt.Println("канал закрыт")
            return
        }
        fmt.Println("значение:", v)
    case <-ctx.Done():
        fmt.Println("отмена!")
        return
    }
}
```
- <-ch вернёт ok=false, когда канал закрыт и пуст.
- ctx.Done() — ещё один канал, который сообщает об отмене.

  Блокируется, если:
  - канал небуферизованный и нет отправителя;

Схема: send -> cap = 3 [ индекс 0: 10, индекс 1: 20, индекс 2: 30 ] -> receive
- Отправка блокируется, когда буфер заполнен.
- Получение блокируется, когда буфер пуст.

#### 8. CONTEXT И ОТМЕНА GOROUTINE
Context позволяет передавать сигнал отмены всем goroutine. ctx.Done() — это канал, который закрывается при отмене.
Схема: cancel() -> ctx.Done() (канал закрывается при cancel()) -> worker 1 (завершена), worker 2 (завершена) ... worker N (завершена)

```go
ctx, cancel := context.WithCancel(context.Background())
defer cancel() // важно: освобождаем ресурсы

// в goroutine
select {
case v := <-ch:
    // получаем данные
case <-ctx.Done():
    // отмена
    return
}
```

Правильно:
- передавайте контекст во все goroutine;
- проверяйте <-ctx.Done() в select;
- всегда вызывайте cancel().

Зачем это нужно:
- Предотвращает утечки
- Освобождает ресурсы
- Переослать отмену

#### 9. КАК НЕ ДОПУСТИТЬ УТЕЧЕК (GOROUTINE LEAK)
- У каждой goroutine должен быть способ завершения (через close, context, done-канал).
- Не оставляйте отправку без получателя.
- Не оставляйте получение без отправителя.
- Закрывайте каналы, по которым больше не будут отправлять.
- Используйте select с ctx.Done() в длительных операциях.
- Следите за числом goroutine: runtime.NumGoroutine().

```go
import "runtime"
fmt.Println("goroutines:", runtime.NumGoroutine())
```

#### 10. ТИПИЧНЫЕ ОШИБКИ (Ошибка — Что происходит — Как сделать правильно)
- X Чтение из nil-канала — Блокировка навсегда — Инициализируйте канал: make(chan T)
- X Отправка в nil-канал — Блокировка навсегда — Инициализируйте канал
- X Отправка в закрытый канал — Panic — Закрывайте только со стороны отправителя и только один раз
- X Закрытие канала со стороны получателя — Panic (если есть отправители) — Закрывает только отправитель
- X Двойное закрытие канала — Panic — Закрывайте канал ровно один раз
- X Забыли закрыть канал с range — Блокировка навсегда — Закройте канал, чтобы цикл завершился
- X Игнорирование ok при чтении — Потеря сигнала о закрытии, ошибки в логике — Используйте v, ok := <-ch
- X Отсутствие отмены (context) — Утечки goroutine — Используйте context + cancel()
- X Забыли defer cancel() — Утечки ресурсов — Всегда defer cancel() после создания context
- X Нет буфера и медленный получатель — Частые блокировки отправителя — Используйте буфер или увеличьте скорость обработки

Что такое channel в Go?
Channel в Go — это типизированный механизм связи между goroutine. Через channel одна goroutine может отправить значение, а другая получить его.

Чем buffered channel отличается от unbuffered channel?
Unbuffered channel блокирует отправителя, пока получатель не заберёт значение. Buffered channel имеет буфер и позволяет временно хранить несколько значений без немедленного чтения.

Почему возникает deadlock при работе с channels?
Deadlock возникает, когда goroutine ждёт операцию с channel, которая уже никогда не произойдёт. Например, отправка есть, а получателя нет, или чтение есть, а отправителя нет.

Кто должен закрывать channel в Go?
Обычно channel закрывает отправитель, потому что именно он знает, что новых данных больше не будет. Receiver чаще всего только читает данные.

Что будет при чтении из закрытого channel?
Чтение из закрытого channel безопасно. Сначала можно дочитать оставшиеся значения, затем канал начнёт возвращать zero value и ok = false.

Что будет при записи в закрытый channel?
Запись в закрытый channel вызывает panic: send on closed channel.

Зачем нужен select в Go?
select позволяет ждать несколько операций с channels одновременно. Его используют для timeout, cancellation, чтения из нескольких каналов, fan-in, worker pool и graceful shutdown.

Что такое nil channel?
Nil channel — это channel, который не был создан через make. Чтение и запись в nil channel блокируются навсегда.

Что такое goroutine leak при работе с channels?
Goroutine leak возникает, когда goroutine зависает на операции с channel и больше не может завершиться. Например, она ждёт данные из channel, в который никто уже не отправит значение.

Когда использовать channel, а когда mutex?
Channel удобен для передачи данных и координации goroutine. Mutex лучше подходит для защиты общей памяти, когда нескольким goroutine нужен безопасный доступ к одной структуре данных.
