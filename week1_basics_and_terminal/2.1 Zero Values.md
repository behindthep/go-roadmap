Zero value - значение по умолчанию, которое получает переменная, если ты её объявил, но не инициализировал.
В Go не бывает неинициализированных переменных. Язык гарантирует, что у каждой переменной будет валидное, предсказуемое, безопасное, стартовое значение, это часть дизайна языка, а не случайная фича.
Во многих языках переменная без инициализации, потенциальная проблема: мусор из памяти, null, undefined, сюрприз в рантайме.

- Числа             - int / int64 / float64 - 0
- string                                    - ""
- bool                                      - false
- Указатели pointer - *User                 - nil
- slice             - []int                 - nil
- map[string]int                            - nil
- Каналы            - chan int              - nil
- func()                                    - nil
- interface         - error / io.Reader     - nil
- struct{}                                  - все поля получают свой zero values

### Nil slice vs nil map: одна из самых частых реальных ловушек, из-за которой падают сервисы.

И slice, и map в Go имеют zero value nil. Но ведут себя они по-разному.

#### Nil slice - безопасен

```go
func main() {
	var s []int

	fmt.Println(len(s)) // 0
	fmt.Println(cap(s)) // 0

	s = append(s, 1) // сработает
	fmt.Println(s) // [1]
}
```

- range по nil slice не упадёт (0 итераций)
- чтение/запись элементов - ок через append. append возвращает новый slice header, и Go сам может выделить память под элементы.

#### Nil map - читать можно, писать нельзя

Код с nil map компилируется, ошибка вылезет уже в рантайме.

```go
func main() {
	var m map[string]int

    fmt.Println(len(m)) // 0

    fmt.Println(m["key"]) // 0
    m["key"] = 1 // panic: assignment to entry in nil map
}
```

- чтение работает (верёнт zero value)
- range сработает (0 итераций)
- писать в в nil map нельзя, будет panic. Карта должна быть явно инициализирована.
Запись требует внутренней структуры хеш-таблицы, у nil map её просто нет.

```go
m := make(map[string]int)
m["key"] = 1
```

#### Nil slice и empty slice - не всегда одно и то же

```go
var s1 []int
s2 := []int{}

s1 == nil -> true
s2 == nil -> false
```

Важно при JSON-маршалинге:
- nil slice часто превращается в null
- пустой slice превращается в []

Если ты пишешь API, тесты - это может быть критично.

### Zero Values в Структурах

Когда ты создаёшь структуру в Go, все её поля автоматически получают zero values своих типов.

```go
Type User struct {
    Name string
    Age int
    Active bool
}

func main() {
	var u User
	fmt.Printf("%+v\n", u)
}

{Name: Age:0 Active:false}
```

Не заполнять вручную, если тебе подходит состояние по умолчанию.

#### Не все поля безопасны.
Если в структуре есть map, slice, chan или что-то, где для работы нужна инициализация, zero value может быть формально валидным, но практически неудобным или опасным. Если внутри map, а ты собираешься туда писать, нужен конструктор или явная инициализация.

```go
type Cache struct {
	items map[string]string
}

var c Cache
c.items["key"] = "value"
// panic, map внутри структуры = nil.
```

### Вопрос необходимости конструктора (NewXxx)
- Не используй NewXxx, если:
* zero value структуры рабочий
* конструктор не добавляет реальной пользы

- Используй NewXxx, если:
* zero value невалиден, опасен или требует обязательной инициализации внутренних полей
* внутри есть map, в которую нужно писать
* внутри есть chan, который должен работать сразу
* у типа есть обязательные зависимости

##### Нужен (zero value нерабочий)
```go
type Item struct {
	Value string
}

type Cache struct {
    items map[string]Item // nil
}

func NewCache() *Cache {
    return &Cache{
        items: make(map[string]Item),
    }
}
```

Без NewCache() - запись = panic. NewCache() нужен, иначе поле items будет nil, и запись в карту вызовет panic.

##### Не нужен (zero value рабочий)
```go
type Counter struct {
    count int // count по умолчанию = 0, с ним уже можно работать.
}
func (c *Counter) inc() {
    c.count++
}
```

Готов к работе сразу после объявления.

### Один из паттернов, это типы, у которых zero value рабочий и их можно использовать сразу после объявления.
Не нужно тратить время на лишнюю инициализацию, вызывать конструктор, писать New. Примеры из стандартной библиотеки:

- sync.Mutex{}
- bytes.Buffer{}
- strings.Builder{}
- sync.WaitGroup{}
- sync.Once{}

```go
import (
	"bytes"
	"fmt"
	"sync"
)

func main() {
	var mu sync.Mutex
	mu.Lock()
	mu.Unlock()

	var buf bytes.Buffer
	buf.WriteString("hello")

	fmt.Println(buf.String()) // hello
}
```

Нет ни New, ни make.

### Проектирование собственного типа
Если ты проектируешь свой тип, задавать себе вопрос: что будет, если кто-то напишет var x MyType и сразу начнёт им пользоваться?
- Если ответ нормальный, значит тип спроектирован удачно.
- Если ответ: "ну тут надо не забыть ещё вызвать инициализацию, иначе всё развалится", интерфейс у типа уже не дружелюбный.

### Nil channel блокирует выполнение
Zero value для канала - nil.

var ch chan int
Такой канал нельзя использовать для отправки и получения. Операции с ним будут блокироваться.

ch <- 1   // блокировка
<-ch      // блокировка

Чтобы канал работал, нужен make:
```go
ch = make(chan int)
```

#### Ожидание, что nil channel будет работать
```go
var ch chan int
ch <- 1 // зависание
```
Исправление:
```go
ch := make(chan int)
ch <- 1
```

### Nil interface и typed nil - не одно и то же
Интерфейс в Go считается nil только когда у него нет ни типа, ни значения.

```go
var err error
fmt.Println(err == nil) // true
```

так уже нет:
```go
var p *MyError = nil
var err error = p

fmt.Println(err == nil) // false
```

Внутри интерфейса уже лежит тип *MyError, даже если само значение nil.
Эта штука часто кусает в обработке ошибок.

### Хороший вопрос при проектировании своих типов
Принцип:
Если можно сделать, чтобы zero value был полезен, делай так.

- Удобное проектирование API. Хороший Go-код часто можно использовать сразу, без лишних действий.
- меньше шансов забыть инициализацию
- Меньше бойлерплейта. Не надо везде городить конструкторы и ручную инициализацию.
- API выглядит чище и понятнее. Читаемость. Когда zero value рабочий, код становится проще для всех, кто будет его поддерживать.

Вопрос, который держать в голове при проектировании своих типов, структур и пакетов:
Что произойдёт, если другой разработчик создаст мой тип через var x MyType и сразу начнёт использовать?
- если всё работает нормально, значит дизайн удачный
- если код падает, требует обязательного Init() или скрытых условий, значит тип неудобный
