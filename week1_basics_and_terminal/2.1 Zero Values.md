Zero value - значение по умолчанию, которое получает переменная, если её объявить без инициализации.
В Go не бывает неинициализированных переменных. У переменной будет предсказуемое, стартовое значение.
Во многих языках переменная без инициализации, потенциальная проблема: мусор из памяти, null, undefined, сюрприз в рантайме.

- Числа             - int / int64 / float64 - 0
- string                                    - ""
- bool                                      - false
- Указатели pointer - *User                 - nil
- slice                                     - nil
- map                                       - nil
- Каналы            - chan int              - nil
- func()                                    - nil
- interface         - error / io.Reader     - nil
- struct{}                                  - все поля получают свой zero values

### Nil slice vs nil map

* Nil slice - безопасен

```go
func main() {
	var s []int

	fmt.Println(len(s), cap(s)) // 0 0

	s = append(s, 1) // сработает
	fmt.Println(s) // [1]
}
```

- range по nil slice не упадёт (0 итераций)
- чтение/запись элементов - ок через append. append возвращает новый slice header, и Go сам может выделить память под элементы.

* Nil map - читать можно, писать нельзя

Код с nil map компилируется, ошибка вылезет уже в рантайме.

```go
func main() {
	var m map[string]int

    fmt.Println(len(m)) // 0

    fmt.Println(m["key"]) // 0
	// m := make(map[string]int)
    m["key"] = 1 // panic: assignment to entry in nil map
}
```

- чтение работает (верёнт zero value)
- range сработает (0 итераций)
- писать в в nil map нельзя, будет panic. Карта должна быть явно инициализирована. Запись требует внутренней структуры Хеш-таблицы, у nil map её просто нет.

#### Nil slice и empty slice - не всегда одно и то же

```go
var s1 []int  // nil slice превращается в null
s2 := []int{} // Пустой slice превращается в []

s1 == nil -> true
s2 == nil -> false
```

Если ты пишешь API, тесты - это может быть критично. Важно при JSON-маршалинге.

### Zero Values в Структурах

При создании структуры её поля получают zero values типов. Не заполнять вручную, если тебе подходит состояние по умолчанию.

```go
Type User struct {
    Name string
    Age int
    Active bool
}

func main() {
	var u User
	fmt.Printf("%+v\n", u) // {Name: Age:0 Active:false}
}
```

#### Не все поля безопасны.
Если в структуре есть map, slice, chan или что-то, где для работы нужна инициализация, даже если zero value может быть валидным, но неудобным или опасным. 
Если внутри map и собираешься туда писать, нужен конструктор или явная инициализация.

```go
type Cache struct {
	items map[string]string
}

var c Cache
c.items["key"] = "value" // panic, map внутри структуры = nil.
```

### Необходимость конструктора (NewXxx)

##### Да NewXxx:
* zero value невалиден, опасен или требует обязательной инициализации внутренних полей
* внутри есть map, в которую нужно писать
* внутри есть chan, который должен работать сразу
* у типа есть обязательные зависимости

```go
type Item struct {
	Value string
}

type Cache struct {
    items map[string]Item // nil
}

func NewCache() *Cache {
    return &Cache{
        items: make(map[string]Item),
    }
}
```

NewCache() нужен, иначе поле items будет nil, и запись в карту вызовет panic.

##### Нет NewXxx:
* С zero value структуры можно работать сразу после объявления
* конструктор не даёт пользы

```go
type Counter struct {
    count int // 0
}
func (c *Counter) inc() {
    c.count++
}
```

### Паттерн: типы, у которых zero value рабочий и их можно использовать сразу после объявления.
Не тратить время на лишнюю инициализацию (make), вызывать конструктор, писать New. 

Примеры из стандартной библиотеки:
- sync.Mutex{}
- bytes.Buffer{}
- strings.Builder{}
- sync.WaitGroup{}
- sync.Once{}

```go
import (
	"bytes"
	"fmt"
	"sync"
)

func main() {
	var mu sync.Mutex
	mu.Lock()
	mu.Unlock()

	var buf bytes.Buffer
	buf.WriteString("hello")

	fmt.Println(buf.String()) // hello
}
```

### Проектирование собственных типов, структур и пакетов
Если проектируешь свой тип, задавать себе вопрос: 
Что будет, если кто-то создаст мой тип var x MyType и сразу начнёт им пользоваться?
Если всё работает нормальный - тип спроектирован удачно. Если ответ: "ну тут надо не забыть ещё вызвать инициализацию, иначе всё развалится", если код падает, требует обязательного Init() или скрытых условий, интерфейс у типа не дружелюбный.

Если можно сделать, чтобы zero value был полезен, делай так.

- Удобное проектирование API. Хороший Go-код часто можно использовать сразу, без лишних действий.
- Меньше шансов забыть инициализацию.
- Меньше бойлерплейта. Не надо везде городить конструкторы и ручную инициализацию.
- API выглядит чище и понятнее. Читаемость. Когда zero value рабочий, код становится проще для всех, кто будет его поддерживать.

### Nil channel блокирует выполнение
Такой канал нельзя использовать для отправки и получения. Операции с ним будут блокироваться.

```go
var ch chan int
ch <- 1   // блокировка
<-ch      // блокировка

ch = make(chan int)
ch <- 1
```

### Nil interface и typed nil - не одно и то же
Интерфейс = nil только когда у него нет ни типа, ни значения.

```go
var err error
fmt.Println(err == nil) // true

var p *MyError = nil
var err error = p
fmt.Println(err == nil) // false
```

Внутри интерфейса уже лежит тип *MyError, даже если само значение nil.
Эта часто кусает в обработке ошибок.
