Garbage Collector: почему твой сервис ест CPU

В Go сборщик мусора работает из коробки почти всегда, но для написания эффективного кода важно понимать его внутреннюю механику.

### ЧТО ТАКОЕ GARBAGE COLLECTOR
Каждый раз когда ты создаёшь переменную, структуру или слайс — Go выделяет память. Но память не бесконечная. Кто-то должен её освобождать.

#### В C:
ты делаешь это руками — malloc/free.
Забыл free — утечка. Сделал free дважды — краш.

#### В GO:
за это отвечает Garbage Collector.
Он автоматически находит объекты, которые больше никому не нужны, и освобождает память.
Тебе не нужно думать об этом в 95% случаев.

Но чтобы писать быстрый код — нужно понимать, как GC работает под капотом.

#### Схема: Garbage Collector в Go
GC находит и удаляет мусор (Автоматическое управление памятью):
- Ячейки памяти: [ используется ] [ используется ] [ мусор ] [ мусор ]
- Ячейки памяти: [ мусор ] [ мусор ] [ используется ] [ мусор ]

### TRI-COLOR MARKING: КАК GC НАХОДИТ МУСОР
Go использует алгоритм tri-color marking — трёхцветная маркировка.
Каждый объект в памяти получает один из трёх цветов:

- Белый — GC ещё не видел этот объект. Если после обхода остался белым — это мусор, можно удалять.
- Серый — GC нашёл объект, но ещё не проверил, на что он ссылается.
- Чёрный — GC проверил объект и все его ссылки. Он точно нужен.

#### Схема Tri-color marking:
- ЭТАП 1. СТАРТ: root (светлый) -> все 6 объектов в памяти белые (не проверен).
- ЭТАП 2. ОБХОД: root (чёрный) -> верхний ряд объектов (3 узла) серые (в очереди), нижний ряд объектов (3 узла) белые (не проверен).
- ЭТАП 3. РЕЗУЛЬТАТ: root (чёрный) -> верхний ряд объектов (3 узла) чёрные (нужен), нижний ряд объектов (3 узла) белые с отметкой X (мусор на удаление).
- Легенда: белый — не проверен, серый — в очереди, чёрный — нужен.

GC начинает с корневых объектов (стек, глобальные переменные) и красит их в серый. Потом берёт серые, проверяет их ссылки, красит в чёрный. И так пока серых не останется.
Всё что осталось белым — мусор.

### CONCURRENT GC: РАБОТАЕТ ПАРАЛЛЕЛЬНО С КОДОМ
Главная фишка GC в Go — он concurrent. Работает параллельно с твоим кодом, а не останавливает всё приложение.
Как это происходит:

1. Mark Setup — короткая пауза (STW). GC включает write barrier и готовится к обходу.
2. Marking — GC обходит объекты параллельно с горутинами. Это самая долгая фаза, но приложение работает.
3. Mark Termination — ещё одна короткая пауза (STW). GC заканчивает маркировку.
4. Sweeping — освобождение белых объектов. Происходит в фоне, без пауз.

STW-паузы в Go обычно меньше 1 мс. Даже под нагрузкой.

### ЧТО ЗАСТАВЛЯЕТ GC РАБОТАТЬ ЧАЩЕ
GC запускается когда heap вырастает в 2 раза от предыдущего размера после сборки. Это контролирует переменная GOGC (по умолчанию 100 — значит рост на 100%).
Что создаёт нагрузку на GC:

1. Частые аллокации — каждый new, make, замыкание, интерфейс может выделять память в heap
2. Escape to heap — если компилятор не может доказать что переменная живёт только в функции, она уходит в heap
3. Много мелких объектов — карты со строковыми ключами, слайсы указателей, слайсы интерфейсов

Чем больше мусора ты создаёшь — тем чаще GC работает — тем больше CPU тратится не на твой код.

```go
// Плохо: аллокация в цикле - heap растёт
for i := 0; i < 1_000_000; i++ {
    user := &User{Name: "test"} // каждый раз новый объект в heap
    process(user)
}

// Лучше: переиспользовать объект
user := &User{}
for i := 0; i < 1_000_000; i++ {
    user.Name = "test"
    process(user)
}
```

### ОБЩАЯ КАРТИНА: GC В GO
Go GC — это concurrent, tri-color, mark-and-sweep сборщик. Он спроектирован для низких пауз, а не для максимальной пропускной способности.
Что важно помнить:

- GC работает параллельно с кодом, STW-паузы < 1 мс
- Чем меньше аллокаций — тем реже GC — тем быстрее код
- GOGC контролирует как часто запускается сборка (default 100)
- runtime.ReadMemStats() и GODEBUG=gctrace=1 — инструменты для диагностики
- Escape analysis (go build -gcflags='-m') показывает что уходит в heap

GC в Go не враг. Он отлично работает из коробки. Но если у тебя highload — понимание GC отличает middle от senior.

#### Схема: GC В GO — ОБЩАЯ КАРТИНА (Go Runtime)
- Heap -> (heap вырос × 2 -> запуск) -> GC -> (sweep -> освобождение) -> Heap
- Goroutines <-> (concurrent) <-> GC
- GOGC=100 -> управляет частотой запуска GC
- Stack / Globals -> (roots) -> GC
- Инструменты внизу схемы: GODEBUG=gctrace=1, go build -gcflags='-m'

🛠️ Garbage Collector в Go: как он работает и зачем он нужен?

❓ Что такое Garbage Collector (GC)?

Garbage Collector — это механизм автоматического управления памятью в Go. Он освобождает память, которая больше не используется программой, чтобы избежать утечек памяти.

💡 Зачем нужен Garbage Collector?

GC помогает:

1. Упростить управление памятью:
- Разработчикам не нужно вручную освобождать память.
2. Предотвратить утечки памяти:
- GC автоматически находит и освобождает неиспользуемые объекты.
3. Повысить безопасность:
- Исключаются ошибки, связанные с неправильным освобождением памяти.

⚠️ Как работает GC в Go?

GC в Go использует триколорный алгоритм маркировки и очистки:

1. Маркировка:
- GC проходит по всем объектам в памяти и помечает используемые.
2. Очистка:
- Все непомеченные объекты считаются мусором и удаляются.
3. Сжатие:
- Память может быть уплотнена для уменьшения фрагментации.

❗Минусы GC:

- Может вызывать паузы (stop-the-world) во время работы.
- Требует дополнительных ресурсов CPU и памяти.

🎯 Garbage Collector — это мощный инструмент для автоматического управления памятью в Go!
