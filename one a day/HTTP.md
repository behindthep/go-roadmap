HTTP - протокол, по которому общаются браузеры и серверы. Открываете сайт - браузер отправляет запрос, сервер отвечает - и страница загружается.
Механизм: "клиент спрашивает - сервер отвечает". Внутри него правила, заголовки, методы и структура, которая делает интернет стабильным.

HTTP = клиент <-> сервер
Клиент запрос -> Сервер ответ -> Клиент

### HTTP запрос состоит из 3 частей:
- Строка запроса (метод, путь, версия http)
GET /profile HTTP/1.1

- Заголовки
HOST: example.com
User-Agent: Chrome
Accept: text/html
Accept-Language: ru-RU

- Тело запроса (может быть пустым)
{ "name": "Maks" }

Запрос внутри всегда структурирован одинаково, сервер понимает, что хочет клиент.

### HTTP-ответ состоит из 3 частей:

- Статус
HTTP/1.1 200 OK
Статус: всё хорошо

- Заголовки
Content-Type: application/json
Content-Length: 123
Cache-Control: no-cache

- Тело ответа (данные для клиента)
{ "id": 1, "name": "Maks" }

Когда всё успешно - браузер показывает результат (страницу, данные, файл)

### Под капотом

Открываете сайт, происходит цепочка действий:
1) Клиент создаёт запрос
2) Запрос идёт через интернет до сервера
3) Сервер обрабатывает его
4) Формирует ответ
5) Отправляет назад клиенту
6) Клиент отображает результат

Это происходит за миллисекунды - сайты открываются быстро.

### Методы HTTP

HTTP использует методы, чтобы объяснить серверу, что нужно сделать:
- GET получить данные
- POST отправить данные
- PUT обновить данные
- DELETE удалить
- PATCH изменить часть данных

Эти команды - как глаголы в языке. Благодаря им сервер понимает намерение клиента.

📨 Структура HTTP запроса: анатомия веб-коммуникации
HTTP запрос — сообщение, которое клиент отправляет серверу. Каждый запрос содержит определенную структуру, которая позволяет серверу понять, что именно хочет клиент.

💡 Основные компоненты:
1. Стартовая строка:
     METHOD /path HTTP/version
      - METHOD: GET, POST, PUT, DELETE, etc.
   - path: URL-путь к ресурсу
   - version: HTTP/1.1 или HTTP/2
2. Заголовки (Headers):
     Host: www.example.com
   User-Agent: Mozilla/5.0
   Accept: text/html
   Content-Type: application/json
   Authorization: Bearer token123
3. Тело запроса (опционально):
     {
     "key": "value",
     "data": "content"
   }

- Заголовки отделяются от тела пустой строкой
- Каждый заголовок на новой строке
- Регистр методов имеет значение
- Content-Length должен соответствовать размеру тела

- Разные методы имеют разное предназначение
- Некоторые заголовки обязательны
- Тело запроса не используется в GET-запросах

Процентили — метрики, показывают, какой процент запросов выполняется быстрее определенного времени. 95-й процентиль означает, что 95% запросов выполнились быстрее указанного времени.

💡 Как использовать процентили в Go?
- Сбор метрик: Используйте библиотеки, такие как Prometheus, для сбора времени выполнения запросов.
- Анализ процентилей: Визуализируйте процентили в Grafana или других инструментах.
- Оптимизация: Используйте процентили для поиска узких мест и оптимизации производительности.

⚠️ Когда использовать процентили?
- Для анализа производительности API и HTTP-запросов.
- Когда важно понимать, как ведут себя "худшие" запросы (например, 99-й процентиль).

❗Минусы процентилей:
- Сложность интерпретации: Требуется опыт для анализа и понимания метрик.
- Накладные расходы: Сбор и анализ процентилей может увеличить нагрузку на систему.

### ЧТО ТАКОЕ ИДЕМПОТЕНТНОСТЬ

[ IDEMPOTENCY ] [ ПОЛЬЗА ]

Сценарий проблемы:
Пользователь нажал "Оплатить" и ничего не произошло -> Нажал ещё раз -> Нажал ещё раз -> Деньги списались три раза

Идемпотентность – это гарантия, что повторный запрос даёт тот же результат, что и первый. НАЖАЛ "ОПЛАТИТЬ" ПЯТЬ РАЗ – СПИСАНИЕ ОДНО.

- В распределённых системах запросы теряются, дублируются, ретраятся
- Клиент не знает, дошёл запрос или нет, и отправляет снова
- Сеть ненадёжна
- Если сервер не идемпотентен — данные ломаются

### КАКИЕ МЕТОДЫ ИДЕМПОТЕНТНЫ ПО ПРИРОДЕ

[ IDEMPOTENCY ] [ ПОЛЬЗА ]

#### НЕКОТОРЫЕ ОПЕРАЦИИ ИДЕМПОТЕНТНЫ САМИ ПО СЕБЕ:

- GET: читаем данные, ничего не меняем. Хоть 100 раз вызови, результат один
- PUT: заменяет ресурс целиком. PUT /users/42 {name: "Niyaz"} — сколько ни вызови, результат один и тот же
- DELETE: удаляет ресурс. Первый вызов удалит, повторные вернут 404. Состояние системы не меняется
- POST: НЕ идемпотентен. Каждый вызов создаёт новый ресурс или выполняет новое действие. Именно POST требует дополнительной защиты
- PATCH: зависит от реализации. balance += 100 — не идемпотентен. balance = 500 — идемпотентен

### IDEMPOTENCY KEY: КАК РЕАЛИЗОВАТЬ

[ IDEMPOTENCY ] [ ПОЛЬЗА ]

#### ОСНОВНОЙ ПРИЁМ:

клиент генерирует уникальный ключ (UUID) и отправляет его с каждым запросом в заголовке Idempotency-Key

#### СЕРВЕР ПРИ ПОЛУЧЕНИИ ЗАПРОСА:

1. Проверяет: есть ли этот ключ в хранилище?
   - Нет (шаг 2): выполняет операцию, сохраняет ключ и результат
   - Есть (шаг 3): возвращает сохранённый результат без повторного выполнения

Хранилище ключей: Redis с TTL (обычно 24-72 часа) или отдельная таблица в БД. Ключ должен жить достаточно долго, чтобы покрыть все ретраи.
ТАК РАБОТАЮТ STRIPE, PAYPAL И ДРУГИЕ ПЛАТЁЖНЫЕ API

```go
func (h *Handler) CreatePayment(w http.ResponseWriter, r *http.Request) {
	key := r.Header.Get("Idempotency-Key")

	// Уже выполняли?
	if result, ok := h.cache.Get(key); ok {
		json.NewEncoder(w).Encode(result)
		return
	}

	result := h.service.Pay(r.Context(), req)
	h.cache.Set(key, result, 24*time.Hour)
	json.NewEncoder(w).Encode(result)
}
```

### ДРУГИЕ СПОСОБЫ ОБЕСПЕЧИТЬ ИДЕМПОТЕНТНОСТЬ

[ IDEMPOTENCY ] [ ПОЛЬЗА ]

- УНИКАЛЬНЫЙ CONSTRAINT В БД:
  UNIQUE(order_id, operation)
  база не даст создать дубль. Дёшево и надёжно для простых случаев

- INSERT ... ON CONFLICT DO NOTHING:
  PostgreSQL выполнит вставку только если нет конфликта. Атомарно, без гонок

- CONDITIONAL UPDATE (ОПТИМИСТИЧНАЯ БЛОКИРОВКА):
  UPDATE ... WHERE version = 5
  обновление пройдёт только если версия совпадает. Повторный запрос с той же версией ничего не изменит

- ЕСТЕСТВЕННЫЙ ИДЕМПОТЕНТНЫЙ ДИЗАЙН:
  Вместо balance += 100 используй balance = 500
  Вместо "создай заказ" используй "создай заказ с ID=uuid". Проектируй операции так, чтобы повтор был безопасен

```go
// PostgreSQL: INSERT с защитой от дубля
_, err := db.ExecContext(ctx, `
	INSERT INTO payments (idempotency_key, amount, status)
	VALUES ($1, $2, 'success')
	ON CONFLICT (idempotency_key) DO NOTHING
`, key, amount)
```

### ОБЩАЯ КАРТИНА

[ IDEMPOTENCY ] [ ПОЛЬЗА ]

Идемпотентность — это не фича, это требование для любой системы, где есть сеть. Запросы дублируются всегда: ретраи клиента, таймауты, балансировщики, очереди сообщений.

#### ЧТО ЗАПОМНИТЬ:

- GET, PUT, DELETE идемпотентны по природе. POST — нет
- Idempotency Key (UUID от клиента) — стандартный способ защиты POST-запросов
- Храни ключи в Redis с TTL или в отдельной таблице
- ON CONFLICT DO NOTHING — простая защита на уровне БД
- Проектируй операции идемпотентными с самого начала: абсолютные значения вместо дельт, клиентские ID вместо серверных
