###  CAP–теорема: почему нельзя получить все и сразу

Принцип для понимания компромиссов в распределенных системах.

В распределённых система у тебя есть 3 свойства:
- Consistency (Согласованность): Все узлы видят одни и те же данные в одно и то же время.
- Availability (Доступность): Каждый запрос получает ответ, даже если некоторые узлы недоступны.
- Partition Tolerance (Устойчивость к разделению): Система продолжает работать, даже если связь/сеть между узлами нарушена.

CAP теорема (Consistency, Availability, Partition Tolerance) — принцип, утверждает, что в распределенных системах можно одновременно гарантировать только 2 из 3 свойств.

В распределенных системах невозможно одновременно обеспечить все 3 свойства.
  - CP: Системы, которые жертвуют доступностью ради согласованности (БД с сильной согласованностью).
  - AP: Системы, которые жертвуют согласованностью ради доступности (Cassandra).
  - CA: Системы, которые жертвуют устойчивостью к разделению (традиционные SQL-БД).

Учитывать CAP теорему при:
- При проектировании распределенных систем.
- При выборе БД или архитектуры системы.

Когда сеть между узлами рвётся (а она рвётся всегда), выбираешь: консистентность или доступность.

#### Partition Tolerance: выбора нет

Сетевые разрыва (partition) случаются всегда. Кабель перерезали, switch завис, даатцентр потерял связь. В реальной распределённой система отказаться от P невозможно.
Поэтому выбор на практике не "2 из 3", а "C или A при условии P":
- CA. Не бывает в распределённых системах.

- CP. Система консистента, но может не ответить пока узлы не синхронизируются.
- AP. Система всегда отвечает, но может вернуть устаревшие данные.

Нет систем, которые дают всё. Есть системы, которые честно говорят, что они жертвуют.

#### CP системы: сначала консистентность.

CP система гарантирует, что все узлы видят одинаковые данные. Если часть узлов недоступна, система откажет в запросе вместо возврата старых данных.
- PostgreSQL (single-master): запись только через мастер, реплики для чтения
- etcd: хранилище конфигов Kubernetes, Raf-консенсус
- ZooKeeper: координация распределённых систем
- MongoDB (with majority write concern): ждёт подтверждения от большинства узлов

Когда выбирать: финансы, инвентарть, всё где "продали один товар двум клиентам" недопустимо.

Node1 -- balance:100 -- Node2 -- partition -- Node3
Клиент шлёт запрос к Node 3 - получает отказ "503 unavailable".
Лучше не ответить, чем ответить неправильно.

#### AP системы: сначала доступность.

AP система всегда отвечает на запросы, даже если узлы потеряли связь между собой. Цена - разные узлы могут врмеменно показывать разные данные.
- Cassandra: каждый узел принимает запись, синхронизация потом
- DynamoDB: eventually consistent чтения по умолчанию
- Redis Cluster: при split-brain оба мастера принимают записи
- DNS: кешированные записи могут быть устаревшими

Когда выбирать: лента соцсети, счётчик лайков, кеш, логи, метрики. Где "показали старые данные на 5 секунд" никого не убьёт.

Node1 -- likes:142 -- Node2 -- likes:148 -- Node3 (данные отстают, но ответ есть)
Клиент шлёт запрос к Node 3 - получает ответ "200 OK, likes: 140"
Лучше ответить старыми данными, чем не ответить.


CAP не бинарный выбор на всю систему. Разные части приложания могут использовать разные стратегии.
- Баланс на счёте. CP. нельзя показать неправильную сумму.
- Лента уведомлений. AP. Задержка в 2 сек. никого не волнует.
- Корзина: добавление. AP. Не теряем действия пользователя.
- Корзина: оформление. CP. Не продаём то, чего нет.

Вопрос не "какую базу выбрать", а "что дороже: недоступность или неконсистентность?". Ответ разный для каждого use case внутри одного сервиса.
