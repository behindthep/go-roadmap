Fan–in / Fan–out: как ускорить код в 20 раз

Параллельная обработка — это то, за что любят Go, но именно здесь новички чаще всего ловят дедлоки и утечки памяти. Разбираемся, как правильно строить конвейеры данных.

### ЗАЧЕМ НУЖНЫ ЭТИ ПАТТЕРНЫ
У тебя есть задача, которая выполняется слишком долго. Например, 1000 HTTP-запросов по одному, это 10 минут. Параллельно, 30 секунд

#### FAN-OUT
это когда ты раздаёшь одну задачу нескольким горутинам.
Одна очередь задач, 10 воркеров разбирают её параллельно

#### FAN-IN
это когда ты собираешь результаты из нескольких горутин в один канал.
10 воркеров отвечают, ты читаешь всё из одного места

#### Схема Fan-out / Fan-in:
- раздать: задачи -> worker 1, worker 2, worker 3, worker 4
- собрать: worker 1, worker 2, worker 3, worker 4 -> результаты

Вместе они дают конвейер: раздал -> обработали параллельно -> собрал результаты

---

### FAN-OUT: РАЗДАЁМ РАБОТУ
Fan-out, это запуск нескольких горутин, которые читают задачи из одного канала. Каждая горутина берёт следующую свободную задачу и обрабатывает её
Канал работает как очередь: если один воркер занят, задачу возьмёт другой. Балансировка нагрузки из коробки, ничего не нужно писать руками

- Количество воркеров обычно фиксированное. Не запускай по горутине на каждую задачу, если задач миллион.
- 10–100 воркеров достаточно для большинства случаев

#### Схема распределения задач:
tasks channel -> (range tasks) -> worker 1, worker 2, worker 3, worker 4, worker 5

```go
tasks := make(chan Task)
// Запускаем 5 воркеров (fan-out)
for i := 0; i < 5; i++ {
    go func() {
        for task := range tasks {
            process(task)
        }
    }()
}
// Отправляем задачи в канал
for _, t := range allTasks {
    tasks <- t
}
close(tasks)
```

### FAN-IN: СОБИРАЕМ РЕЗУЛЬТАТЫ
Fan-in, это обратный процесс. Несколько горутин пишут результаты в один общий канал, а ты читаешь из него
Ключевой момент: когда закрывать канал результатов? Нужно дождаться пока все воркеры завершатся. Для этого используй sync.WaitGroup

WaitGroup считает активных воркеров. Каждый воркер при завершении вызывает Done. Когда счётчик дойдёт до нуля, отдельная горутина закрывает канал результатов

#### Схема сбора результатов:
worker 1, worker 2, worker 3, worker 4, worker 5 -> (sync.WaitGroup) -> results channel -> (range results) -> обработка
WaitGroup -> close(results) -> range завершается

```go
results := make(chan Result)
var wg sync.WaitGroup
// Fan-out: 5 воркеров пишут в results
for i := 0; i < 5; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for task := range tasks {
            results <- process(task)
        }
    }()
}
// Закрываем results когда все воркеры завершились
go func() {
    wg.Wait()
    close(results)
}()
// Fan-in: читаем все результаты из одного канала
for res := range results {
    save(res)
}
```

### ПОДВОДНЫЕ КАМНИ

- Горутина на каждую задачу:
  1 млн задач = 1 млн горутин. Каждая ест минимум 2 KB. Это 2 GB только на стеки. Используй пул воркеров фиксированного размера

- Забыл close(results):
  range по каналу будет ждать вечно. Горутина зависнет, память утечёт. Всегда закрывай канал после WaitGroup.Wait()

- Забыл wg.Add перед go func:
  Если вызвать wg.Add внутри горутины, возможна гонка: wg.Wait() завершится раньше чем все воркеры стартуют. Add всегда до go func

- Небуферизированный канал результатов:
  Если читатель медленнее воркеров, все воркеры встанут на записи в канал. Буфер помогает: make(chan Result, 100)

### ПОЛНАЯ КАРТИНА
Fan-out / Fan-in, это конвейер для параллельной обработки. Раздал задачи по воркерам, собрал результаты в один канал

#### Компоненты:
- Канал задач (tasks), входная очередь
- N воркеров (горутины), читают из tasks, пишут в results
- sync.WaitGroup, считает активных воркеров
- close(results), сигнал что все результаты собраны
- range results, читает пока канал не закрыт

Этот паттерн подходит для: HTTP-запросов, обработки файлов, запросов в БД, любой IO-bound работы. Для CPU-bound задач количество воркеров = runtime.NumCPU()

#### Общая схема конвейера:
источник задач -> tasks channel -> (контроль через sync.WaitGroup) worker 1, worker 2, worker 3, worker 4, worker 5 -> results chan -> (range + close) -> Обработка
IO-bound -> N воркеров, CPU-bound -> runtime.NumCPU()

📦 Fan-in и Fan-out в Go: распараллеливание задач и сбор результатов

❓ Что такое Fan-in и Fan-out?

Fan-out позволяет распараллелить выполнение задачи на несколько горутин, а Fan-in собирает результаты этих горутин в один поток данных.

💡 Полная реализация:
// Fan-out
func FanOut(input <-chan int, workers int) []<-chan int {
    outputs := make([]<-chan int, workers)
    for i := 0; i < workers; i++ {
        output := make(chan int)
        go func() {
            for value := range input {
                output <- value * 2
            }
            close(output)
        }()
        outputs[i] = output
    }
    return outputs
}

// Fan-in
func FanIn(inputs []<-chan int) <-chan int {
    output := make(chan int)
    var wg sync.WaitGroup
    for _, input := range inputs {
        wg.Add(1)
        go func(ch <-chan int) {
            for value := range ch {
                output <- value
            }
            wg.Done()
        }(input)
    }
    go func() {
        wg.Wait()
        close(output)
    }()
    return output
}

// Пример использования
func main() {
    input := make(chan int)
    go func() {
        for i := 0; i < 10; i++ {
            input <- i
        }
        close(input)
    }()

    outputs := FanOut(input, 3)
    result := FanIn(outputs)

    for value := range result {
        fmt.Println(value)
    }
}

⚠️ Преимущества:

- Распараллеливание задач.
- Эффективное использование ресурсов.
- Удобство сбора результатов.

❗ Ограничения:

- Требует синхронизации (например, `sync.WaitGroup`).
- Может быть сложным для управления при большом количестве горутин.
