🛠️ Context в Go: управление жизненным циклом операций

❓ Что такое context?

Context — это механизм в Go для управления жизненным циклом операций, таких как HTTP-запросы, горутины или запросы к базам данных. Он позволяет передавать значения, отменять операции и задавать тайм-ауты.

💡 Зачем нужен context?

Context помогает:

1. Управлять отменой операций:

- Например, отмена HTTP-запроса при закрытии соединения.
2. Задавать тайм-ауты:
- Ограничение времени выполнения операции.
3. Передавать значения:
- Например, передача идентификатора запроса между горутинами.

⚠️ Когда использовать context?

Context полезен в следующих случаях:

- Долгие операции, которые могут быть отменены (например, запросы к API).
- Работа с горутинами, которые должны завершаться при определенных условиях.
- Передача метаданных между слоями приложения.

❗Минусы context:

- Требует аккуратного использования, чтобы избежать утечек ресурсов.
- Может усложнить код, если используется чрезмерно.

🕹 ТЕХ-КВИЗ: Поймай утечку

Ситуация: Ты создал контекст с таймаутом на 10 секунд. Функция doWork справилась за сотку мс, но cancel() ты вызвать забыл. Что будет?

ctx, _ := context.WithTimeout(context.Background(), 10 * context.Second)
go doWork(ctx)

утечка действительно будет

И самое интересное, что проблема тут не в самой doWork(). Она давно завершилась. Но таймер внутри WithTimeout продолжит жить все 10 секунд, потому что cancel() никто не вызвал

На маленьком проекте это незаметно. Но под нагрузкой такие мелочи превращаются в лишние таймеры, висящие горутины и деградацию сервиса, которую потом очень неприятно дебажить

---

### ЧТО ТАКОЕ CONTEXT

- пользователь отправил запрос, но закрыл вкладку через 2 секунды
- твой сервер этого не знает и продолжает ходить в базу, вызывать другие сервисы, формировать ответ
- работа впустую

Context решает эту проблему. Это объект, который пробрасывается через всю цепочку вызовов и несёт два сигнала:

- ОТМЕНА: всё, прекращай работу
- ДЕДЛАЙН: у тебя 5 секунд, потом отмена

Каждый HTTP-запрос в Go уже приходит с контекстом. Твоя задача — пробросить его дальше и слушать.

### ЧЕТЫРЕ КОНСТРУКТОРА

[ CONTEXT В GO ] [ ПОЛЬЗА ]

- context.Background() — пустой корневой контекст. Стартовая точка, обычно в main или в начале запроса
- context.WithCancel(parent) — возвращает новый контекст и функцию cancel. Вызвал cancel — контекст отменён, ctx.Done() закрывается
- context.WithTimeout(parent, duration) — автоматическая отмена через N секунд. Внутри это тот же WithDeadline
- context.WithValue(parent, key, val) — кладёт значение в контекст. Для request-scoped данных: request ID, user ID. Не для передачи бизнес-параметров

```go
// Отмена вручную
ctx, cancel := context.WithCancel(context.Background())
defer cancel()

// Таймаут 3 секунды
ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
defer cancel()

// Значение в контексте
ctx = context.WithValue(ctx, "requestID", "abc-123")
```

### КАК СЛУШАТЬ ОТМЕНУ

[ CONTEXT В GO ] [ ПОЛЬЗА ]

У контекста есть канал ctx.Done(). Он закрывается когда контекст отменён или истёк таймаут. Используй select чтобы реагировать на отмену.

#### ДВА СПОСОБА ПРОВЕРКИ:

- SELECT С CTX.DONE(): для долгих операций в цикле или при ожидании каналов. Горутина слушает и результат, и отмену одновременно
- CTX.ERR(): быстрая проверка перед началом работы. Если контекст уже отменён, нет смысла начинать операцию. Возвращает context.Canceled или context.DeadlineExceeded

```go
// select: слушаем результат и отмену
select {
case result := <-workCh:
	return result, nil
case <-ctx.Done():
	return nil, ctx.Err() // Canceled или DeadlineExceeded
}

// Быстрая проверка перед работой
if ctx.Err() != nil {
	return ctx.Err()
}
```

### ПРАВИЛА РАБОТЫ С КОНТЕКСТОМ

[ CONTEXT В GO ] [ ПОЛЬЗА ]

1. ВСЕГДА ПЕРВЫЙ АРГУМЕНТ ФУНКЦИИ:
func GetUser(ctx context.Context, id int) — не в структуру, не вторым, не в конце

2. ВСЕГДА ВЫЗЫВАЙ CANCEL:
defer cancel() сразу после создания. Иначе горутины и таймеры утекут

3. НЕ КЛАДИ В КОНТЕКСТ БИЗНЕС-ДАННЫЕ:
request ID, trace ID, user ID — можно. Параметры запроса, конфиги, зависимости — нельзя

4. НЕ ХРАНИ КОНТЕКСТ В СТРУКТУРЕ:
Context живёт на время запроса, структура может жить дольше

5. ПРОБРАСЫВАЙ РОДИТЕЛЬСКИЙ КОНТЕКСТ:
Не создавай context.Background() внутри сервисов. Если вызывающая сторона отменит запрос, твой новый контекст об этом не узнает

### КАК СЛУШАТЬ ОТМЕНУ

[ CONTEXT В GO ] [ ПОЛЬЗА ]

У контекста есть канал ctx.Done(). Он закрывается когда контекст отменён или истёк таймаут. Используй select чтобы реагировать на отмену.

Если клиент разорвал соединение, контекст отменяется. Отмена доходит до SQL-запроса — база прекращает выполнение. Ни один слой не делает лишнюю работу.

#### ЦЕПОЧКА:

Handler r.Context() -> Service принимает ctx -> Repository передаёт в db.QueryContext(ctx, ...) -> PostgreSQL получает cancel

Это не просто хорошая практика, это стандарт. Функция без context.Context в сигнатуре — повод спросить "почему?"

```go
func (h *Handler) GetUser(w http.ResponseWriter, r *http.Request) {
	user, err := h.service.GetUser(r.Context(), userID)
}

func (s *Service) GetUser(ctx context.Context, id int) (*User, error) {
	return s.repo.FindByID(ctx, id)
}

func (r *Repo) FindByID(ctx context.Context, id int) (*User, error) {
	return r.db.QueryRowContext(ctx, "SELECT ...", id).Scan(&u)
}
```
