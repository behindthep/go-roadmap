Select в Go: как перестать писать хаотичный конкурентный код

Если ты работаешь с горутинами и каналами, но не понимаешь select, ты по сути не управляешь конкурентным кодом.

### ЧТО ТАКОЕ SELECT
Select позволяет горутине ждать сразу несколько каналов одновременно. Какой канал первым получит данные, тот case и выполнится
Без select ты можешь читать только из одного канала за раз. А если у тебя HTTP-ответ, таймаут и сигнал отмены приходят по разным каналам? Нужно слушать все сразу

Select похож на switch, но работает с каналами. Он блокирует горутину пока хотя бы один case не станет готов. Если готовы несколько, Go выберет случайный

#### Схема: Select в Go
msgCh, errCh, timer -> SELECT -> первый готовый case

```go
select {
case msg := <-msgCh:
    fmt.Println("сообщение:", msg)
case err := <-errCh:
    fmt.Println("ошибка:", err)
case <-time.After(5 * time.Second):
    fmt.Println("таймаут")
}
```

---

### КАК РАБОТАЕТ
Когда Go доходит до select, происходит следующее:

1. Все case проверяются одновременно
2. Если ни один канал не готов, горутина засыпает
3. Как только один из каналов получает значение или готов к записи, горутина просыпается
4. Выполняется код этого case
5. Select завершается (если не в цикле)

Если готовы сразу два канала, Go выбирает случайный. Не первый по порядку, а именно случайный. Это сделано специально, чтобы ни один канал не получал приоритет

---

### DEFAULT: НЕБЛОКИРУЮЩИЙ SELECT
Если добавить default, select перестаёт блокировать. Когда ни один канал не готов, выполняется default вместо ожидания
Это полезно для:

- Проверки канала без блокировки (try-receive)
- Неблокирующей отправки (try-send)
- Polling-циклов с обработкой между проверками

Но будь осторожен: select с default в бесконечном цикле без задержки сожрёт 100% CPU. Добавляй time.Sleep или runtime.Gosched если используешь polling

```go
// try-receive: проверить канал без блокировки
select {
case msg := <-ch:
    process(msg)
default:
    // канал пуст, делаем что-то другое
}
// try-send: отправить если есть место
select {
case ch <- event:
    // отправлено
default:
    // канал полный, пропускаем
}
```

#### Схема: default без блокировки
- try-receive — код чтения из канала с default
- try-send — код записи в канал с default
- Предупреждение: select + default в бесконечном цикле без паузы = 100% CPU

### ПАТТЕРНЫ С SELECT

#### Таймаут на операцию:
1. time.After возвращает канал, который сработает через N секунд
2. Комбинируй с select для ограничения времени ожидания

#### Graceful shutdown:
1. Слушай канал от signal.Notify (SIGTERM/SIGINT) через select
2. Когда сигнал пришёл, завершай работу чисто

#### Fan-in (слияние каналов):
1. Select в цикле читает из нескольких каналов
2. Все результаты идут в одну обработку

#### Context cancellation:
1. ctx.Done() возвращает канал
2. В select проверяешь отмену вместе с основной логикой

```go
// Таймаут + отмена через context
select {
case result := <-workCh:
    return result, nil
case <-ctx.Done():
    return nil, ctx.Err()
case <-time.After(10 * time.Second):
    return nil, errors.New("timeout")
}
```

### ОБЩАЯ КАРТИНА
Select, это мультиплексор каналов. Позволяет одной горутине слушать несколько каналов и реагировать на первый готовый

#### Что запомнить:
- Select блокирует пока один из case не станет готов
- Несколько готовых case -> случайный выбор, не по порядку
- default делает select неблокирующим, используй осторожно
- Таймауты, отмена через context, graceful shutdown, всё строится на select
- Select работает только с каналами, для мьютексов и обычных значений не подходит

Без select конкурентный код в Go превращается в набор отдельных горутин, которые не умеют координироваться. Select, это клей, который связывает каналы в рабочую архитектуру

#### Схема: Select, общая картина
данные, ошибки, ctx.Done(), таймаут, OS signal -> SELECT -> Обработка первого готового
Мультиплексор каналов: слушай всё, реагируй на первое
