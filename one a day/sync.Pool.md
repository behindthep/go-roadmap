sync.Pool в Go: как уменьшить нагрузку на GC и ускорить сервис

### ЗАЧЕМ НУЖЕН SYNC.POOL
Каждый запрос создает временный буфер. Парсишь JSON, собираешь ответ, сериализуешь. Миллион запросов в минуту, миллион аллокаций, миллион работ для GC. Сборщик не справляется, p99 прыгает

- X СБОРЩИК НЕ СПРАВЛЯЕТСЯ — p99 прыгает

#### SYNC.POOL РЕШАЕТ ЭТУ ПРОБЛЕМУ
Это хранилище временных объектов, которые можно переиспользовать между горутинами. Вместо создания нового объекта берешь готовый из пула. Закончил работу, вернул обратно

РЕЗУЛЬТАТ:
- меньше аллокаций,
- меньше работы GC,
- стабильный latency

Стандартная библиотека использует пулы внутри: fmt, encoding/json, net/http.
В сервисе под нагрузкой sync.Pool дает ощутимый прирост без усложнения архитектуры

---

### КАК ИСПОЛЬЗОВАТЬ
API из трех методов:

#### NEW:
функция, которую пул вызывает когда свободных объектов нет. Создает новый экземпляр

#### GET:
достает объект из пула. Если пул пуст, вызывается New

#### PUT:
возвращает объект обратно в пул

Главный паттерн: перед Put сбрасывай состояние объекта. Иначе следующий Get получит мусор от предыдущего использования. Для bytes.Buffer это Reset, для slice это s[:0], для структуры — обнуление полей

```go
var bufferPool = sync.Pool{
    New: func() any {
        return new(bytes.Buffer)
    },
}
func handle(w http.ResponseWriter, r *http.Request) {
    buf := bufferPool.Get().(*bytes.Buffer)
    defer func() {
        buf.Reset()
        bufferPool.Put(buf)
    }()
    buf.WriteString("hello ")
    buf.WriteString(r.URL.Path)
    w.Write(buf.Bytes())
}
```

### КОГДА РЕАЛЬНО ПОМОГАЕТ

#### SYNC.POOL ДАЕТ ПРИРОСТ КОГДА:
1. Объект крупный (буфер на килобайты) или дорогой в создании
2. Аллокации идут в hot path, десятки тысяч раз в секунду
3. Объект однотипный, состояние сбрасывается просто

#### ТИПИЧНЫЕ КЕЙСЫ:
1. bytes.Buffer для сериализации HTTP-ответов
2. gzip.Writer и gzip.Reader
3. json decoder с большим внутренним буфером
4. scratch-slice для парсинга пакетов

#### КОГДА ПУЛ НЕ ПОМОЖЕТ:
1. Маленькие структуры с парой полей, дешевле просто аллоцировать
2. Редкие операции, разница теряется в шуме
3. Объекты разного размера, пул не даст предсказуемости

Мерь бенчмарками. Без профилирования sync.Pool превращается в карго-культ

### ПОДВОДНЫЕ КАМНИ

- ПУЛ МОЖЕТ ОЧИСТИТЬСЯ В ЛЮБОЙ МОМЕНТ:
  GC вытирает часть пула каждый цикл. Полагаться на наличие объекта нельзя. Всегда готов к вызову New

- STATE МЕЖДУ GET И PUT — УТЕЧКА ДАННЫХ:
  Объект в пуле общий для всех горутин. Оставил чужой UserID в response, следующий пользователь увидит чужие данные

- ОБЯЗАТЕЛЬНО СБРАСЫВАЙ ПЕРЕД PUT:
  buf.Reset(), slice[:0], обнуление полей структуры. Иначе новый владелец получит чужой state

- НЕ КЛАДИ ОБЪЕКТЫ С УКАЗАТЕЛЯМИ НА БОЛЬШИЕ СТРУКТУРЫ:
  Пул будет удерживать эти структуры от сборки. Обнуляй поля перед Put или используй пулы аккуратно

- НЕ ИСПОЛЬЗУЙ ДЛЯ КОННЕКТОВ:
  Соединения к БД, файлы, сокеты требуют явного lifecycle. Для них бери специализированные пулы (database/sql, pgxpool)

```go
// ПЛОХО: забыл сбросить UserID, следующий запрос увидит чужой
resp := respPool.Get().(*Response)
resp.UserID = userID
respPool.Put(resp)

// ХОРОШО: обнуляем перед возвратом
resp := respPool.Get().(*Response)
resp.UserID = userID

// ... работаем ...
*resp = Response{}
respPool.Put(resp)
```

### ОБЩАЯ КАРТИНА
sync.Pool — инструмент тонкий. Полезен когда профилирование показывает давление на GC от частых однотипных аллокаций. В остальных случаях он добавляет сложности без выгоды

#### Что запомнить:
- Пул переиспользует временные объекты между горутинами
- Пул может быть очищен GC в любой момент, всегда готов к New
- Перед Put всегда сбрасывай state (Reset, [:0], обнуление полей)
- Используй для крупных объектов в hot path: буферы, writer, decoder
- Для соединений бери специализированные пулы, sync.Pool не подходит
- Прирост меряй бенчмарками до и после, на глаз не оценивай

sync.Pool — оптимизация. Сначала работающий код, потом пулы
