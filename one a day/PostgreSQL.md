🎦Как YouTube хранит миллиарды видео. Часть 1

За годы работы сервиса накопились миллиарды роликов общим объемом в десятки эксабайт

И здесь возникает логичный вопрос: Где вообще хранятся все эти видео?

Большинство подумает, что в базе данных. И это именно то решение, которое YouTube никогда бы не использовал


❌ Почему PostgreSQL — плохое место для хранения видео

Представим самое простое решение. Есть таблица (см. карточку 2)

Кажется логичным хранить видео прямо внутри базы. А теперь представьте ролик размером 2 ГБ. А теперь миллиард таких роликов

Начнут появляться серьезные проблемы

SQL-базы отлично подходят для хранения структурированных данных, но не для огромных бинарных файлов


⚡️Главное архитектурное решение

Вместо хранения самого видео крупные сервисы разделяют данные на две части

Первая – метаданные:
• название
• автор
• количество просмотров
• длительность
• путь к файлу

Вторая – само видео. Оно хранится отдельно (см. карточку 3)


📁 Где тогда лежат сами видео?

Для этого существуют специальные системы хранения – Object Storage

Его задача всего одна: надежно хранить объекты любого размера и быстро отдавать их по запросу

Когда пользователь открывает видео, приложение сначала обращается к базе данных, получает путь к файлу, а затем загружает само видео уже из Object Storage. (см. карточку 4)

Именно поэтому даже при огромном количестве роликов база данных остается небольшой и быстрой


### А ЧТО ЕСЛИ ХРАНИТЬ ВИДЕО ПРЯМО В POSTGRESQL?

#### Таблица videos:
- id | title | author | video_file (2 GB)
- id | title | author | video_file (4 GB)
- id | title | author | video_file (7.8 GB)
- id | title | author | video_file (20 GB)
- id | title | author | video_file (72 GB)
- + 10 000 000 000 видео

#### Проблемы:
- X Огромные резервные копии
- X Медленная репликация
- X Долгое восстановление
- X Очень дорого хранить

---

### ТОГДА ГДЕ ХРАНИТЬ САМИ ВИДЕО?

#### Схема разделения хранения:
- PostgreSQL (метаданные): id, title, author, views, duration, storage_path -> (Где лежит видео?) ->
- Object Storage (сами файлы): video_8fa2.mp4, video_9c14.mp4, video_a921.mp4, video_d813.mp4 ... + миллиарды файлов

База данных хранит информацию о видео. Object Storage хранит сами файлы

---

### КАК ПОЛЬЗОВАТЕЛЬ ПОЛУЧАЕТ ВИДЕО?

#### Схема получения видео:
1. Пользователь -> Backend API (ищет информацию)
2. Backend API -> PostgreSQL (id, title, author, storage_path — получает путь)
3. По полученному пути -> Object Storage (video.mp4, video2.mp4, video3.mp4 — получает файл) -> Видео (отдаётся пользователю)

🚗 Как Яндекс Go обрабатывает миллионы GPS-координат каждую минуту?

Когда водитель работает в Яндекс Go, приложение постоянно отправляет его GPS-координаты

Если представить, что на линии находится 100 000 водителей, а координаты обновляются раз в 2 секунды, получится около 50 000 обновлений каждую секунду

Как обработать такой поток данных?


❌ Почему PostgreSQL не подходит?

На первый взгляд кажется логичным хранить последние координаты каждого водителя в PostgreSQL

Но тогда каждое обновление превращается в UPDATE. Десятки тысяч операций записи в секунду создают большую нагрузку на диск, WAL и репликацию. Для данных, которые меняются практически непрерывно, реляционная БД становится узким местом. (см. карточку 2)


🍀 Как эту проблему обычно решают?

В системах реального времени последние координаты обычно хранят в in-memory-хранилище (например, Redis). Новая точка просто заменяет предыдущую, поэтому обновления занимают миллисекунды и не требуют постоянной записи на диск. (см. карточку 3)


📍Как найти ближайшего водителя?

Проверять расстояние до всех автомобилей слишком дорого. Для поиска кандидатов используется геоиндекс, который позволяет искать только среди ближайших машин. В подобных системах эту задачу часто решают с помощью Geohash или H3. (см. карточку 4)

📁 А где хранится история маршрутов?

Последняя координата нужна только для работы сервиса здесь и сейчас. Для аналитики поток GPS-событий обычно отправляют в брокер сообщений (например, Kafka), а затем сохраняют в аналитическое хранилище (например, ClickHouse). (см. карточку 5)

### ПОЧЕМУ POSTGRESQL НЕ ПОДХОДИТ?

#### Схема нагрузки на БД:
GPS от водителей (~50 000 обновлений/сек) -> UPDATE drivers SET lat = ..., lon = ... -> PostgreSQL -> WAL -> Запись на диск -> Репликация

#### Проблемы:
- X Постоянная запись на диск
- X Рост WAL
- X Высокая нагрузка на репликацию
- X Становится узким местом

---

### ПОЧЕМУ ТУТ ПОДХОДИТ IN-MEMORY STORAGE?

#### Схема хранения:
GPS от водителей -> In-memory storage (например, Redis) -> Хранится только последняя координата водителя

#### Пример записи в хранилище:
- Driver: 42
```yaml
lat: 55.75
lon: 37.61
updated: 18:42:13
```
-> обновляется на новое значение:
- Driver: 42
```yaml
lat: 55.76
lon: 37.62
updated: 18:42:14
```

Обновление занимает миллисекунды и не требует постоянной записи на диск

---

### КАК РАБОТАЕТ ГЕОИНДЕКС?

#### Схема сетки геоиндекса:
- Карта разбита на сетку ячеек (регионов/хешей).
- Пользователь находится в центре выделенной области (охватывающей ближайшие ячейки вокруг него, например 4×4).
- Из всех машин на карте в выборку попадает только та, что находится внутри выделенной зоны поиска вокруг пользователя (остальные машины за пределами зоны игнорируются).

Геоиндекс используется для поиска водителей рядом с пользователем. Geohash и H3 — самые распространенные реализации подобных индексов

---

### ПОЧЕМУ ИСПОЛЬЗУЮТ НЕСКОЛЬКО ХРАНИЛИЩ?

#### Схема распределения потоков данных:
GPS от водителей ->
- Последняя точка -> In-memory storage (например, Redis)
- Поток событий (все точки) -> Брокер сообщений (например, Kafka) -> Аналитич. хранилище (например, ClickHouse)

#### Что хранить и где лучше хранить:
- Последнюю координату -> In-memory storage — быстрые обновления в реальном времени
- Поток GPS-событий -> Брокер сообщений — надежная доставка и масштабируемость
- Историю перемещений -> Аналитическое хранилище — аналитика и построение отчетов

Такой подход позволяет одновременно работать в реальном времени и анализировать миллионы событий
