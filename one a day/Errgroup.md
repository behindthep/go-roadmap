### ЗАЧЕМ НУЖЕН ERRGROUP

Запускаем несколько горутин параллельно, каждая может вернуть ошибку. Хотим: дождаться всех, поймать первую ошибку, отменить остальные. На голом sync.WaitGroup это пишется руками, на каждом проекте заново.

errgroup решает задачу одной структурой. Часть пакета golang.org/x/sync. Официальный, активно используется в стандарте, но формально не в стандартной либе.

#### ЧТО ДАЕТ:

- Wait() ждет все горутины и возвращает первую ошибку
- Контекст с автоматической отменой при первой ошибке
- Лимит параллелизма через SetLimit
- TryGo для non-blocking запуска при достижении лимита

Используется почти везде где нужна параллелизация: загрузка данных из нескольких источников, обработка батча, fan-out по сервисам.

### БАЗОВОЕ ИСПОЛЬЗОВАНИЕ

Импорт: golang.org/x/sync/errgroup

#### БАЗОВЫЙ ПАТТЕРН:

1. Создаем errgroup.Group -> 2. Запускаем функции через g.Go(func() error) -> 3. g.Wait() блокирует до завершения всех, возвращает первую non-nil ошибку

Каждая g.Go запускает горутину. Если функция вернула ошибку, errgroup ее запоминает (только первую). Wait вернет именно эту ошибку.

```go
import "golang.org/x/sync/errgroup"

func fetchAll(ctx context.Context) (User, []Order, error) {
	var g errgroup.Group
	var user User
	var orders []Order

	g.Go(func() error {
		var err error
		user, err = fetchUser(ctx)
		return err
	})

	g.Go(func() error {
		var err error
		orders, err = fetchOrders(ctx)
		return err
	})

	if err := g.Wait(); err != nil {
		return User{}, nil, err
	}

	return user, orders, nil
}
```

### КОНТЕКСТ И АВТОМАТИЧЕСКАЯ ОТМЕНА

Главная фича — errgroup.WithContext(ctx). Возвращает группу и производный контекст. Если любая горутина вернула ошибку, контекст отменяется автоматически.

#### НА ПРАКТИКЕ:

- Остальные горутины должны слушать ctx.Done() и сами завершиться
- Сетевые вызовы (http, gRPC, pgx) уважают ctx и отменятся сами
- Долгие циклы внутри функции — добавь явную проверку ctx.Done()

```go
g, ctx := errgroup.WithContext(parentCtx)

g.Go(func() error {
	return fetchUser(ctx) // отменится при ошибке других
})

g.Go(func() error {
	return fetchOrders(ctx)
})

if err := g.Wait(); err != nil {
	// одна из задач упала, остальные уже отменены
}
```

Без WithContext: первая ошибка запоминается, но остальные горутины продолжают работу. Зря тратятся ресурсы и время. Для параллельных операций всегда используй WithContext.

### ЛИМИТ ПАРАЛЛЕЛИЗМА (SETLIMIT)

[ ERRGROUP ] [ ПОЛЬЗА ]

Запустить 10000 горутин на 10000 файлов — рецепт OOM и перегрузки downstream. SetLimit ограничивает одновременно работающие горутины.

```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(10) // максимум 10 одновременных

for _, url := range urls {
	url := url
	g.Go(func() error {
		return fetch(ctx, url)
	})
}

g.Wait()
```

#### ЕСЛИ ЛИМИТ ДОСТИГНУТ, G.GO БЛОКИРУЕТСЯ ДО ОСВОБОЖДЕНИЯ СЛОТА

Альтернатива — g.TryGo(fn). Non-blocking запуск. Если слотов нет, возвращает false, функция не запускается. Полезно когда нужен drop вместо ожидания.

```go
if !g.TryGo(fn) {
	metrics.Dropped.Inc()
}
```

SetLimit вызывай до первого g.Go. Изменять во время работы поведение не задумано.

### ПОДВОДНЫЕ КАМНИ И ОБЩАЯ КАРТИНА

1. ERRGROUP ЗАПОМИНАЕТ ТОЛЬКО ПЕРВУЮ ОШИБКУ:
Если упало 5 горутин, увидишь первую. Остальные потеряны. Если важны все — собирай руками с mutex и errors.Join

1. ЗАМЫКАНИЕ НА ПЕРЕМЕННУЮ ЦИКЛА (ДО GO 1.22):
for _, x := range items { g.Go(func() error { return work(x) }) } до Go 1.22 захватит общий x. Все горутины работают на последнем значении. С 1.22 переменная per-iteration. Если поддерживаешь старые версии — x := x перед g.Go

1. ДОЛГАЯ ЗАДАЧА БЕЗ ПРОВЕРКИ CTX:
Если задача не слушает ctx.Done(), отмена не сработает. errgroup ждет ее естественного завершения

1. WAIT ВЫЗЫВАЮТ ОДИН РАЗ:
После Wait группа использована. Для нового батча — новая группа

1. ERRGROUP VS SYNC.WAITGROUP:
2. WaitGroup — счетчик, ничего не знает про ошибки и отмену
3. errgroup — счетчик + первая ошибка + контекст с cancel
4. Если задачи без ошибок и отмены не нужны, WaitGroup проще
