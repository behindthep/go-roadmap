CI/CD - автоматический процесс сборки, тестирования и выкатывания кода.
Основа стабильных релизов.

CI (Countinuos Integration) - автоматически проверяет код после каждого коммита.

CD (Continuous Delivery/Deployment) - автоматизирует релизы в прод и стейдж

```go
Код     -> Проверка -> Релиз
Commit     CI          CD
```

Идея: сделал коммит -> система сама всё собрала, протестировала и выложила.

### CI

После каждого коммита в репозиторий автоматически запускаются:
1. Build сборка проекта
2. Lint линтеры
3. Test тесты
4. Quality check проверка качества кода

Если что-то упало - релиз отсанавливается.
Если всё зеленое - можно выкатывать.

CI экономит время и защищяет от ошибок при сборке.

### CD

Автоматически выкатывает приложение на сервера: сначала на тестовый стенд, потом в прод.

CD Pipeline:
1) Deploy yo Staging
2) Smoke Tests
3) Deploy to Production

Перед выкладкой система снова проверяет все: здоровье, окружение, переменные, секреты.

Если что-то не так - откат.

CD делает релизы предсказуемыми, быстрыми и безопасными.

### Стратегии Роллаута

Как выкатываются релизы. В CD сущ. несколько стратегий выката:

- Blue-Green: две версии, переключаемся мгновенно
- Canary: выкатываем на часть пользователей
- Rolling Update: обновляем серверы один за одним
- Recreate: выключить -> включить заново

Проекты используют разные стратегии, в зависимости от нагрузки и рисков.

CI/CD:
1) Ускоряет разработку
2) Делает релизы предсказуемыми
3) Уменьшает кол-во ошибок
4) Команда перестаёт руками собирать, тестировать и катить релизы
5) Быстрее, безопаснее, стабильнее


### Канареечный релиз (Canary Release)

один из самых безопасных способов выкатывать обновления без риска уронить прод.
Способ выкатывать новую версию сервиса сначала на небольшой процент трафика.
Запуск новой версии параллельно со старой и направляем на неё 1-5% пользователей.
Кол-во обрабатываемого трафика: 99% старая версия, 1% новая.
Смотрий метрики, ошибки и поведение системы.
Если метрики нормальные - увеличавем долю трафика.
Если проблемы - быстро откатываемся.

Название Канарейки пришло из шахт: шахтёры брали с собой канареек - если был газ, птица реагировала первой, и люди успевали выйти.

В IT новая версия - это та самая канарейка. Если она "задывахется", видим проблему раньше, чем пострадают все пользователи.

#### Зачем нужна канарейка

Канареечный релиз позволяет безопасно проверять новую версию на реальных пользователях.

- Если новая версия ломается, дреградирует, вызывает ошибки или увеличивает latency - видно на маленьком проценте трафика
- Если всё хорошо - увеличваем трафик. Если появляются проблемы - быстро откатываемся.

Даже критическая ошибка затронет 1-5% пользователей.
Риск массового падения сильно ниже.
Проблема в модуле оплаты. Если выкатить сразу на 100%, можно потерять половину транзакций / на 1 % - канарейка это ловит, откат мгновенный.

#### Как работает Канареечный релиз

1) Деплой новой версии рядом со старой - обе работают параллельно
2) МАршрутизатор/Gateway/Ingress делит трафик: старой версии 95-99%, новой 1-5%
3) Смотрим ключевые метрики: оишбки, latency, нагрузку на базу, очереди, успешные операции
    4) Если всё хорошо - повышаем трафик (1-5-20-50-100%)
    5) Если плохо - делаем rollback за секунду

Мгновенный роллбэк за счет переключения маршрутизации трафика (Traffic Shifting) с новой версии на старую без пересборки или перезапуска контейнеров.
Возможен только для кода приложения. Если релиз включал несовместимые миграции БД (удаление колонки), простой сменой трафика не обойтись.

#### Показатели

Чтобы понять, работает новая версия или нет, смотрят показатели:
1) Ошибки
2) Нагрузка на сервер
3) Нагрузка на БД
4) Скорость работы
5) Очереди
6) Успешные действия: оплаты, заказы, авторизации

Если новая версия ухудшает любой показатель - её откатывают.

Плюсы:
- Безопасно
- Можно быстро откатить
- Видно, как новая версия работает "вживую"
- Подходит для важных сервисов

Минусы:
- Нужно больше настроекк
- Нужен хороший мониторинг
- Требует больше времени, чем обычный релиз
