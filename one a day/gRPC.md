🌐 gRPC: современный RPC фреймворк

❓ Что такое gRPC?

gRPC - это высокопроизводительный фреймворк для удаленного вызова процедур (RPC), разработанный Google.

💡 Ключевые особенности:

1. Протокол:
   - Protocol Buffers для сериализации
   - HTTP/2 для транспорта
   - Поддержка потоковой передачи
   - Двунаправленная коммуникация

2. Типы взаимодействий:
   - Унарные (request/response)
   - Серверные потоки
   - Клиентские потоки
   - Двунаправленные потоки

⚠️ Когда использовать?

- Микросервисная архитектура
- Системы реального времени
- Мобильные приложения
- Высоконагруженные системы

❗Особенности реализации:

- Необходимость написания .proto файлов
- Сложность отладки
- Требует HTTP/2

### ЗАЧЕМ СРАВНИВАТЬ

[ GRPC VS REST ] [ ПОЛЬЗА ]

Два сервиса должны общаться. Как именно – вопрос, который определит скорость, удобство разработки и возможности масштабирования.

- REST (Стандарт последних 15 лет): JSON по HTTP, понятный всем, работает везде. Открыл браузер, отправил запрос, получил ответ
- gRPC (Протокол от Google): Бинарный формат, строгие контракты, стриминг. Быстрее, но сложнее в настройке

Оба решают одну задачу: связь между сервисами. Но подходят для разных ситуаций.

### REST: ПРОСТО И ПОНЯТНО

[ GRPC VS REST ] [ ПОЛЬЗА ]

REST работает поверх HTTP. Ресурсы описываются URL-ами, действия – методами (GET, POST, PUT, DELETE). Данные передаются в JSON.

#### ЧТО ПОЛУЧАЕШЬ:

1. Читаемый формат, JSON можно открыть глазами
2. Работает из браузера, curl, Postman, мобилки
3. Кеширование из коробки (HTTP-кеш, CDN)
4. Огромная экосистема: Swagger/OpenAPI, middleware, библиотеки
5. Любой разработчик поймёт API за 5 минут

#### ГДЕ СЛАБОСТИ:

JSON тяжёлый (текстовый), нет строгой типизации контракта, нет стриминга из коробки, для каждого запроса новое соединение в HTTP/1.1

```go
// REST: обработчик на chi
r.Get("/users/{id}", func(w http.ResponseWriter, r *http.Request) {
	id := chi.URLParam(r, "id")
	user, err := service.GetUser(r.Context(), id)
	json.NewEncoder(w).Encode(user)
})
```

### GRPC: БЫСТРО И СТРОГО

[ GRPC VS REST ] [ ПОЛЬЗА ]

gRPC использует Protocol Buffers (protobuf) для описания контрактов и сериализации. Данные передаются в бинарном формате по HTTP/2.

#### ЧТО ПОЛУЧАЕШЬ:

1. Бинарный формат, в 5-10 раз компактнее JSON
2. Строгий контракт: .proto файл описывает все методы и типы
3. Генерация кода для Go, Java, Python, TypeScript — из одного .proto
4. Мультиплексирование: много запросов по одному соединению (HTTP/2)
5. 4 типа взаимодействия: unary, server stream, client stream, bidirectional stream

#### ГДЕ СЛАБОСТИ:

нельзя вызвать из браузера напрямую, бинарный формат не прочитаешь глазами, сложнее дебажить, нужна кодогенерация

```proto
// user.proto — контракт
service UserService {
	rpc GetUser (GetUserRequest) returns (User);
	rpc ListUsers (ListRequest) returns (stream User);
}
```

```go
// Go: сгенерированный клиент
user, err := client.GetUser(ctx, &pb.GetUserRequest{Id: 42})
```

### СРАВНЕНИЕ

[ GRPC VS REST ] [ ПОЛЬЗА ]

- Формат данных: REST — JSON (текст) | gRPC — Protobuf (бинарный)
- Транспорт: REST — HTTP/1.1 или HTTP/2 | gRPC — только HTTP/2
- Контракт: REST — OpenAPI/Swagger (опционально) | gRPC — .proto (обязательно)
- Стриминг: REST — нет (нужны WebSocket) | gRPC — 4 типа из коробки
- Размер сообщений: REST — крупнее | gRPC — в 5-10x меньше
- Скорость сериализации: REST — медленнее | gRPC — быстрее
- Браузер: REST — работает | gRPC — нужен grpc-web прокси
- Кеширование: REST — HTTP-кеш, CDN | gRPC — нет из коробки
- Порог входа: REST — низкий | gRPC — выше

### КОГДА ЧТО ВЫБИРАТЬ

[ GRPC VS REST ] [ ПОЛЬЗА ]

#### REST ВЫБИРАЙ ДЛЯ:

1. Публичный API (мобилки, сторонние разработчики, браузер)
2. CRUD-сервисы с простой логикой
3. Когда важна простота и скорость разработки
4. Когда нужно кеширование через CDN

#### GRPC ВЫБИРАЙ ДЛЯ:

1. Общение между микросервисами внутри кластера
2. Высоконагруженные внутренние API (тысячи RPS)
3. Стриминг данных (чат, обновления в реальном времени, логи)
4. Полиглотные системы (один .proto на все языки)

#### ТИПИЧНАЯ АРХИТЕКТУРА:

REST наружу (для клиентов), gRPC внутри (между сервисами). API Gateway принимает REST, проксирует в gRPC
