### ЗАЧЕМ ДВА ПОДХОДА

[ ACID VS BASE ] [ ПОЛЬЗА ]

Когда проектируешь систему, рано или поздно встаёт вопрос: насколько строго хранить данные?

- ACID – СТРОГИЕ ГАРАНТИИ: Данные всегда консистентны, транзакции надёжны. Но это стоит производительности и сложно масштабировать горизонтально
- BASE – МЯГКИЕ ГАРАНТИИ: Система быстрее и легче масштабируется, но данные могут быть временно неконсистентны

Это не "хороший vs плохой". Это два инструмента для разных задач. Банковский перевод и лента новостей требуют разных гарантий.

### G, M, P: ТРИ СУЩНОСТИ

[ ACID VS BASE ] [ ПОЛЬЗА ]

1. ATOMICITY:
транзакция выполняется целиком или не выполняется вообще. Перевёл деньги: списались у одного, зачислились другому. Если зачисление упало, списание откатывается

2. CONSISTENCY:
данные переходят из одного валидного состояния в другое. Если баланс не может быть отрицательным, транзакция, которая это нарушит, не пройдёт

3. ISOLATION:
параллельные транзакции не видят промежуточные результаты друг друга. Два человека покупают последний товар одновременно, только один получит его

4. DURABILITY:
если транзакция подтверждена, данные не потеряются даже при падении сервера. Записано на диск, точка

Примеры: PostgreSQL, MySQL, Oracle, SQLite

### BASE: ТРИ ПРИНЦИПА

[ ACID VS BASE ] [ ПОЛЬЗА ]

1. BASICALLY AVAILABLE:
система всегда отвечает на запросы, даже если часть узлов недоступна. Лучше вернуть немного устаревшие данные, чем не вернуть ничего

2. SOFT STATE:
состояние системы может меняться со временем, даже без новых запросов. Данные реплицируются между узлами в фоне, и в какой-то момент узел получит обновление

3. EVENTUALLY CONSISTENT:
если прекратить запись, все узлы со временем придут к одинаковому состоянию. Не мгновенно, но гарантированно

BASE, это осознанный компромисс: мы ослабляем консистентность, чтобы получить доступность и горизонтальное масштабирование.

Примеры: Cassandra, DynamoDB, MongoDB (default), Redis Cluster

### СРАВНЕНИЕ

[ ACID VS BASE ] [ ПОЛЬЗА ]

- Консистентность: ACID — строгая, мгновенная | BASE — eventual, с задержкой
- Доступность: ACID — может отказать ради консистентности | BASE — всегда отвечает
- Масштабирование: ACID — вертикальное (мощнее сервер) | BASE — горизонтальное (больше узлов)
- Скорость записи: ACID — медленнее (ждём подтверждения) | BASE — быстрее (пишем локально)
- Сложность: ACID — проще для разработчика | BASE — сложнее (конфликты, идемпотентность)
- Связь с CAP: ACID — CP (Consistency + Partition tolerance) | BASE — AP (Availability + Partition tolerance)

ACID проще в разработке, ты получаешь гарантии из коробки. BASE требует больше работы: нужно обрабатывать конфликты, дубликаты, обеспечивать идемпотентность.

### КОГДА ЧТО ВЫБИРАТЬ

[ ACID VS BASE ] [ ПОЛЬЗА ]

Выбор зависит не от базы, а от задачи. Внутри одного приложения могут жить оба подхода.

#### ACID

Выбирай для:

1. Платежи и финансы (перевод, списание, возврат)
2. Управление заказами (статус, остатки на складе)
3. Регистрация и авторизация
4. Всё, где потеря или дубль данных = деньги или репутация

#### BASE

Выбирай для:

1. Лента, рекомендации, уведомления
2. Аналитика, логи, метрики
3. Счётчики лайков и просмотров
4. Кеширование и поисковые индексы

Типичная архитектура: PostgreSQL (ACID) для ядра бизнес-логики + Cassandra или Redis (BASE) для быстрого чтения и аналитики
