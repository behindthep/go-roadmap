Один неудачный клиент может положить весь сервис

И проблема не всегда в железе или коде, иногда ты просто не ограничил поток запросов вовремя.

Rate limiting — одна из тех тем, про которые редко думают на старте, но почти всегда вспоминают уже после первых проблем под нагрузкой.

На собеседованиях это тоже любят: где поставить лимитер, почему Token Bucket стал дефолтом, зачем Redis и почему наивный INCR + EXPIRE ломается в кластере.

### ЗАЧЕМ НУЖЕН RATE LIMITING
API принимает 10k rps. Один клиент запустил скрипт, шлет 50k rps. Соседи не могут достучаться, сервис ложится
Rate limiting ограничивает частоту запросов. Разным клиентам, на разные endpoint, в разное время

#### Где применяется:
- Защита от DDoS и перегрузки
- Честное распределение между клиентами (fair use)
- Тарифы API: free / pro / enterprise
- Защита от брутфорса логина и регистрации
- Контроль расходов на платные внешние API

Алгоритмов несколько, ключевые три: Token Bucket, Leaky Bucket, Sliding Window. Выбор зависит от того что важнее: burst-трафик, плавность или точность

---

### TOKEN BUCKET
Идея: у клиента есть ведро с токенами. Каждый запрос забирает один токен. Если токенов нет, запрос отклоняется. Токены добавляются с постоянной скоростью

#### Параметры:
- Capacity — максимум токенов в ведре
- Refill rate — сколько токенов в секунду

#### Плюсы:
- Разрешает burst: накопил 100 токенов, разом отправил 100 запросов
- Прост в реализации
- В стандартной либе Go из коробки: golang.org/x/time/rate

#### Минусы:
- Burst может перегрузить downstream-сервис
- Если burst нежелателен, нужна другая схема

```go
import "golang.org/x/time/rate"
// 10 rps в среднем, burst до 30
limiter := rate.NewLimiter(10, 30)
if !limiter.Allow() {
    http.Error(w, "too many requests", 429)
    return
}
```

### LEAKY BUCKET
Идея: запросы складываются в очередь. Обработчик вычитывает их с постоянной скоростью, как вода вытекает из ведра с дыркой. Если очередь переполнена, запрос отбрасывается

#### Параметры:
- Capacity — максимум в очереди
- Leak rate — скорость обработки

#### Плюсы:
- Плавный исходящий трафик, downstream защищен от всплесков
- Хорошо подходит для защиты медленного бэкенда

#### Минусы:
- Нет burst-режима, все запросы ждут своей очереди
- Добавляет latency: запрос мог бы пройти сразу, но стоит в очереди
- Очередь = память + сложность реализации

Применяется реже Token Bucket. В большинстве систем burst допустим, а лишний latency пользователи не любят

### ОБЩАЯ КАРТИНА
Самый точный алгоритм, но самый сложный. Решает проблему пограничных эффектов fixed window

- FIXED WINDOW - НАИВНЫЙ ВАРИАНТ: считаем запросы в окне 60 секунд. В 00:59 пришло 100 запросов, в 01:00 еще 100. Формально лимит 100 rpm соблюден, но за 2 секунды прошло 200 запросов. Граница окна — дыра в защите
- SLIDING WINDOW: окно "движется" вместе с временем, всегда смотрит на последние 60 секунд

#### Два подхода:
- SLIDING LOG — храним timestamp каждого запроса, считаем сколько попало в последние 60 секунд. Точно, но дорого по памяти на трафике
- SLIDING WINDOW COUNTER — гибрид: два счетчика (текущее и предыдущее окно), взвешенная сумма по позиции внутри текущего окна. Быстро, достаточно точно, расход памяти константный

```lua
-- Redis Lua: атомарный sliding window counter
local current = redis.call('INCR', KEYS[1])
if current == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[1])
end
if current > tonumber(ARGV[2]) then
    return 0
end
return 1
```

### КОГДА ЧТО ИСПОЛЬЗОВАТЬ (ОБЩАЯ КАРТИНА)

#### 1. TOKEN BUCKET — ВЫБОР ПО УМОЛЧАНИЮ:
1. Публичный API с тарифами
2. Нужен burst, клиенты могут копить лимит
3. В Go из стандарта: golang.org/x/time/rate

#### 2. LEAKY BUCKET:
1. Защита слабого downstream
2. Нужен ровный исходящий трафик
3. Готов добавить latency вместо отказов

#### 3. SLIDING WINDOW:
1. Биллинг по API, где каждый запрос считается в счет
2. Нужна точность без эффектов границы fixed window
3. Распределенный сценарий через Redis

#### 4. ЧТО ЗАПОМНИТЬ:
1. Token Bucket покрывает 80% задач, начни с него
2. Leaky Bucket — когда важна плавность исходящего потока
3. Sliding Window — когда важна точность счета
4. Распределенный лимитер живет в Redis с Lua-скриптом для атомарности
5. На входе кластера используй Nginx limit_req, Envoy или Cloudflare, не пиши с нуля
