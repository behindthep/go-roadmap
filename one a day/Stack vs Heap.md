Stack vs Heap: где живут ваши переменные

Местоположение данных в памяти напрямую влияет на то, хватит ли сервису двух подов под высокой нагрузкой или придется арендовать еще двадцать.

### ЗАЧЕМ РАЗБИРАТЬСЯ
Каждая переменная в Go живёт в одном из двух мест: stack или heap. Оба хранят данные, но работают по-разному.

#### STACK:
быстрый и бесплатный

#### HEAP:
гибкий, но за него платишь производительностью

Большинство Go-разработчиков не задумываются об этом, и в 90% случаев это нормально.
Но когда сервис обрабатывает тысячи запросов в секунду, разница между stack и heap определяет, хватит ли тебе 2 подов или нужно 20

#### Схема: Stack vs Heap в Go
STACK vs HEAP — Где живут твои переменные?

---

### STACK: БЫСТРЫЙ И ПРОСТОЙ
Stack работает как стопка тарелок, последняя положенная снимается первой (LIFO).
Каждая горутина получает свой stack, начинается с 2–8 KB и растёт по необходимости до 1 GB.

#### Когда функция вызывается
на stack кладётся фрейм: локальные переменные, аргументы, адрес возврата.

#### Когда функция завершается
фрейм просто удаляется. Никакого GC, никаких аллокаций.

Выделение памяти на stack, это сдвиг одного указателя. Одна инструкция процессора. Быстрее не бывает

#### Схема стека вызовов (растёт снизу вверх, текущий фрейм внизу):
- main()
- handler()
- process()
- sum(a, b) <- текущий фрейм

#### Особенности Stack:
1. Своя для каждой горутины
2. 2–8 KB -> до 1 GB
3. LIFO, автоочистка
4. Аллокация = сдвиг указателя

```go
func sum(a, b int) int {
    result := a + b // result на stack
    return result   // фрейм удаляется при выходе
}
```

---

### HEAP: ГИБКИЙ, НО ДОРОГОЙ
Heap, это общая память для всех горутин. Сюда попадают объекты, которые должны жить дольше одной функции.
Выделение в heap дороже: нужно найти свободный блок нужного размера, обновить метаданные аллокатора. А потом GC должен найти и удалить объект, когда он станет не нужен.
Каждый объект в heap, это работа для GC. Много объектов, GC работает чаще, больше CPU тратится не на твой код.

В Go нельзя явно выбрать stack или heap. Компилятор решает сам через escape analysis

#### Схема кучи и особенности Heap:
Блоки памяти в Heap: [ мусор ], [ используется ], [ мусор ], [ мусор ], [ используется ], [ мусор ], [ используется ] -> GC находит и удаляет мусор
1. Общий для всех горутин
2. Нужен GC для очистки
3. Аллокация = поиск свободного блока
4. Указатели, интерфейсы, замыкания

```go
func newUser() *User {
    u := User{Name: "Niyaz"} // убегает в heap
    return &u                // указатель живёт дольше функции
}
```

### КЛЮЧЕВЫЕ ОТЛИЧИЯ

- Скорость аллокации:
  - STACK: 1 инструкция CPU
  - HEAP: поиск свободного блока
- Очистка:
  - STACK: автоматическая при выходе из функции
  - HEAP: Garbage Collector
- Видимость:
  - STACK: только текущая горутина
  - HEAP: все горутины
- Размер:
  - STACK: 2 KB -> 1 GB на горутину
  - HEAP: ограничен RAM
- Что хранит:
  - STACK: локальные переменные, аргументы
  - HEAP: объекты, которые "убегают"
- Стоимость:
  - STACK: бесплатно
  - HEAP: CPU на GC

Простое правило: если переменная не покидает функцию, она на stack. Если убегает наружу (через указатель, интерфейс, замыкание), она в heap

### КОГДА ЧТО ИСПОЛЬЗОВАТЬ
Go решает за тебя, но ты можешь влиять на решение.

#### Помогаешь stack:
1. Возвращай значение вместо указателя для маленьких структур
2. Передавай конкретные типы вместо interface{}
3. Избегай замыканий в горячих циклах
4. Заранее аллоцируй слайсы через make([]T, 0, cap)

#### Помогаешь heap (когда он нужен):
1. Большие структуры, которые дорого копировать
2. Объекты, которые шарятся между горутинами
3. sync.Pool для переиспользования частых аллокаций

```bash
Проверяй: go build -gcflags='-m' покажет что куда уходит
```
