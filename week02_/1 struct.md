### Custom Type

Через type создавать собственные, кастомные типы на основе примитивного, базового.

```go
type OurString string

var customStr OurString
fmt.Printf("%T %#v \n", customStr, customStr) // тип OurString и значение "" (zero value for string (as base type))
customStr = "What is up?" // OurString, What is up?

// %v  - {Vasya 28}
// %#v - main.Person{Name:"Vasya", Age:28}
```

Прячем string за кастомным типом.
При присвоении значения используем базовый тип.

Создание через короткий синтаксис:

```go
// Нужно явное приведение базового типа к кастомному, иначе Go сам выберет дефолтный тип.
customStr := OutString("wow nice")
noCustomStr := "wow nice" // просто string

// Кастомный тип может быть приведён обратно к своему базовому.
fmt.Println(string(customStr))
```

### struct

struct - тип. Основной способ группировать связанные данные. Заменяют классы из других языков, при этом работают через композицию.

Структура - шаблон с набором переменных, объединённых логическим смыслом. Набор полей.

Хочу создать группу людей. Вместо создания по каждого набор переменных, создать шаблон Человек со всеми его свойствами.

Для создания нового человека - заполнить структуру, как форму по шаблону.

Хранить несколько логически связанных значений внутри 1 переменной.

```go
// Объявление структуры:
type Person struct { // Person - название моего типа. тип данных - структура Person
    Name string
    Surname string
    Age int
}

// Инициализация структуры:

// объект структуры
vasya := Person{
    Name: "Vasya",
    Surname: "Dex",
    Age: 28,
}
// {} - функция IDE - fill all fields - заполнит zero values

// Просто перечисление без полей, с обязательным сохранением порядка
dima := Person{"Dima", "Molot", 12}

// Инициализация с zero values
var Jonh Person
Jonh := Person{}
```

В полном объявлении для vasya, поля можно указывать не по порядку или пропустить.
Для dima - нет.

### Method

Метод - функция, у которой есть приёмник (получатель). Через методы описывать поведение стркутуры.

Человек - не просто набор свойств. У него есть действия.

Методы - поведение для структуры. Те же функции, с отличием, что они привязаны к определённой структуре и имеют доступ к её полям (свойствам).

```go
func (k kelven) celsius() celsius
```

- func          } ключевое слово
- k - название  } -|
            |-> } приёмник
- kelvin - тип  } -|
- celsius()     } название метода
- celsius - тип } реузльтат

Чтобы превраить функция в метод - перед её названием указать в () к какой структуре она относится.

```go
func (p Person) Talk() { // указвыем тип структуры
    fmt.Println("Hello, my name is", p.Name)
}

// Расширили поведение структуры. На объектах появится новое поведение
vasya.Talk()
```

### Pointer

Указатель - адрес проживания переменной в памяти компьютера, где хранится информация о её типе, названии и значении.

Обращясь к переменной компьютер смотрит по какому адресу хранится переменная, идёт туда и достёт, что в ней лежит.

Чтобы сохранить адрес переменной в другую переменную (будет хранить адрес), нужно использовать тип данных указетль:

```go
var foo int = 23

// Где конкретно хранится переменная foo
pointerFoo := &foo // адрес. тип данных не int, а *int - указатель на int
fmt.Println(pointerFoo) // 0xc00357f346
```

Адрес переменной - число, указывает на первый байт переменной.

```go
Имена переменных | Адреса ячеек | Ячейки памяти
X                ->  00153      |   9       }
Y                ->  00154      | -13       } Значения переменных
Sum              ->  00155      |  -4       }
                 ->  00156      |
```

0x - говорит, что число написано 16 сс.

Знаем адрес проживания переменной - можем посмотреть что в ней находится. Операция разименованием указателя:

```go
fmt.Println(*pointerFoo) // 23. *адрес_переменной
*pointerFoo = 10 // изменить то что лежит по этому адресу
fmt.Println(foo) // 10, а не 23. pointerFoo и foo ссылаются на один участок памяти.
```

При изменении в foo или *pointerFoo, другая тоже изменится - обращение к одному участку в памяти.

```go
                Адресс ячеек в памяти
                        0004
num = 4     }  |        0008
pNum = &num }  |------- 000C
                        0010
                        0014
```

Кажется, что проще сделать так:

```go
foo = 15
```

Но это не всегда получится.

```go
func main() {
    a := 4
    println(&a) // 0x...730
    println(a) // 4
    squareVal(a)
    println(a) // 4, не 16
}

func squareVal(value int) {
    println(&value) // 0x...728. Они в разных участках памяти
    square := value * value
    value = square
}
```

Переменные ограничены областью видимости {} в которых они объявлены - в данном случае main(). Переменная за пределами функции main() недоступна.
Также как переменная value недоступна за пределами функции squareVal()

В функцию передаётся копия переменной `a`, а не сама переменная - не можем выходить за пределы фукнции. Безопасно, но не очень эффективно.

Чтобы не делали с переменной `value` - не будет влиять на `a` - у них разные участки памяти.

Чтобы работать напрямую с переменной `a`, функция должна принимать не просто параметр int, а *int (указатель на тип данных int):

```go
// измени значение по такому-то адресу
func squareAdd(pointer *int) { // принимаем адрес переменной, не значение
    println(pointer) // 0x...730
    sqr := *pointer * *pointer
    *pointer = sqr
}

func main() {
    println(&a) // 0x...730
    squareVal(&a) // передаём не саму переменную, а её адрес
    println(a) // 16
}
```

Сможем достучаться по адресу, который лежит внутри переменной `a` - `pointer` и `a` ссылаются на один адрес.

Теперь когда мы разименуем указатель `pointer` и изменим значение лежащее по нему, переменная `a` также изменится.

Кажется, что проще сделать так:

```go
func main() {
    a := 4
    a = Square(a) // 16
}

func Square(x int) (sqr int) {
    sqr = x * x
    return sqr
}

func squareAdd(p *int) {
    sqr := *p * *p
    *p = sqr
}
```

В данном, простом случае это лучше, чем мучиться с указателями.
НО, что если функция будет принимать не просто x int, а что-по сложнее и больше, например структуру (храняющую очень много инфы), подгруженную из БД.
Заново её копировать очень трудоёмкий и не эффективный процесс. Придётся выделять ещё раз много памяти под эту структуру, которая уже где-то хранится.
В этом случае использовать указатели, чтобы не прибегать к копированию.

При работе с обычными переменными указатели излишни, просто принимай, копируй, и возвращяй значения.

### Опасная ошибка backend-разработчика

Работая с памятью и указателями, при неправильном использовании программа может упасть.

```go
func main() {
    var pointer *int // nil pointer - указатель никуда не указывает. нет переменной на которую он ссылается.
    // pointer = nil // аналогично
    println(*pointer) // !!!
}
```

Попытка разименовать nil pointer и посмотреть что лежит по этому адресу - будет panic. Программа полностью упадёт, завершиться аварийно.
Если у меня 1 сервер - приложение полностью упадёт, клиенты не смогут им пользоваться.


В Go всё передаётся по значению. Если функция должна менять данные структуры - передавай указатель.

```go
func AddYear(u *User) {
    u.Age++
}
```

& - амперсант

```go
func (p Persin) IncAge() {
    println(&p)
    p.Age++
}

vasya.IncAge()
println(&vasya)
```

Возраст не поменялся. Указатели и адреса памяти.
Через & посмотреть где находятся переменные. &p и &vasya - ссылаются на разные участки памяти.

```go
type ReceiverType struct {
    Field FieldType
}

// copy - RecieverType
func (r RecieverType) methodName() {
    r.Field = ModifiedValue // mutate copied object's field
}

// memory address - *RecieverType
func (r *RecieverType) methodName() {
    r.Field = ModifiedValue // mutate original object's field
}
```

Если метод меняет поля структуры, используй указатель в приёмнике:

```go
func (p *Person) IncAge() {
    println(p) // убираем &, т.к. p - уже указатель на структуру.
    p.Age++
}

vasya.IncAge() // +1
println(&vasya)
```

Теперь p (*Person) и &vasya - ссылаются на один участок памяти.

### Композиция вместо наследования

Go не использует наследование в классическом смысле. Вместо этого структура может "встраивать" другую, наследуя её поля и методы.

Встраивать - когда встраиваем поведение, либо свойства какого-то типа в опредленённое поле структуры.

Встраивание работает со структурами.

Выбирая тип для встраивания, расширяем поведение основого типа куда хотим встроить некий новый тип.

Это не наследование. При наследование, наследуемый тип получает свойства и методы родителя, расширяя своё поведение.
Наследуемый тип является подтипом своего родителя (имеет его тип).
Тип B является подтипом A. Отношщение: is

Встраивание работает по принципу композиции.
При композиции тип A содержит B.
Можешь расширить поведение типа А, за счёт встраивания типа В, но тип А не будет являеться типом В. Отношение: has

#### Паттерн компановщик

Компоновщик — это структурный паттерн проектирования, который позволяет сгруппировать множество объектов в древовидную структуру, а затем работать с ней так, как будто это единичный объект.

Паттерн Компоновщик имеет смысл только тогда, когда основная модель вашей программы может быть структурирована в виде дерева.

Например, есть два объекта: Продукт и Коробка. Коробка может содержать несколько Продуктов и других Коробок поменьше. Те, в свою очередь, тоже содержат либо Продукты, либо Коробки и так далее.

Теперь предположим, ваши Продукты и Коробки могут быть частью заказов. Каждый заказ может содержать как простые Продукты без упаковки, так и составные Коробки. Ваша задача состоит в том, чтобы узнать цену всего заказа.

Заказ может состоять из различных продуктов, упакованных в собственные коробки.

Если решать задачу в лоб, то вам потребуется открыть все коробки заказа, перебрать все продукты и посчитать их суммарную стоимость. Но это слишком хлопотно, так как типы коробок и их содержимое могут быть вам неизвестны. Кроме того, наперёд неизвестно и количество уровней вложенности коробок, поэтому перебрать коробки простым циклом не выйдет.

Компоновщик предлагает рассматривать Продукт и Коробку через единый интерфейс с общим методом получения стоимости.

Продукт просто вернёт свою цену. Коробка спросит цену каждого предмета внутри себя и вернёт сумму результатов. Если одним из внутренних предметов окажется коробка поменьше, она тоже будет перебирать своё содержимое, и так далее, пока не будут посчитаны все составные части.

Компоновщик рекурсивно запускает действие по всем элементам дерева — от корня к листьям.

Для вас, клиента, главное, что теперь не нужно ничего знать о структуре заказов. Вы вызываете метод получения цены, он возвращает цифру, а вы не тонете в горах картона и скотча.

Армии большинства государств могут быть представлены в виде перевёрнутых деревьев. На нижнем уровне у вас есть солдаты, затем взводы, затем полки, а затем целые армии. Приказы отдаются сверху и спускаются вниз по структуре командования, пока не доходят до конкретного солдата.

- Компонент определяет общий интерфейс для простых и составных компонентов дерева.
- Лист — это простой компонент дерева, не имеющий ответвлений.
Из-за того, что им некому больше передавать выполнение, классы листьев будут содержать большую часть полезного кода. Совершить операцию самостоятельно.
- Контейнер (или композит) — это составной компонент дерева. Он содержит набор дочерних компонентов, но ничего не знает об их типах. Это могут быть как простые компоненты-листья, так и другие компоненты-контейнеры. Но это не является проблемой, если все дочерние компоненты следуют единому интерфейсу.
Методы контейнера переадресуют основную работу своим дочерним компонентам, хотя и могут добавлять что-то своё к результату. Делегировать работу дочерним компонентам.
- Клиент работает с деревом через общий интерфейс компонентов.
Благодаря этому, клиенту не важно, что перед ним находится — простой или составной компонент дерева.


Компоновщик помогает реализовать вложенные геометрические фигуры.

Класс CompoundGraphic может содержать любое количество подфигур, включая такие же контейнеры, как он сам. Контейнер реализует те же методы, что и простые фигуры. Но, вместо непосредственного действия, он передаёт вызовы всем вложенным компонентам, используя рекурсию. Затем он как бы «суммирует» результаты всех вложенных фигур.

Клиентский код работает со всеми фигурами через общий интерфейс фигур и не знает, что перед ним — простая фигура или составная. Это позволяет клиентскому коду работать с деревьями объектов любой сложности, не привязываясь к конкретным классам объектов, формирующих дерево.


Применимость
 - Когда вам нужно представить древовидную структуру объектов.
 Паттерн Компоновщик предлагает хранить в составных объектах ссылки на другие простые или составные объекты. Те, в свою очередь, тоже могут хранить свои вложенные объекты и так далее. В итоге вы можете строить сложную древовидную структуру данных, используя всего две основные разновидности объектов.

 - Когда клиенты должны единообразно трактовать простые и составные объекты.
 Благодаря тому, что простые и составные объекты реализуют общий интерфейс, клиенту безразлично, с каким именно объектом ему предстоит работать.

 Шаги реализации
- Убедитесь, что вашу бизнес-логику можно представить как древовидную структуру. Попытайтесь разбить её на простые компоненты и контейнеры. Помните, что контейнеры могут содержать как простые компоненты, так и другие вложенные контейнеры.

- Создайте общий интерфейс компонентов, который объединит операции контейнеров и простых компонентов дерева. Интерфейс будет удачным, если вы сможете использовать его, чтобы взаимозаменять простые и составные компоненты без потери смысла.

- Создайте класс компонентов-листьев, не имеющих дальнейших ответвлений. Имейте в виду, что программа может содержать несколько таких классов.

- Создайте класс компонентов-контейнеров и добавьте в него массив для хранения ссылок на вложенные компоненты. Этот массив должен быть способен содержать как простые, так и составные компоненты, поэтому убедитесь, что он объявлен с типом интерфейса компонентов.
Реализуйте в контейнере методы интерфейса компонентов, помня о том, что контейнеры должны делегировать основную работу своим дочерним компонентам.

- Добавьте операции добавления и удаления дочерних компонентов в класс контейнеров.
методы добавления/удаления дочерних компонентов можно поместить и в интерфейс компонентов. Да, это нарушит принцип разделения интерфейса, так как реализации методов будут пустыми в компонентах-листьях. Но зато все компоненты дерева станут действительно одинаковыми для клиента.

 Преимущества и недостатки:

Компоновщик — это структурный паттерн, который позволяет создавать дерево объектов и работать с ним так же, как и с единичным объектом.

Компоновщик давно стал синонимом всех задач, связанных с построением дерева объектов. Все операции компоновщика основаны на рекурсии и «суммировании» результатов на ветвях дерева.

Давайте попробуем понять паттерн Компоновщик, используя для примера файловую систему ОС. Внутри нее есть два типа объектов: файлы и папки. В некоторых случаях они должны восприниматься как одно и то же. Здесь нам пригодится паттерн проектирования Компоновщик.

Представьте, что вам нужно провести поиск по конкретному ключевому слову в вашей файловой системе. Такая операция поиска применяется в равной степени и к файлам, и к папкам. В случае файла, она только проверит содержимое файла, а в случае папки – обработает все файлы этой папки для нахождения ключевого слова.

 component.go: Интерфейс компонента

```go
package main

type Component interface {
    search(string)
}
```

 folder.go: Компоновщик

```go
 package main

import "fmt"

type Folder struct {
    components []Component
    name       string
}

func (f *Folder) search(keyword string) {
    fmt.Printf("Serching recursively for keyword %s in folder %s\n", keyword, f.name)
    for _, composite := range f.components {
        composite.search(keyword)
    }
}

func (f *Folder) add(c Component) {
    f.components = append(f.components, c)
}
```

 file.go: Лист

```go
package main

import "fmt"

type File struct {
    name string
}

func (f *File) search(keyword string) {
    fmt.Printf("Searching for keyword %s in file %s\n", keyword, f.name)
}

func (f *File) getName() string {
    return f.name
}
```

main.go: Клиентский код

```go
package main

func main() {
    file1 := &File{name: "File1"}
    file2 := &File{name: "File2"}
    file3 := &File{name: "File3"}

    folder1 := &Folder{
        name: "Folder1",
    }

    folder1.add(file1)

    folder2 := &Folder{
        name: "Folder2",
    }
    folder2.add(file2)
    folder2.add(file3)
    folder2.add(folder1)

    folder2.search("rose")
}
```

#### Shadowing

При указании имени поля, компилятор начинает проверять его наличия начиная от корня типа WoodBuilder, углублясь дальше во вложенные типы.

```go
builder.printName() // Annie
```

Что если в WoodBuild тоже добавить собсвтенное поле Name:

```go
type WoodBuilder struct {
    Person
    Name string
}

builder := WoodBuilder{Person{Name: "Annie", Age: 41}, "Bob"}

builder.Person.Name // Annie
builder.Name // Bob
builder.printName() // Annie, несмотря на shadowing. Вызов для внутренней структуры Person, метод есть только у неё.
```

При встраивании типов можем столкнуться с:
Shadowing - когда свойство находится ближе к корню (WoodBuilder) (меньшей углублённости, чем другие), оно затемняет более глубокие свойства.
Компилятор начал с корня структуры и сразу нашёл Name, ему не нужно дальше идти внутрь.

Метод printName также ищется от корня структуры вглубь.

Можем переопределить такой же метод на уровне WoodBuilder:

```go
func (wb WoodBuilder) printName() {
    fmt.Println(wb.Name)
}

builder.PrintName() // Bob
builder.Person.PrintName() // Annie
```

#### Colliding

Получение свойства/метода находящегося на одинаковой вложенности.

```go
type WorkExperience struct {
    Name string
    Age int
}

type WoodBuilder struct {
    Person
    Name string
    WorkExperience
}
builder := WoodBuilder{Person{"annie", 20}, "Jonh", WorkExperience{"bank", 2}}

builder.Age // коллизия. Компилятор не понимает какое свойство достать

// Единственное решение - полный путь
builder.Person.Age
builder.WorkExperience.Age
```

### Use-case встраивания

- Отсутствие дублирования. Чтобы не копировать какие-то поля или методы, можем встроить тип в другой.
- Писать более масштабируемый и поддерживаемый код за счёт композиции:

```go
// Могут быть разные строители, работают с разными материалами.
type Builder interface {
    Build() // сигнатура метода интерфейса. определяет контракт (что тип должен уметь делать)
}

type Building struct {
    Builder // Принимает значение интерфейсного типа Builder, не важно какое
    Name string
}

// Реализации интерфейса:
type WoodBuilder struct {
    Person
}

func (wb WoodBuilder) Build() {
    fmt.Println("Building wood house")
}

type BrickBuilder struct {
    Person
}

func (bb BrickBuilder) Build() {
    fmt.Println("Building brick house")
}

func usecase() {
    woodenBuilding := Building{
        Builder: WoodBuilder{Person{
            "Vasya",
            40,
        }},
        Name: "Wood cottage",
    }
    woodenBuilding.Build() // Building wood house

    brickBuilding := Building{
        Builder: BrickBuilder{Person{
            "Allison",
            54,
        }},
        Name: "Brick cottage",
    }
    brickBuilding.Build() // Building brick house
}
```
Нужно построить дом из дерева. Можно написать отдельный код для работы только с деревянными домами. Для металла, также отдельный код.
Но правильное использование компаозиции делает код более расширяемым.

Здание принимает строителя любого типа.
В коде здание одно, строителей несколько.
Реализовали один тип здания, но его могут строить разные типы строителей (работающие с разными материалами).

Суть композиции - сделать работу структуры гибкой. Основную работу делегировать встраивоемому типу.
Строителям делегировали работу, достаточно реализовать у каждого типа строителя метод Build(), чтобы построить новый тип здания.


Элементы внутри блока interface называются методами (method specifications), описывают поведение, привязанное к конкретному типу-получателю, который реализует этот интерфейс.

Снаружи без приёмника: Если бы func Build() была объявлена сама по себе вне структуры и интерфейса, тогда это была бы обычная функция.


Расширяемость кода:
Пришло требование строить монолитные дома. Вместо написания новой реализации типа здания, просто добавить новый тип строителя, реализовать ему метод Build().
Просто создадим здание и ему передадим нового строителя. Кода самого здания касаться не нужно.
Отдельно работаем именно со строителями.
Код получается масштабируемым. Строителей можно создать сколько угодно, следовательно и домов.

Поддерживаемость:
При поиске багов, нужно будет проверить конкретного строителя, не нужно рассматривать весь код по работе с домом.


В Go интерфейсы реализуются неявно (концепция «утиной типизации» на этапе компиляции).
WoodBuilder автоматически считается реализацией интерфейса Builder, потому что у него есть метод Build() с точно такой же сигнатурой (названием, параметрами и возвращаемыми значениями).
Компилятор сам проверяет совпадение сигнатур методов.

Все методы должны совпадать: Если бы в интерфейсе Builder было два метода (Build() и Destroy()), то для реализации интерфейса структуре WoodBuilder пришлось бы объявить оба.

встроили Person в WoodBuilder, все методы Person тоже стали методами WoodBuilder и учитываются при проверке интерфейсов. (Person сам по себе ничего никому не должен и не обязан реализовывать этот интерфейс. Компилятор просто складывает методы в общую «копилку»:
• Общий набор методов: WoodBuilder автоматически «наследует» (продвигает) все методы встроенного Person и объединяет их со своими собственными.
• Проверка интерфейса: При проверке соответствия интерфейсу Go смотрит на итоговый список всех доступных методов у WoodBuilder (своих + полученных от Person).
• Переопределение: Если у WoodBuilder и у Person есть метод с одинаковым именем, сработает собственный метод WoodBuilder.)

передать объект WoodBuilder в любую функцию, которая ожидает на вход интерфейс Builder.
