map - хэш-таблица Go: пары "ключ -> значение".

map:
- не гарантирует порядок
- может расширяться
- создаётся через make, иначе panic

```go
m := make(map[string]int)
m["age"] = 25
m["age"] // 25
```

Ошибки:
- var m map[string]int без make -> panice при записи
- использование вложенных map без инициализации
- append по слайсу, который используют два пакета одновременно
- изменение underlying array через другой slice


map в реальных сервисах:
- соц. сети. ключ: userID -> значение: профиль пользователя
- интернет магазин. ключ: товарID -> значение: описание товара
- система авторизации. ключ: sessionID -> значение: данные сесии


### Internals (classic/old version)

bucket - блок на 8 элементов (до 1.24)
overflow - доп. bucket при переполнении
tophash - верхний байт хэша в старой map
control byte - 7-bit отпечаток (h_2) в новой map
tombstone - маркер удалённого элемента
group of 8 - единаци хранения (новая map)

map в Go — встроенная hash table. O(1) среднее на вставку, поиск, удаление. Любой comparable тип в качестве ключа: int, string, struct без слайсов и map внутри

Под капотом массив "корзин" (buckets). Хеш-функция распределяет ключи по корзинам. Идеальная структура для случайного доступа по ключу

Что важно сразу:
- range дает разный порядок каждый раз (намеренно)
- nil-map можно читать (получишь zero value), писать — паника
- map не thread-safe, конкурентная запись = паника
- map передается по reference, под капотом указатель

С Go 1.24 (февраль 2025) реализация map переписана на Swiss tables.
Классическую версию спрашивают на собесах, разберём её ниже:

#### Структура под капотом

1) HMAP - header:
- count - of elements
- B - log2 buckets numbers (2^B buckets)
- buckets - pointer to buckets array
- oldbuckets - pointer to old array during the growth

2) BMAP (Bucket) - to 8 key-val pairs:
- tophas[8] - 8 hash bit on top for each slot
- keys[8]
- values[8]
- overflow - pointer to next bucket in chain

3) Hash-function returns 64-bit hash. From it:
- low B bit - bucket index in array
- top 8 bit - tophash for fast comparing insdie bucket

When 8 buckets sloats are full - overflow bucket is added. It turn out to Chain.

#### Get and Put

1) Get(key):
- calculate hash(key)
- low B bit -> bucket index
- top 8 bit -> required tophash
- Going by bucket slowt: compare tophash with tophash[i]
- if tophash correct - compare keys (full equlness)
- if not - go in overflow and repeat
- if come to an end of chain without required result - return zero value

2) Put(key, value):
- Same steps, finding existing key or first empty slot
- if there is not empty in bucket + overflow - allocate new overflow bucket
- if load factor > 6.5 - grow is starting

Why tophash needed:
compare 1 byte faster than 16-byte string or complex struct. Tophash - fast filter before full keys comparing.

#### Growth and Evacuation

Conditions for growth:
- Load factor > 6.5 (average bucket fill) - double grow, size doubles
- too many overflow buckets with low load factor - same-size grow, reorganisation without increase.

Why is Incrimental:
- evacuation is incrimental. By grow array isn't moving fully by 1 shot. On each operatino (Get/Put) 1-2 old buckets moving to new array
- grow on map with million elements by 1 show occures pause in tens millisec. With Incrimental - load is spread.

During the grow:
1) oldbuckets point to an old array
2) buckets - on new
3) Reading checks both, writing writes to new
When all is evacuated, oldbuckets are being released. Garbage collector takes old memory

#### Underwater stones
- range gives random order: on start range choose random start bucket. Don't write code, that rely on keys oreder
- Parallel writing - panic:
    - map aren't thread-safe. concurrent map writes -> fatal error
    - For concurent accsess: sync.RWMutes over map or sync.Map
- Nil-Map:
    - var m map[string]int - m = nil. Read/range work(zero value). Write - panic
    - Always init through make or literal
- Pointer to value is not allow:
    - &m[k] - not compilable. Bucket can move in case of grow, pointer would be invalid
    - Need pointer - store pointer itself like map values
- Size during init: make(map[K]V, hint) - reserve place for N elements. On big map applies put speed in times by absence series of grow.




### Устройство map (старая реализация)

Базовый принцип:
ключ -> хэш-функция hash() -> число (хэш) -> хэш-таблица (массив bucket'ов) | бакет/группа -> слот [key, value]

Бакет из 3 массивов:
- tophash[8]
- keys[8]
- values[8]

Алогритм:
хэш прогоняется через хэш функцию, получается число
это число указывает на бакет в хэш-таблице
внутри бакета могло находиться до 8 элементов - массив ключей, массив значений и массив маленьких кусочков хэша (top hash)
дальше по этому бакету идёт поиск и вставка.
если ключей оказалось слишком много, то создаётся overflow bucket

Хэш-функция - получает ключ и превращает его в число


key := "String"
hash := hash(key) = 1234567890
Один и тот же ключи -> всегда одинаковый хэш

Коллизия - разные ключи дают одинаковый хэш.

Как по полученному хэшу найти bucket?

bucket - коробка для хранения ключей и значений.

Чтобы понять в какой bucket положить элемент:
bucket_index = hash % 8 // 2

Остатоком от деления будет номер bucket

Формально:
index = hash & ((1<<B)-1)
число bucket'ов всегда степень двойки (2^B).

Способы борьбы с коллизиями:
1) Открытая адресация - поиск след. свободного места.
2) Цепочки (chaining) - в одной ячейке храним список с несколькими элементами.
3) Доп. хэш. Повторный прогон получившегося хэша через хэш-функцию - получается другое число.

До 1.24 использовался метод цепочек, то есть buckets.

Один bucket хранит до 8 элементов и состоит из трёх массивов:
- tophash (маленькие кусочки хэша)
- keys
- values

По tophash сначала отбирали кандидатов, потом сравнивали сами ключи.

Вставка нового элемента в map:

hash(key) -> hash -> bucket со свободным слотом / заполненный

Если в bucket есть свободный слот, помеченный пустым (в том числе после delete), он будет переиспользован

В массиве tophash записывается верхний байт хэша ключа. Используется как быстрый фильтр при поиске.

У каждого слота в bucket есть tophash - это верхний байт хэша ключа. Нужен, чтобы быстрее находить кандидатов при поиске.

Если бакет заполенен - создаётся overflow bucket и новый элемент кладётся туда.

Так в старой реализации могла появится целая цепочка bucket.
overflow bucket решают проблему переполнения. Но поиск и вставка становятся медленние, потому что нужно проходить по цепочке.

Поиск элемента:
Берём элемент, считаем хэш, находим bucket.
В bucket смотрим на массив tophash, если совпал - проверяем ключи, если нашли - возвращяем значение.
Если tophash не совпал, то пропускаем слот без проверки ключа. Может быть что tophash совпал, но ключи разные.
hash(number) -> Bucket с совпавшим tophash -> Сравнить реалиный ключ -> Overflow, если в основном не нашли - идём дальше.

Удаление элемента:
Удаление = помечаем слот пустым. Ключ и значение считаются стёртыми, но слот остаётся в bucket.
Таких дыр могло становится много, особенно в overflow bucket, это замедляло поиск - нужно обходить слоты, даже пустые.
Память занята, а пользы от неё нет.


Poct (grow) и load factor
Когда map заполнялась, Go создавал новую таблицу в 2 раза больше и перекидывал туда элементы.

Решение по росту принималось в 2 условиях:
- если в среднем в каждом bucket больше 6.5 элементов.
- если overflow-bucket примерно столько, сколько основных.

В обоих случаях Go запускал рост: создавал новую таблицу и перекидывал туда все ключи.
Для больших map была дорогостоющая операция по времени и памяти.

Копирование bucket постепенное, во время след. операций, а не сразу моментальное.

***************

Если overflow-bucket примерно столько же, сколько основных бакетов

Новая таблица (16 bucket)

Когда таблица становится слишком плотной или overflow-bucket слишком много - запускается рост и ключи пересыпаются в новую таблицу.

Проблеым старой реализации:
- Слишком много сравнений ключей. Частые проверки реальный ключей нагружает CPU и замедляют поиск.
- Overflow-bucket плохо работали с памятью. Цепочки overflow -> плохая локальность. Данные лежат далеко друг от друга - большое пропусков кеша и лишних шагов.
- Удаление оставляло мусор. Пустые/удалённые слоты копятся и ухужщшают поиск и память
- Рост x2 map имел дорогую пересыпку, нужно было перекидывать все элементы. Резкое удвоение таблицы создаёт пиковые задержки и расход памяти.

### Поэтому в 1.24 разработчики решили переписать map.

Теперь под капотом архитектура Swiss Table.
Вместо overflow bucket цепочек, данные хранятся по группам по 8 слотов (Group of 8). Каждый слот описывается control byte = h_2(7 bit отпечатка). Позволяют очень быстро отобрать кандидатов.

Внутренние устройство:
- Когда вставляем или ищем элемент Go вычисляет hash(key) - это 64-битное число.

Группы заменили цепочки overflow


- 64-битный Хэш, делится на две части = h_1 + h_2:

h1(57 бит) - выбор группы
Вибрает группу (Group of 8). Группа - набор из 8 слотов.

h2(7 бит) - быстрый фильтрфильт кандидатов
Маленький отпечаток, хранится в control bytes. Нужен, чтобы понять, есть ли такой элемент в этой группе.

В старой map, сравнивали tophash для каждого слота отдельно. Теперь Go может сравнить h2 всех 8 слотов за 1 операцию.
Если h2 совпадает хоты-бы в одном слоте, только тогда проверяется ключ.

Если группа переполнена, то переходим к следующему. Но без overflow цепочек

- Группа - основная единица хранения.

map состоит из групп, по 8 элементов каждая.

У каждой группы есть 8 контрольных байт, показывают, что находится в каждом слоте. Описывают состояние 8 слотов.
(пустой, удалённый или занятый слот)
-------------------------------------
Group of 8
-------------------------------------
Contol bytes
h2 empty h2 deleted empty h2 empty h2
-------------------------------------
Слоты (key, value)
-------------------------------------

Вместо overflow - последовательное probing по группам.

Contol bytes и слоты, находятся в одной структуре - поиск и вставка работают быстрее.
Всё что нужно попадает в хэш-процессоры.


#### Поиск элемента в новой map

1) Берём ключ userID = 42
2) Прогоняем ключ через хэш-функцию. hash(userID)
3) Получаем большое число - 64-битный хэш.
4) Делим это число на 2 части:
- h1 (57 bit) - показывает в какой блок памяти (группу) нам нужно идти
- h2 (7 bit) - маленький отпечаток, по которому Go проверяет, есть ли нужный элемент в этом слоте.
h2 -> Group of 8 (Сравнение с отпечатками (h2)).
Go сразу проверяет все 8 маленьких отпечатков.
Если хотя-бы один совпал, то Go идёт проверять ключ.

Благодаря этому поиск стал быстрее.

Большенство кандидатов отсеиваются до того как мы проверяем реальные ключи.


#### Вставка нового элемента в новой map

newUserID = 77
hash(newUserID) = большое число

Первая часть хэша - в какую группу пойдём
Вторая - маленький отпечток

Го заходит в выбранную группу и проверяет есть ли свободное место.
Ячейка может быть либо пустая, либо где раньше был удалённый элемент.

Если место есть, Go вставляет ключ и значение, а в верхний ряд записывает этот отпечаток.

Если вся группа заполнена, алгоритм просто переходит к след. группе.

#### Удаление элемента в новой map

Когда удаляем ключ - Go не стирает его полностью, а ставит туда спец. маркер - Tombstone.
Маркер нужен, чтобы map не потеряла логику поиска. Временная метка - сохраняет цепочку поиска и позволяет переиспользовать слот позже.

Если слот стал бы просто пустым, Go мог бы ошибочно считать, что такого ключа нет и перестал бы искать дальше по цепочке.

Решение помогает работать map эффективнее.


#### Рост стал локальным

В старой map рост был тоже постепенным, Go переносил элементы частями (inctemental evacuation), но со временем всё равно приходилось пересывать всю map, переносить все bickets целиком.

В новой реализации рост умнее:
map делится на под-таблицы. Когда переполняет только, одна из них - Go делит только её. Рост стал локальным, а значит стабильным (производительнсоть не падает при росте размера) и менее затратным по памяти.

Снижает нагрузку.

#### Улучшения новой map. Что стало быстрее

1) Поиск
SIMD-сравнение 8 байт -> меньше проверок ключей
Раньше по 1 слота за раз.
Теперь все 8 слотов проверяются одновременно, меньше проверок ключей.
Прирост +30-40% в операциях поиска.

1) Вставка
Равномерное распределение. Overflow-bucket исчезли, вставка стала равномерной без Overflow-цепочек и предсказуемой по времени.

1) Память и лучше кэш-локальность CPU
Контрольные байты + данные рядом -> кэш L1
Все данные группы лежат рядом. Процессор чаще попадает в кэш и операция выполняется быстрее.

1) Предсказщуемый рост без пиков
