как работает отложенный вызов, где он реально спасает код и на чём чаще всего ошибаются

### DEFER В GOLANG
КАК РАБОТАЕТ, КОГДА ВЫПОЛНЯЕТСЯ И ГДЕ ПРИМЕНЯТЬ

#### Визуальная схема (железнодорожная стрелка DEFER):
- Выполнение функции -> Основной поток кода -> переключатель DEFER -> Отложенные функции (DEFER) -> Выполнение DEFER

#### Этапы работы:
1. ФУНКЦИЯ НАЧИНАЕТСЯ -> 2. DEFER РЕГИСТРИРУЕТСЯ -> 3. ОСНОВНОЙ КОД ВЫПОЛНЯЕТСЯ -> 4. ФУНКЦИЯ ЗАВЕРШАЕТСЯ (return или panic) -> 5. DEFER ВЫПОЛНЯЮТСЯ В ОБРАТНОМ ПОРЯДКЕ (LIFO) -> 6. УПРАВЛЕНИЕ ВОЗВРАЩАЕТСЯ НАРУЖУ

#### ГДЕ ИСПОЛЬЗОВАТЬ DEFER:
- Закрытие файлов
- Освобождение блокировок
- Закрытие соединений
- Закрытие HTTP-ответов
- Очистка ресурсов и кэша

закрыли файл в конце.

defer file.Close()

при работе с os.File, mutex, http.Response.Body, sql.Rows, при cleanup, логировании, снятии блокировок, работе с паникой и восстановлении после неё. тема упирается в жизненный цикл функции, порядок выполнения и аккуратное управление ресурсами.

defer в Go это отложенный вызов функции.

defer fmt.Println("done")

Go не выполняет этот вызов сразу. Он откладывает его до момента выхода из текущей функции.

defer = выполнить этот вызов перед выходом из функции

Самое важное слово здесь — именно перед выходом из функции.

Не когда-нибудь потом, не в конце блока, не после return в глобальном смысле. А ровно в момент, когда текущая функция завершает свою жизнь.

```go
package main
import "fmt"
func main() {
fmt.Println("start")
defer fmt.Println("deferred")
fmt.Println("end")
}

start
end
deferred
```

Выполняется fmt.Println("start")
Go видит defer fmt.Println("deferred") и ставит этот вызов в стек отложенных вызовов
Выполняется fmt.Println("end")
Функция main завершает выполнение
Только теперь Go запускает отложенный вызов
Зачем defer вообще нужен

Чаще всего затем, чтобы гарантированно выполнить cleanup:

закрыть файл
снять блокировку mutex
закрыть http.Response.Body
закрыть sql.Rows
освободить ресурсы
выполнить финальный лог
поймать panic через recover()

defer полезен, где действие выполнить в конце функции независимо от того, по какому пути она завершится.

### Почему defer любят в Go-коде
Потому что хороший defer держит рядом две вещи, которые по смыслу должны быть рядом:

захват ресурса
его освобождение
Например, без defer:

```go
f, err := os.Open("data.txt")
if err != nil {
return err
}
// работа с файлом
err = f.Close()
if err != nil {
return err
}
```

при появлении новых return, веток или ошибок cleanup начинает расползаться по функции. На маленьком примере это ещё не страшно. На живом коде очень быстро появляются ситуации, где один путь закрытие делает, а другой уже нет.

С defer чище:

```go
f, err := os.Open("data.txt")
if err != nil {
return err
}
defer f.Close()
// работа с файлом
```

Полезная ментальная модель
На defer удобно смотреть так: как только получил ресурс, сразу зафиксируй, как его правильно отпустить.

не потом не забуду закрыть, а сразу привяжи cleanup к точке, где ресурс был захвачен.

Это Go-шный стиль мышления. Он делает код не только короче, но и прозрачнее: видно, что у объекта есть жизненный цикл, и видно, где этот жизненный цикл заканчивается.

### без defer / с defer

#### без defer
- Вызывается Open() -> ветвление на 3 условия (!, x, ?) -> в каждой ветке свой return
- Close() остаётся недостижимым внизу (только из первой ветки идёт пунктир к Close())
- cleanup легко забыть

#### с defer
- Вызывается Open(), сразу рядом регистрируется defer Close() -> ветвление на 3 условия (!, x, ?) -> в каждой ветке return
- Из всех трёх return пути ведут обратно в defer Close()
- cleanup гарантирован

### Когда выполняется defer
Это первый вопрос, который надо прояснить до конца.

defer выполняется не сразу и не в момент, когда Go до него дошёл. Он выполняется при выходе из текущей функции.

Что значит “при выходе из функции”
Это может быть любой из вариантов:

функция дошла до конца
сработал return
случилась panic
Во всех этих сценариях отложенные вызовы всё равно будут запущены.

```go
package main
import "fmt"
func demo() {
defer fmt.Println("defer")
fmt.Println("before return")
return
}
func main() {
demo()
}

before return
defer
```

Defer относится к конкретной функции
Очень важный момент: defer привязан не к блоку if, не к циклу, не к switch и не к фигурным скобкам вообще. Он привязан именно к функции.

```go
func main() {
if true {
defer fmt.Println("inside if")
}
fmt.Println("main body")
}

main body
inside if
```

defer, объявленный внутри if, всё равно выполнится только при выходе из main.

Самая частая ошибка понимания
Новичок нередко воспринимает defer как «выполни в конце текущего логического куска».

Но в Golang логический кусок для defer — это не блок, а функция.

Именно поэтому defer так хорошо работает рядом с return, cleanup и panic, но именно поэтому он может оказаться опасным внутри циклов: отложенный вызов не исчезает после итерации, он ждёт конца всей функции.

До этой ловушки мы ещё отдельно дойдём.

Почему defer работает в обратном порядке: LIFO
Если в функции несколько defer, они выполняются в обратном порядке.

Это принцип LIFO: last in, first out. Последний добавленный отложенный вызов выполнится первым.

```go
package main
import "fmt"
func main() {
defer fmt.Println("first")
defer fmt.Println("second")
defer fmt.Println("third")
fmt.Println("body")
}

body
third
second
first
```

Представьте стек тарелок.

положили первую
сверху вторую
сверху третью
Снимать будете сначала верхнюю.

С defer та же логика: Go складывает отложенные вызовы в стек вызовов, и при завершении функции разворачивает их назад.

когда есть несколько связанных cleanup-действий:

lockA()
defer unlockA()
lockB()
defer unlockB()

При выходе из функции сначала снимется unlockB(), потом unlockA().

Это естественно и безопасно: ресурс освобождается в порядке, обратном захвату.

### Порядок выполнения defer (LIFO)

#### добавили:
1. defer 1
2. defer 2
3. defer 3

#### стек (снизу вверх):
- defer 3 (на вершине)
- defer 2
- defer 1 (на дне)

#### выполнилось:
3. defer 3 -> 2. defer 2 -> 1. defer 1

LIFO — последний -> первый


Несколько defer = обратный порядок выполнения

Defer и return: что выполняется раньше
Вот здесь у новичков очень часто каша.

Надо запомнить такую последовательность:
вычисляется return
выполняются defer
функция окончательно завершает работу

Но это объяснение пока слишком короткое.

```go
package main
import "fmt"
func test() int {
defer fmt.Println("defer")
return 10
}
func main() {
fmt.Println(test())
}

defer
10
```

Когда функция дошла до return 10, значение возврата уже определено. Но перед окончательным выходом из функции Go обязан выполнить все отложенные вызовы.

результат уже готов
функция ещё не завершена окончательно
defer успевает выполниться
после этого результат уходит наружу
Defer не отменяет return

defer не означает «вернуться попозже». Он означает «сначала выполни cleanup, потом уже окончательно выйди».

причина, почему defer так удобен для освобождения ресурсов и обработки ошибок.

шаблон мышления: Когда видите return, не думайте что функция уже закончилась.

В Go правильнее думать: return запускает завершение функции, а defer успевает выполниться в этом процессе

Аргументы defer вычисляются сразу
Это одна из самых неприятных ловушек темы.

Новичок часто думает так: раз вызов отложен, значит и аргументы будут вычислены потом.
Нет.

Аргументы defer вычисляются сразу в момент объявления defer, а не в момент выполнения отложенного вызова.

Пример с числом

```go
package main
import "fmt"
func main() {
x := 10
defer fmt.Println(x)
x = 20
}

10
```

Хотя x потом стал 20, в defer уже попало старое значение.

Когда Go видит:
defer fmt.Println(x)

он сразу вычисляет аргумент x и сохраняет его для будущего вызова. То есть откладывается сам вызов, но не момент вычисления его аргументов.

Где на этом реально ошибаются
На логах, на счётчиках, на диагностике ошибок и на временных переменных.

defer logDuration(startTime)

и не до конца понимает, что именно уже зафиксировано в аргументах, а что будет вычисляться позже. Именно поэтому в Go часто встречаются либо аккуратные вызовы с уже готовыми аргументами, либо анонимные функции, если нужно дочитать актуальное состояние в самом конце.

Как получить новое значение
Если нужно, чтобы defer увидел уже актуальное состояние переменной, часто используют анонимную функцию.

```go
package main
import "fmt"
func main() {
x := 10
defer func() {
fmt.Println(x)
}()
x = 20
}

20
```

Почему с анонимной функцией уже иначе
Потому что здесь в defer откладывается вызов анонимной функции, а внутри неё чтение x происходит уже позже, перед выходом из функции.

И вот тут появляется ещё одна важная тема: захват переменной.

Захват переменной и defer
Анонимная функция захватывает саму переменную, а не её старое значение на момент объявления.

Из-за этого поведение:

```go
defer fmt.Println(x)

и

defer func() {
fmt.Println(x)
}()
```

может сильно отличаться.

Это надо не просто запомнить, а реально руками прогнать.

### defer с аргументом / defer с анонимной функцией

#### defer с аргументом
1. x = 10 -> 10 (аргумент вычислился сразу)
2. x = 20
3. defer (использует 10)
Итог: результат 10

#### defer с анонимной функцией
1. x = 10
2. x = 20
3. f() defer (читает x сейчас) -> 20 (значение прочиталось позже)
Итог: результат 20

### Named return и как defer может менять результат
переходим к одной из самых интересных частей темы.

Если у функции есть именованные возвращаемые значения, defer может изменить то, что функция в итоге вернёт.

```go
package main
import "fmt"
func test() (result int) {
defer func() {
result++
}()
return 10
}
func main() {
fmt.Println(test())
}

11
```

Почему не 10
у функции есть именованный результат result
return 10 присваивает result = 10
перед окончательным выходом срабатывает defer
defer делает result++
наружу возвращается уже 11
Что такое named return простыми словами

Это когда возвращаемое значение имеет имя прямо в сигнатуре функции:

func test() (result int)
Тогда внутри функции переменная result реально существует и живёт до конца функции.

Такой приём иногда используют для:
аккуратной обработки ошибок
логирования результата
централизованной модификации возвращаемого значения
работы с panic и recover()

Но важно не переборщить.

Когда named return ухудшает читаемость
Если функция простая, именованные возвращаемые значения и хитрые defer-модификации могут только запутать.

такой код новичку читать тяжелее:

```go
func calc() (result int) {
defer func() { result++ }()
return 5
}
```

чем прямолинейный:

```go
func calc() int {
result := 5
result++
return result
}
```

named return — это не фича ради красоты, а инструмент, который надо использовать аккуратно.


Очень любят вопрос вида:

```go
func f() (x int) {
defer func() { x++ }()
return 1
}
```

И просят сказать, что вернёт функция.
Правильный ответ: 2.

### named return + defer

#### Схема этапов:
1. return 10 — функция готовится вернуть 10
2. named result = 10 — значение записывается в именованный result
3. defer меняет result — deferred-функция изменяет result на 11
4. итог 11 — наружу возвращается уже 11

Где defer реально нужен: Close, Unlock, cleanup
Вот тут начинается настоящий практический смысл golang defer.

Закрытие файла

```go
package main
import (
"os"
)
func readFile() error {
f, err := os.Open("data.txt")
if err != nil {
return err
}
defer f.Close()
// работа с файлом
return nil
}
```

Почему это хорошо:

файл открылся
сразу рядом написан cleanup
неважно, сколько дальше будет return, файл всё равно закроется

```go
Unlock mutex
mu.Lock()
defer mu.Unlock()
// критическая секция
```

Это очень частый паттерн в конкурентном коде.

Если не использовать defer, легко словить ситуацию, где функция выйдет раньше, а блокировка останется висеть.

Закрытие http.Response.Body

```go
resp, err := http.Get("https://example.com")
if err != nil {
return err
}
defer resp.Body.Close()
```

Это почти обязательный шаблон при работе с HTTP-клиентом.

Закрытие sql.Rows

```go
rows, err := db.Query("SELECT id FROM users")
if err != nil {
return err
}
defer rows.Close()
```

Если забыть про cleanup таких ресурсов, можно получить неприятные проблемы: зависшие соединения, утечки дескрипторов, рост нагрузки, трудноуловимые баги.

### Cleanup как стиль мышления
Одна из лучших привычек в Go выглядит так:

открыл ресурс -> сразу подумал, как он будет освобождён

И если освобождение должно произойти в конце функции, defer часто лучший первый кандидат.

Паттерн, который стоит унести в работу
В нормальном Go-коде часто хочется видеть такую последовательность:

захватили ресурс
сразу поставили defer на освобождение
только потом пошли в основную логику
Это мелочь, но она сильно снижает шанс забыть cleanup, когда функция со временем обрастёт новыми ветками, логированием, ранними return и обработкой ошибок.

Но defer не всегда обязателен
Если функция очень короткая и cleanup очевиден без отложенного вызова, defer не всегда даёт выигрыш.

Но в большинстве реальных функций с несколькими ветками он улучшает надёжность и читаемость.

Небольшая история из практики
У новичков это всплывает особенно часто при первых API-проектах. Человек уже умеет читать файл, отправлять HTTP-запрос, делать SQL-запросы, но ещё не привык думать про жизненный цикл функции и освобождение ресурсов. В итоге код вроде работает, а потом начинаются странные подвисания, накопление открытых объектов и баги, которые плохо воспроизводятся.

### Где defer реально живёт в коде

#### Файл (Освободить ресурс)
открыли файл -> закрыли файл
```go
f, err := os.Open("data.txt")
if err != nil { return err }
defer f.Close()
```

#### Lock (Снять блокировку)
захватили lock -> сняли lock
```go
mu.Lock()
defer mu.Unlock()
```

#### Response Body (Освободить ресурс)
получили ответ -> закрыли body
```go
resp, err := http.Get(url)
if err != nil { return err }
defer resp.Body.Close()
... // работа с resp.Body
```

defer становится не просто синтаксисом, а частью нормального инженерного мышления.

Опасная ловушка: defer в цикле
Вот это место очень важно.

defer внутри цикла — не автоматически зло, но очень частая ловушка.

```go
for _, name := range files {
f, err := os.Open(name)
if err != nil {
return err
}
defer f.Close()
// работа с файлом
}
```

На первый взгляд кажется, что файл будет закрываться в конце каждой итерации.
Но нет.

Все defer f.Close() отработают только при выходе из всей функции, а не после каждой итерации.

Почему это опасно
Если файлов много, вы можете долго держать открытыми сразу кучу os.File.

Это уже риск:
утечки дескрипторов
лишней нагрузки на систему
странных ошибок на большом количестве файлов
проблем, которые на маленьких тестах не видны
Когда defer в цикле допустим

Если итераций мало, ресурсы дешёвые, а код очень прозрачен, это ещё может быть терпимо.

Но в большинстве случаев лучше либо закрывать ресурс явно в конце итерации, либо выносить тело итерации в отдельную функцию.

Правильный вариант через отдельную функцию

```go
func processFile(name string) error {
f, err := os.Open(name)
if err != nil {
return err
}
defer f.Close()
// работа с файлом
return nil
}
func main() {
for _, name := range files {
if err := processFile(name); err != nil {
// обработка ошибки
}
}
}
```

defer срабатывает в конце каждой обработки файла, потому что каждая итерация живёт в своей функции.

### Альтернатива без defer
Иногда проще явно закрыть ресурс:

```go
for _, name := range files {
f, err := os.Open(name)
if err != nil {
return err
}
// работа с файлом
f.Close()
}
```

Но здесь уже надо быть аккуратным со всеми путями выхода и ошибками.

### defer в цикле — проблема / правильный подход

#### defer в цикле — проблема
- цикл (итерации 1, 2, 3 ... N):
  - открыть -> defer (defer копится в стеке функции)
- закроется в конце функции
- Итог: ресурсы накапливаются, закрываются слишком поздно

#### правильный подход
- отдельная функция (итерации 1, 2, 3 ... N):
  - [ открыть -> обработать -> закрыть ] (закрывается на каждой итерации)
- Итог: ресурсы не копятся, закрываются сразу на каждой итерации

Если используешь defer в цикле, сначала спроси себя: точно ли мне нужно ждать конца всей функции?

Panic, recover и defer
Теперь разберём связку, которую очень любят и в статьях, и на собеседованиях.

Почему recover работает именно через defer
recover() имеет смысл только внутри отложенной функции, вызванной через defer.

```go
package main
import "fmt"
func safe() {
defer func() {
if r := recover(); r != nil {
fmt.Println("panic recovered:", r)
}
}()
panic("boom")
}
func main() {
safe()
fmt.Println("program continues")
}

panic recovered: boom
program continues
```

функция safe ставит отложенный вызов
внутри этого defer лежит recover()
дальше случается panic("boom")
перед падением функции Go запускает все defer
recover() перехватывает панику
программа не падает целиком

### Схема работы panic + defer + recover
1. функция -> 2. panic -> 3. defer -> 4. recover (вызывается внутри defer) -> 5. выполнение продолжается

Почему recover вне defer не поможет
Такой код бесполезен:

```go
r := recover()
fmt.Println(r)
```

recover() работает только в нужном контексте: внутри deferred-функции во время раскрутки panic.

Важный практический нюанс
defer сам по себе не «лечит» panic. Он просто даёт точку, где у вас есть шанс отреагировать до окончательного падения функции.

полезно разделять две мысли:

defer гарантирует, что cleanup всё равно попробует выполниться
recover() даёт возможность перехватить панику, если это допустимо по архитектуре

Где это реально используют:
в инфраструктурном коде
в middleware
в обвязках воркеров
в библиотеках, где нужно безопасно пережить панику и залогировать её
Чего не надо делать

Не надо превращать recover() в способ маскировать плохой код.

Если у вас повсюду паники, а потом везде стоит recover(), это не устойчивость, это попытка подмести мусор под ковёр.

Нормальный подход такой:
ошибки обрабатываем как ошибки
panic оставляем для действительно аварийных ситуаций
recover() используем там, где нужно защитить систему от полного падения

Как связаны panic, defer и recover?
При panic Go всё равно запускает defer, а recover() внутри deferred-функции может перехватить панику.

Где defer чаще всего используют в реальной работе?
Для Close(), Unlock(), cleanup-логики и безопасного завершения работы с ресурсами.

### DEFER В GOLANG — ПОЛНЫЙ ЧЕК-ЛИСТ
Как работает, когда выполняется и как использовать правильно
Главная идея: defer откладывает выполнение функции до момента выхода из текущей функции (return или panic).

#### 1. ЧТО ТАКОЕ DEFER
defer регистрирует отложенный вызов функции, который выполнится после того, как текущая функция завершится. Независимо от того, как она завершится: обычный return или panic (если не вызван os.Exit).

- Гарантирует cleanup (очистку ресурсов)
- Упрощает код и уменьшает дублирование
- Работает при ранних return
- Работает при panic (функции всё равно выполнятся)
- Выполняется в обратном порядке (LIFO)

```go
func example() error {
    f, err := os.Open("file.txt")
    if err != nil {
        return err
    }

    defer f.Close() // закроется
    // ... работа с файлом
    return nil // f.Close() вызовется здесь
}
// f.Close() выполнится после return
```

#### 2. КОГДА ВЫПОЛНЯЮТСЯ DEFER
defer выполняются в момент, когда функция завершает выполнение.

- Обычный return — Все defer выполнятся
- Ранний return — Все defer выполнятся
- panic — Все defer выполнятся, panic продолжит подниматься
- os.Exit() — defer НЕ выполнятся

Важно: defer не сработают при os.Exit(), runtime.Goexit() и в случае падения программы (segmentation fault и т.п.).

#### 3. ПОРЯДОК ВЫПОЛНЕНИЯ — LIFO
Отложенные вызовы выполняются в порядке, обратном их добавлению (Last In, First Out).

- Порядок добавления:
  1. defer first()
  2. defer second()
  3. defer third()

- СТЕК DEFER (сверху вниз):
  3. third()
  2. second()
  1. first()

- Порядок выполнения:
  1. third()
  2. second()
  3. first()

Представляй defer как стопку тарелок: последнюю положил — первую снимут.

#### 4. АРГУМЕНТЫ DEFER: КОГДА ОНИ ВЫЧИСЛЯЮТСЯ
Аргументы функции в defer вычисляются сразу в момент вызова defer, а не в момент выполнения.

- Аргумент вычислился сразу:
```go
func demo() {
    x := 10
    defer fmt.Println(x) // x = 10
    x = 20
}
// Выведет: 10
```
  - Значение x (10) зафиксировалось в момент defer
  - Изменения после этого не влияют на аргумент
  - Работает для любых аргументов

- Значение прочиталось позже:
```go
func demo() {
    x := 10
    defer func() {
        fmt.Println(x) // читаем x позже
    }()
    x = 20
}
// Выведет: 20
```
  - x читается в момент выполнения defer
  - Видит все изменения
  - Используй, если нужно текущее значение

#### 5. ИМЕНОВАННЫЕ РЕЗУЛЬТАТЫ + DEFER
defer может изменить именованный результат перед тем, как он будет возвращён.

Схема:
return 10 (выполняется) -> named result (result получает 10) -> defer меняет (defer выполняется и меняет result) -> итог 11 (наружу уходит 11)

```go
func calc() (result int) {
    defer func() {
        result = result + 1
    }()
    return 10
}
// result = 10 -> result = 11 -> return 11
```

defer выполняются после присваивания именованным результатам, но до выхода из функции.

#### 6. ГДЕ DEFER РЕАЛЬНО НУЖЕН (ПРАКТИЧЕСКИЕ ПАТТЕРНЫ)

- Файл (Открыл -> обязательно закрой):
```go
f, err := os.Open("file.txt")
if err != nil {
    return err
}
defer f.Close()
// ... работа с файлом
```

- Mutex / Lock (Захватил -> обязательно освободи):
```go
mu.Lock()
defer mu.Unlock()
// ... критическая секция
```

- HTTP Response Body (Получил ответ -> закрой body):
```go
resp, err := http.Get(url)
if err != nil {
    return err
}
defer resp.Body.Close()
// ... читаем resp.Body
```

Главное правило: получаешь ресурс — сразу же ставь defer рядом с этим местом.

#### 7. DEFER В ЦИКЛЕ — ЛОВУШКА

- Неправильно: defer копится
defer выполняется только после выхода из функции, ресурсы копятся на каждой итерации.
```go
func processItems(items []string) error {
    for _, item := range items {
        f, err := os.Open(item)
        if err != nil {
            continue
        }
        defer f.Close() // копится!
        // ... обработка
    }
    return nil // все файлы закроются только здесь
}
```
Схема: Итерация 1 -> 2 -> 3 ... N; Открыто файлов: 1 -> 2 -> 3 ... N
Проблема: при большом N можно упереться в лимиты дескрипторов файлов и памяти.

- Правильно: вынеси в отдельную функцию
Каждая итерация имеет свой стек defer и закрывает ресурс сразу после работы.
```go
func processItems(items []string) error {
    for _, item := range items {
        if err := processItem(item); err != nil {
            continue
        }
    }
    return nil
}

func processItem(item string) error {
    f, err := os.Open(item)
    if err != nil {
        return err
    }
    defer f.Close() // закроется тут же
    // ... обработка
    return nil
}
```
Схема: Итерация 1 -> 2 -> 3 ... N; Открыто файлов: 1 -> 0, 1 -> 0 ... 1 -> 0
Ресурс открывается и закрывается на каждой итерации.

#### 8. PANIC, DEFER И RECOVER
Как это работает по шагам:
1. Функция выполняется — Код работает как обычно.
2. Возникает panic — Выполнение прерывается, начинается раскрутка стека.
3. Срабатывают defer — Все отложенные функции выполняются в порядке LIFO.
4. recover перехватывает — Если внутри defer вызывается recover(), panic перехватывается и выполнение продолжается.
5. Выполнение продолжается — Функция продолжает работу после defer (если panic был восстановлен).

```go
func safe() {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("Поймали panic:", r)
        }
    }()

    fmt.Println("До panic")
    panic("что-то пошло не так")
    // Этот код не выполнится
    // но после defer работа продолжится
    fmt.Println("После panic (не дойдём)")
}

func main() {
    safe()
    fmt.Println("Выполнение продолжается после recover")
}

// Вывод:
// До panic
// Поймали panic: что-то пошло не так
// Выполнение продолжается после recover
```

Если recover() не вызван — panic продолжит подниматься вверх по стеку.

#### ДОПОЛНИТЕЛЬНЫЕ ЗАМЕТКИ И ЛУЧШИЕ ПРАКТИКИ

- Когда использовать defer:
  - Закрытие ресурсов (файлы, сети, БД, mutex)
  - Освобождение блокировок
  - Отмена контекстов: defer cancel()
  - Логирование времени выполнения
  - Отмена таймеров и тикеров
  Получил ресурс — сразу поставь defer!

- Когда defer может быть избыточен:
  - Очень горячие участки кода (микрооптимизации)
  - Короткие функции без ранних return
  - Очень частые вызовы в tight loop (вынеси в отдельную функцию)
  График накладных расходов: Незначительно -> Лучше без defer (горячий цикл)

- Полезные правила:
  - Порядок defer = обратный порядок добавления (LIFO)
  - Аргументы вычисляются сразу
  - Используй анонимную функцию, если нужно значение «на момент выполнения»
  - defer выполняются при return и panic
  - Не надейся на defer при os.Exit()

- Быстрая памятка:
  - defer f.Close() — всегда закрывай рядом с открытием
  - defer mu.Unlock() — после Lock()
  - defer cancel() — после context.WithCancel()
  - defer t.Stop() — для таймеров/тикеров
  - defer recover() — только внутри defer!

Как правильно объяснить работу defer в GO, чтобы собеседование прошло идеально 🔥

На собесах по Go часто спрашивают про оператор defer. Почему? Потому что он показывает, насколько ты глубоко понимаешь порядок выполнения кода и обработку исключительных ситуаций.

1️⃣ Что такое defer и зачем он нужен? 🤔
defer в Go — это оператор, который откладывает выполнение функции до момента выхода из текущей функции. Чаще всего используется для освобождения ресурсов, закрытия файлов или соединений с БД, чтобы гарантировать, что ресурс всегда будет освобождён.

Пример:

func readFile() {
    file, _ := os.Open("data.txt")
    defer file.Close() // файл закроется гарантированно в конце функции
}


2️⃣ Порядок выполнения нескольких defer 🔄
Если в одной функции несколько вызовов defer, то они выполняются в порядке LIFO (последний зашёл — первый вышел). Важно помнить это, чтобы не запутаться и избежать неожиданного поведения

Пример:

func example() {
    defer fmt.Println("Первый defer")
    defer fmt.Println("Второй defer")
    defer fmt.Println("Третий defer")
}

// вывод будет:
// Третий defer
// Второй defer
// Первый defer


3️⃣ Как defer влияет на возвращаемые значения? 🔥
На собеседованиях любят спрашивать tricky вопрос про взаимодействие defer и именованных возвращаемых значений. defer может изменить возвращаемое значение перед выходом из функции

Частый пример с собесов:

func tricky() (x int) {
    defer func() {
        x = 100 // меняем значение перед возвратом
    }()
    return 10 // сначала вернёт 10, но defer изменит это на 100
}

fmt.Println(tricky()) // 100 (!)


4️⃣ Как defer работает с panic/recover? 🚨
Если внутри функции произошла паника, то все вызовы defer выполнятся перед тем, как паника продолжит распространяться наверх. Это свойство активно используется вместе с recover(), чтобы восстановить приложение после паники

Классический пример обработки паники:

func safeDivide(a, b int) (result int) {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("Произошла паника:", r)
            result = 0 // возвращаем безопасное значение
        }
    }()
    result = a / b // возможна паника (деление на 0)
    return
}

fmt.Println(safeDivide(10, 0)) // "Произошла паника" и вывод 0
