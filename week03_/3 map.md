map - хэш-таблица Go: пары "ключ -> значение".

В map:
- не гарантирует порядок
- может расширяться
- создаётся через make, иначе panic

```go
m := make(map[string]int)
m["age"] = 25
m["age"] // 25
```

Ошибки:
- var m map[string]int без make -> panice при записи
- использование вложенных map без инициализации
- append по слайсу, который использует два пакета одновременно
- изменение underlying array через другой slice


map в реальных сервисах:
- соц. сети. ключ: userID -> значение: профиль пользователя
- интернет магазин. ключ: товарID -> значение: описание товара
- система авторизации. ключ: sessionID -> значение: данные сесии


### Устройство map (старая реализация)

ключ -> хэш-функция -> число(хэш) -> хэш-таблица (массив bucket'ов)

- tophash[8]
- keys[8]
- values[8]

Алогритм:
хэш прогоняется через хэш функцию, получается число
это число указывает на бакет в хэш-таблице
внутри бакета могло находиться до 8 элементов - массив ключей, массив значений и массив маленьких кусочков хэша (top hash)
дальше по этому бакету идёт поиск и вставка.
если ключей оказалось слишком много, то создаётся overflow bucket

Хэш-функция - получает ключ и превращает его в число


key := "String"
hash := hash(key) = 1234567890
Один и тот же ключи -> всегда одинаковый хэш

Коллизия - разные ключи дают одинаковый хэш.

Как по полученному хэшу найти bucket?

bucket - коробка для хранения ключей и значений.

Чтобы понять в какой bucket положить элемент:
bucket_index = hash % 8 // 2

Остатоком от деления будет номер bucket

Формально:
index = hash & ((1<<B)-1)
число bucket'ов всегда степень двойки (2^B).

Способы борьбы с коллизиями:
1) Открытая адресация - поиск след. свободного места.
2) Цепочки (chaining) - в одной ячейке храним список с несколькими элементами.
3) Доп. хэш. Повторный прогон получившегося хэша через хэш-функцию - получается другое число.

До 1.24 использовался метод цепочек, то есть buckets.

Один bucket хранит до 8 элементов и состоит из трёх массивов:
- tophash (маленькие кусочки хэша)
- keys
- values

По tophash сначала отбирали кандидатов, потом сравнивали сами ключи.

Вставка нового элемента в map:

hash(key) -> hash -> bucket со свободным слотом / заполненный

Если в bucket есть свободный слот, помеченный пустым (в том числе после delete), он будет переиспользован

В массиве tophash записывается верхний байт хэша ключа. Используется как быстрый фильтр при поиске.

У каждого слота в bucket есть tophash - это верхний байт хэша ключа. Нужен, чтобы быстрее находить кандидатов при поиске.

Если бакет заполенен - создаётся overflow bucket и новый элемент кладётся туда.

Так в старой реализации могла появится целая цепочка bucket.
overflow bucket решают проблему переполнения. Но поиск и вставка становятся медленние, потому что нужно проходить по цепочке.

Поиск элемента:
Берём элемент, считаем хэш, находим bucket.
В bucket смотрим на массив tophash, если совпал - проверяем ключи, если нашли - возвращяем значение.
Если tophash не совпал, то пропускаем слот без проверки ключа. Может быть что tophash совпал, но ключи разные.
hash(number) -> Bucket с совпавшим tophash -> Сравнить реалиный ключ -> Overflow, если в основном не нашли - идём дальше.

Удаление элемента:
Удаление = помечаем слот пустым. Ключ и значение считаются стёртыми, но слот остаётся в bucket.
Таких дыр могло становится много, особенно в overflow bucket, это замедляло поиск - нужно обходить слоты, даже пустые.
Память занята, а пользы от неё нет.


Poct (grow) и load factor
Когда map заполнялась, Go создавал новую таблицу в 2 раза больше и перекидывал туда элементы.

Решение по росту принималось в 2 условиях:
- если в среднем в каждом bucket больше 6.5 элементов.
- если overflow-bucket примерно столько, сколько основных.

В обоих случаях Go запускал рост: создавал новую таблицу и перекидывал туда все ключи.
Для больших map была дорогостоющая операция по времени и памяти.

Копирование bucket постепенное, во время след. операций, а не сразу моментальное.

Новая таблица (16 bucket)

Когда таблица становится слишком плотной или overflow-bucket слишком много - запускается рост и ключи пересыпаются в новую таблицу.

Проблеым старой реализации:
- Слишком много сравнений ключей. Частые проверки реальный ключей нагружает CPU и замедляют поиск.
- Overflow-bucket плохо работали с памятью. Цепочки overflow -> плохая локальность. Данные лежат далеко друг от друга - большое пропусков кеша и лишних шагов.
- Удаление оставляло мусор. Пустые/удалённые слоты копятся и ухужщшают поиск и память
- Рост x2 map имел дорогую пересыпку, нужно было перекидывать все элементы. Резкое удвоение таблицы создаёт пиковые задержки и расход памяти.

### Поэтому в 1.24 разработчики решили переписать map.

Теперь под капотом архитектура Swiss Table.
Вместо overflow bucket, группа по 8 элементов и этих группах хранятся спец. контрольные байты. Позволяют очень быстро отобрать кандидатов.
